The migration DSL now drops and renames through expand and contract steps, so zero-downtime removals no longer need raw `schema.sql` (STA-1406, ADR 0159 decision 3). `t.dropColumn(column, { after, type })`, `t.finishRenameColumn(from, to, { after, type })`, `schema.finishRename(from, to, { after })` and `schema.drop(table, { after })` are contract steps: each opens its transaction with a release gate that refuses the migration while the migration named in `after` was applied under the release this run applies (or never), and `after` becomes one of the migration's edges, so gen orders the two and refuses an unknown id. `stackra db migrate --release <id>` (else `STACKRA_RELEASE`) names the deploy's release, records it on each `schema_migrations_history` row (new `release_id` column) and, outside dev, preview and test, sets `stackra.migrate_from_version` and `stackra.migrate_release`; a retried deploy of the same release and a run naming no release are refused, a forward-only run naming no release is refused before any change on a database that already has applied migrations (so no file is recorded without the release a later retry would name), and the gate passes on a fresh database and wherever Encore's runner or a test applies the files. The data gate and every backfill batch run with `row_security` off, so a role that row-level security would filter, or one without SELECT on the table, fails with a refusal naming both causes instead of counting no rows. `t.renameColumn(from, to, { type })` adds the new, nullable column (no default, generation or NOT NULL) with a `trg_<table>_<from>_<to>` trigger that keeps both names equal on every write, and `schema.rename(from, to)` renames a table and leaves a `security_invoker` view under the old name, so the release before the rename keeps reading and writing. `t.check(name, expression)` adds `ck_<table>_<name>` (`NOT VALID` plus a validation step on an existing table), `t.exclude(name, elements, options)` adds an `ex_<table>_<name>` exclusion constraint to a new table, `t.timeRange(name)` is a `tstzrange` column, and `t.dropIndex` and `t.dropCheck` drop what an earlier migration built, each with a dev inverse.

The new `Backfill` kind (`database/backfills/<name>.backfill.ts`) is the data half of a contract step: `Backfill({ key, table, pending, set?, by?, batch?, pause? })` runs in keyset batches through `runBackfill(type, session)` or `backfill(type, { maxBatches })` from `./node`, moving its cursor in each batch's transaction, pausing between batches, and keeping its progress in the new `database.backfill_runs` ledger (migration `database.0009_create_backfill_runs`), so a queue job runs a slice and queues itself again until it is finished. `schema.requireBackfill(key, { table, pending })` refuses a contract step while any row is still pending. Gen, the `base-matches-suffix` lint table and the module-group check know the `backfill` kind.
