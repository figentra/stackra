An Idempotency-Key's result now commits with the action's writes, and a committed call never frees its key, so a retry can no longer repeat a committed write (STA-2797, ADR 0495 note of 2026-11-26). The pipeline writes the result of a store that joins transactions (the Postgres store) inside the call's transaction, after the interceptors; with no `CallIsolation` bound it opens one `UnitOfWork` transaction around such a keyed call. A Valkey or memory store's claim is extended to the replay window as the last step before the commit (a claim another call took after this one's lease lapsed rolls the call back with `idempotency_key_in_progress`, so it never writes twice); the store is completed right after the commit, and if that write fails the caller still gets its output, the failure is logged as `actions.idempotency_store_failed`, and the key stays held for the window. A claim now holds its key for a 15-minute lease, separate from the 24-hour replay window, so a call whose process died before its commit frees its key after the lease instead of answering in-progress for a day. Every claim carries a holder token unique to the call, and the memory and Valkey stores extend, complete or free a key only while it still holds that call's claim.

Breaking for anyone implementing `IdempotencyStore` (only the shipped memory, Valkey and Postgres drivers do): `claim(key, fingerprint, lease, holder)` takes the lease and the call's holder token; the new `extend(key, fingerprint, ttl, holder)` keeps the holder's claim (or a free key) held for the window and resolves `false` when the claim was lost; `complete(key, fingerprint, output, ttl, holder)` takes the fingerprint, the replay window and the holder, and writes the record when the key is held by that holder or free; `release(key, holder)` frees only the holder's claim.
