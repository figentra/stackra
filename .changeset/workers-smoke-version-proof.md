The `cloudflare-workers` provider's smoke now proves which Worker version answered, so a deploy can no longer pass its smoke on the old version. Before, it smoked a new version through `Cloudflare-Workers-Version-Overrides` while that version was in no deployment; Cloudflare honours an override only for a version in the current deployment and routes any other request as usual, so the "0% smoke" checked the version already serving and passed even when the new one was broken. The provider now adds the new version to the deployment at 0% first (`wrangler versions deploy <serving>@100 <new>@0`), smokes it there by override, and only then moves traffic in the member's `rollout` steps (10/50/100 for an `api` member in production), smoking after every step, the 100% one included. Every smoke answer must name the version under test: in its `x-stackra-version` header (the default, for a Worker with a script on every path), or, with the new member key `versionProof: route`, in the `/-/version` route read before and after the checks (a Worker whose answers are static assets). Another version answering, or none named, fails the step: at 0% the new version leaves the deployment again and no traffic moves; at a later step the previous version is put back. `verify` proves the version its record names. A member must now list at least one smoke check, or it is refused before anything ships.

To adopt it, give each Worker a `version_metadata` binding (`CF_VERSION_METADATA`) and name its id in `x-stackra-version` on every answer, or, for an assets-only Worker, add a script answering only `GET /-/version` with `{ "version": "<id>" }` and the same header (`run_worker_first: ["/-/version"]`) and set `versionProof: route`. `WORKER_VERSION`, `WorkerVersionProof` and `servedVersionProblem` are exported so another smoke (the box deploy's) applies the same proof.
