A package lives at `packages/<category>/<name>` and is published as `@stackra/<name>`. The category is only a folder (see [Package categories](/guides/packages)). Every package is also a [member](/standards/members) and carries its required files.

## Choose the archetype

Asked once, when the package is created. The first yes wins.

| # | Question                                                                                  | Archetype  | Scaffold kind |
| - | ----------------------------------------------------------------------------------------- | ---------- | ------------- |
| 1 | Does it own business meaning (entities, use cases, adapters, a delivery surface)?         | `domain`   | `domain`      |
| 2 | Is it a shared build or quality preset with no logic?                                     | `tooling`  | `tooling`     |
| 3 | Does it serve other packages with no business meaning of its own?                         | `platform` | `platform`    |
| 4 | Otherwise: a small flat utility with one entry and no layers                              | `lib`      | `lib`         |

Domain or platform: would the code need renaming to make sense in a different product? Domain. A package that fits none of these is evidence of a new archetype, which is an [ADR 0004](/adr/0004-package-archetypes-and-layers) amendment, not a reason to stretch `platform`.

Archetypes recorded as reference only (contracts, UI facade, provider, SDK, runtime, asset) have no member yet and govern nothing. Each becomes binding in the change that creates its first member; contracts are specified in [ADR 0015](/adr/0015-contract-packages).

## Shapes

### Domain: four layers

```text
src/
  core/             domain meaning: entities, value objects, invariants, domain errors
  application/      use cases; owns the ports (interfaces) it needs
  infrastructure/   implementations of those ports
  presentation/     delivery surfaces: api/, then opt-in react/ web/ native/
  index.ts          the public surface, re-exports only
```

| Layer            | May import                                  | Never imports                                                |
| ---------------- | ------------------------------------------- | ------------------------------------------------------------ |
| `core`           | nothing else in the package                 | other layers; `react`, `react-dom`, `react-native`, `encore.dev` |
| `application`    | `core`                                      | `infrastructure`, `presentation`; the same host libraries    |
| `infrastructure` | `core`, `application`                       |                                                              |
| `presentation`   | `core`, `application`                       | `infrastructure` (the host binds adapters)                   |

`presentation/native` composes React and never `presentation/web`. A port belongs to `application/`, never to `infrastructure/`. Layers are addressed with subpath imports (`#core`, `#application/*`, declared in `package.json` `imports`).

### Platform

`src/core/` is the runtime-neutral capability. Opt-in entries sit beside it, each its own export subpath and its own peer-dependency boundary:

| Entry          | Runtime        | Holds                                        |
| -------------- | -------------- | -------------------------------------------- |
| `core`         | `isomorphic`   | the capability; imports no host library      |
| `contracts`    | `isomorphic`   | types and tokens a consumer needs at zero runtime cost |
| `react`        | `browser`      | hooks and providers; imports only `core`     |
| `native`       | `react-native` | React Native bindings; imports only `core`   |
| `node`         | `node`         | Node-only concerns; imports only `core`      |
| `testing`      | `node`         | fakes and builders for consumers' tests      |

There is no `presentation/` in a platform package. Rules for a package that works under more than one runtime:

1. The root entry is runtime-neutral; a runtime-specific symbol never reaches it.
2. Every runtime-specific dependency is an optional peer (`peerDependenciesMeta`), so installing the package pulls in no host library.
3. Reaching a subpath without its peer fails with a message naming the missing peer, not a module-resolution error from inside a barrel.

### Lib

One entry (`.`), no layers: `src/<kebab-name>.ts` re-exported by `src/index.ts`. A second entry point is the sign that it should be a platform package.

### Tooling

Data, not a build: JSON or JSONC presets with a `files` allowlist and an `exports` map, tag `tier:config`, no `src/` layers. A change goes into the preset, never into each consumer. Presets keep `./x.ts` specifiers because plain Node loads them.

## Exports, barrels and imports

- Every package builds with tsdown to ESM-only `dist/*.mjs` plus `.d.mts`. Each `exports` entry lists the `@stackra/source` condition first (pointing at `./src/**`, read by typecheck, Vitest and Vite), then `types` and `default` in `dist` (runtimes load these). The validator checks the shape ([0025](/adr/0025-packages-publish-to-private-registry)).
- `index.ts` is the only barrel name. A barrel declares nothing; it re-exports.
- A consumer imports the package or a declared subpath, never another package's `src/` (`@stackra/*/src/*` is a lint error).
- A package never imports an app, a service, or `encore.dev` and `~encore/*`.
- A shared package holds mechanisms, not product literals: no brand name, locale list, project id or `process.env` read. It exposes decorators, base classes and typed config contracts, never `define*()` ([0094](/adr/0094-decorators-only-authoring)), and the app holds the definition. See [Boundaries](/constitution/boundaries).
- Naming, one declaration per file and specifier style: [Code style](/standards/code-style).

## Provenance of copied code

Code copied from another repository is copied, not depended on, and says where it came from. Next to the package, `ORIGIN.md` records:

- the source repository, path and commit hash, and the date;
- what changed on copy (renames, product values removed, dependencies swapped);
- how to pull a later change: diff the source at the new commit against the recorded one, port by hand, update the file.

### Port or rewrite

Decide per package before copying:

| Verdict    | When                                                                                          |
| ---------- | --------------------------------------------------------------------------------------------- |
| **Port**   | The design is sound and tests exist; only names, product literals and dependencies change     |
| **Shrink** | Most of it is surface nobody uses; keep the core and its tests                                |
| **Replace**| A platform primitive (`fetch`, Intl) does the job; keep only the parts it lacks, with new tests |
| **Rewrite**| The model is wrong (strings where typed keys belong); keep the ideas, write it fresh          |
| **Drop**   | A few typed lines in an existing package replace it                                           |

A port that diverges from its origin does so openly: in `ORIGIN.md`, not silently.

## What enforces this

| Rule                                                              | Check                                                        | Status  |
| ----------------------------------------------------------------- | ------------------------------------------------------------ | ------- |
| Layer direction (`core`, `application`, `presentation`, native)   | oxlint `no-restricted-imports` in `boundaries.jsonc`         | Yes     |
| No import of an app, service or `encore.dev` from a package       | oxlint `boundaries.jsonc` + `turbo boundaries`               | Yes     |
| No deep import of `@stackra/*/src/*`                              | oxlint `boundaries.jsonc`                                    | Yes     |
| `exports` dist + `@stackra/source` shape, `sideEffects: false`   | `validate-repository.mjs`                                    | Yes     |
| Unused files and exports                                          | `knip`                                                       | Yes     |
| Archetype fields and a barrel/deep-import shape check             | planned: validator check (ported from a package-shape script) | No     |
| No product literal or `process.env` in a package                  | planned: validator check                                     | No      |
| `ORIGIN.md` present where code was copied                         | planned: validator check; review by `package-steward` today  | No      |

The `package-steward` reviews every new package and every new `exports` subpath; see the [agent roster](/agents/roster).
