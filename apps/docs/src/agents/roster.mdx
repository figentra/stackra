Twelve roles ship with the `sdlc` plugin. Their names are canonical and their definitions are not copied into this repository. The rest are new roles this repository adds under `.agents/agents/`, named `<domain>-<role>`.

## Tiers and models

An agent declares a **tier**, never a model. `.agents/models.json` maps each tier to a model, so a model change is one edit. Everything is Claude. Delegation to other model families was tried and retired; the reasoning is in [ADR 0017](/adr/0017-agent-roster-and-models).

| Tier default | Model | Used for |
| --- | --- | --- |
| Frontier | Opus | Guardians, the orchestrator, spec authoring, officers |
| Standard | Sonnet | Executors and reviewers |
| Economy | Haiku | Mechanical stewards |

The per-agent model in the table below is the starting assignment. No role is assigned to `fable`: there is no evidence yet for where it fits, so revisit it after a trial. If a cheaper tier produces a wrong result, escalate one tier for that task rather than editing the agent.

## Who blocks

Two rules apply to every role.

1. **Where enforcement and prose disagree, the enforcement is the fact.** Each blocking role has something that fails mechanically when its concern breaks: `pnpm verify`, `pnpm validate`, the Turborepo boundaries, the oxlint layer rules. If a charter and the check disagree, the charter is the bug.
2. **Never report a stage complete on the strength of a gate that could not have observed it.** Say what was and was not run.

A human approves every release and every deploy. No agent promotes to production.

## Routing

| The work | Goes to |
| --- | --- |
| Anything unclear, or touching more than one row below | `delivery-orchestrator` first |
| Adds a member, crosses a tier, or reverses a recorded decision | `architecture-guardian` before anyone builds |
| Changes an `api()` contract, an id prefix or the generated client | `api-contract-reviewer` |
| Touches auth, secrets, tenancy, payments, files or webhooks | `security-tenancy-reviewer` (gate) |
| Backend behaviour in a service | `service-builder` |
| A web or mobile screen | `frontend-builder` or `mobile-builder`, then `design-brand-reviewer` and `accessibility-reviewer` |
| Tests, isolation tests, contract tests | `test-engineer` |
| A new package or a new `exports` subpath | `package-steward` |
| Versions, advisories, licences, pins | `dependency-steward` |
| ADR, docs, rule or roster drift | `docs-governance` |
| CI, release, environment | `release-operations` |
| Any non-trivial change | `code-reviewer` (informs, does not block) |

## One charter shape

Every agent file under `.agents/agents/` has the same shape, so a reviewer knows where to look: frontmatter with `name`, `description` (what it does and when to call it), `tier` and the tool grant, then **Must read** (the rules, pages and skills it loads first), a numbered checklist, and a closing verdict. A gate agent states what it blocks on. A reviewer that never edits carries a read-only tool grant. The verdict is `PASS`, `TASKS` (findings, each with a named owner) or `BLOCKED`.

`code-reviewer` asks four questions in a fixed order because each builds on the last: is it correct, is it simple, is it reused, is it at the right altitude. It reports findings as `blocking`, `should-fix` or `consider`, each with a file reference and a concrete failure, never a preference. It does not report anything `pnpm verify` already covers. Finding one of those in review means the gate is broken, and that finding replaces the original.

## Folded away, not created

These existed in older roster designs and are covered by an existing role instead.

- Backend architecture review is part of `architecture-guardian`.
- ADR stewardship and changeset stewardship are part of `docs-governance` and `release-operations`.
- Separate e2e, brief-author, sweeper and merge-train roles are part of `test-engineer`, `delivery-orchestrator` and `release-operations`.
- Separate stewards for docblocks, errors, redaction and test helpers are part of `code-standards-steward`, `security-tenancy-reviewer` and `test-engineer`.
- A spec reviewer is the `spec-verify` skill.
- A design agency (director, senior designer, design engineer) was judged too heavy and unproven. One non-blocking `design-brand-reviewer` plus the design skills replaces it.
- Business intake and AI-agent builders are not ported. The AI builder returns with the AI engine decision.
