Not every change needs a spec. Work that touches money, permissions, data integrity, external contracts, concurrency or state machines does, and so does anything several agents will implement or that will outlive its author's memory. Everything else is a direct change reviewed at the gates on [Working with agents](/agents/index).

The spec engine is [GitHub spec-kit](https://github.com/github/spec-kit) (`specify` CLI, pinned in `.specify/init-options.json`). It is initialised for both Claude Code (`.claude/skills/speckit-*`) and OpenCode (`.opencode/commands/speckit.*`), so both assistants run the same flow. A Stackra preset (`.specify/presets/stackra`) adds the gate described below. A change that is not specified starts at `/speckit.specify`: the prompt-hints hook nudges an ad-hoc feature request there.

## The flow

```text
/speckit.specify ──▶ /speckit.clarify ──▶ /speckit.plan ──▶ /speckit.tasks ──▶ /speckit.implement
   spec.md + Impact     marks "complete"    gate runs first    tasks → Linear
```

| Command                                  | Writes                         | Stackra rule                                                         |
| ---------------------------------------- | ------------------------------ | -------------------------------------------------------------------- |
| `/speckit.specify`                       | `specs/NNN-feature/spec.md`    | Interviews the **Impact** questionnaire. Never plans                 |
| `/speckit.clarify`                       | Answers in `spec.md`           | Sets `**Clarifications status**: complete` only when nothing is open |
| `/speckit.plan`                          | `plan.md`, research, contracts | **Refuses** until the spec gate passes                               |
| `/speckit.tasks`                         | `tasks.md`                     | Tasks map to Linear sub-issues of the spec's issue                   |
| `/speckit.analyze`, `/speckit.checklist` | reports                        | Optional                                                             |
| `/speckit.implement`                     | code                           | Executes `tasks.md`                                                  |

## The clarify-before-build gate

Every `spec.md` carries three things the template provides:

- `**Linear**: STA-n`, the issue for the spec (team STA). Optionally `**Linear project**`.
- `**Clarifications status**: pending | complete`.
- An `## Impact` questionnaire, every line answered (`none` is an answer): apps, services and packages touched, cross-service events, tenancy and data, secrets (names, never values), whether an ADR is needed, new dependencies.

`tools/scripts/spec-gate.mjs plan` passes only when the status is `complete`, a real `STA-n` is set, every Impact line is answered and no `[NEEDS CLARIFICATION` marker remains. It is enforced twice:

1. **Locally.** `.specify/scripts/bash/setup-plan.sh` runs it first, so `/speckit.plan` fails before it writes anything. `specify init --force` or `specify integration upgrade` can overwrite that script; `spec-gate.mjs ci` fails if the call is gone.
2. **In CI.** `pnpm validate` runs `spec-gate.mjs ci`, which checks every `specs/<feature>/` changed since `origin/main`. A branch that touches `specs/**` without a clarified, Linear-linked spec fails the Quality Gate.

Answers that raise an ADR go to `docs-adr-steward`; a new dependency goes through the catalog (`dependency-steward`).

## Linear

**Work isn't done until its Linear issue is in the right state; agents use `pnpm linear`.** That includes subagents and OpenCode executors that have no Linear MCP.

| Moment        | Command                                                           | Issue state                   |
| ------------- | ----------------------------------------------------------------- | ----------------------------- |
| Start         | `pnpm linear start STA-n`                                         | In Progress, branch commented |
| PR opened     | `pnpm linear review STA-n <pr-url>`                               | In Review, PR attached        |
| Merged        | `pnpm linear done STA-n <link>` (or `Fixes STA-n` in the PR)      | Done                          |
| Anything else | `pnpm linear comment STA-n "…"`, `link`, `create`, `mine`, `open` | unchanged                     |

`pnpm linear` runs `tools/scripts/linear.mjs` under `infisical run --env=dev --path=/agents`. It acts as the **Stackra Agent** Linear app, which becomes the issue's _delegate_, never its assignee. The token is `LINEAR_AGENT_TOKEN`, re-minted from `LINEAR_AGENT_CLIENT_ID`/`LINEAR_AGENT_CLIENT_SECRET` when it expires. The personal `LINEAR_API_KEY` is the fallback. `create` adds the `agent` label when an agent runs it.

Stage transitions report themselves. `spec-gate.mjs plan` comments "clarified" on the spec's issue when it passes. `spec-gate.mjs stage <spec.md> planned|implementing|verified` comments the later stages, and `implementing` also moves the issue to In Progress. `pnpm delegate` requires `--issue STA-n`: it starts the issue at dispatch and comments the result. None of these calls can fail a gate. Linear sync never blocks (ADR 0065 rule 7), and `STACKRA_LINEAR=off` turns them off.

Keys are enforced offline. A `feat`, `fix`, `refactor` or `perf` commit needs a `Refs: STA-n` footer, checked by commitlint in lefthook and over the PR range in CI. The Quality Gate also fails a PR whose title and branch both lack an STA key, unless it is labelled `chore-lane` or comes from `renovate/*` or `changeset-release/*`.

The **Linear sync** workflow (`.github/workflows/linear-sync.yml`, nightly and on push to main) runs `tools/scripts/linear-reconcile.mjs`. It moves issues with a merged PR to Done and issues with an open PR to In Review. It closes "Decide ADR NNNN" once that ADR is Accepted or Superseded. It labels In Progress issues `stale` after 3 days without branch or PR activity, and comments on Backlog issues whose ADR is now Accepted. Each comment carries a `linear-reconcile (<tag>)` marker, so a re-run, or a human reopening an issue, is never overridden. `--dry-run` writes nothing.

`tools/scripts/spec-linear.mjs issue <spec.md>` creates the spec's issue and writes the key into `spec.md`. `tools/scripts/spec-linear.mjs tasks <tasks.md>` creates one sub-issue per `T###` task and appends ` [STA-n]` to the line. Both take `--dry-run` (no token, no calls) and use the same client and tokens as `pnpm linear`, so run them as `infisical run --env=dev --path=/agents -- node tools/scripts/spec-linear.mjs ...`. No token is ever stored in a file.

## The constitution

`.specify/memory/constitution.md` is **generated** from [the laws](/constitution/index) in `apps/docs/src/constitution/*.mdx` by `tools/scripts/agents-sync.mjs`. Edit the laws, run `pnpm agents:sync`, and `pnpm agents:check` fails on drift. Never edit the generated file or run `/speckit.constitution` against it.

## Review checklist

A spec passes review when every row is **PASS** or **N/A with a reason**. Reviewers check against the real tree, not the prose.

1. **Decisions honoured.** Each applicable law and ADR is cited where the plan honours it. See [Constitution](/constitution/boundaries) and [Architecture decisions](/adr/index).
2. **Cross-package consistency.** Every symbol the plan imports exists in that package's current barrel. Dependency direction has no cycle. Events a package emits are listed once, and ones it consumes exist in the owner.
3. **Hygiene.** Every requirement is covered by a task. No `TBD`, `later`, `for now`, `temporary` or `stub`. The plan has no open question at approval.
4. **Impact is true.** The Impact answers match the files the plan actually touches.

`/speckit.analyze` is the mechanical half: it cross-checks spec, plan and tasks. It does not judge whether the requirements were the right ones. That is what the human gate is for.

## When a finding becomes a rule

The `failure-loop` skill handles a gate failing in front of you: classify it, route it to the owner, fix the cause, re-run. For most findings that is the end. For some it is not. A finding about the repository rather than the diff will recur on the next spec, raised by a different reviewer, unless something changes.

A finding is **durable** when any one of three holds:

1. It has been raised before. The second occurrence, not the third.
2. A check could have caught it, and none exists. This is the highest-value trigger.
3. It touches an area where the first occurrence is already too many: secrets, generated artefacts, the CI gate, tier and layer boundaries, a published export surface.

Anything else is one-off. Fix it in the change and write nothing. Promoting a one-off is a real cost, because every rule is read by every agent in every session.

| What was missing                                 | Where it goes                           | Who writes it           |
| ------------------------------------------------ | --------------------------------------- | ----------------------- |
| A decision                                       | An ADR                                  | `architecture-guardian` |
| Enforcement: a decision exists and nothing fails | A check wired into `pnpm verify` and CI | `release-operations`    |
| Awareness: only a human reading can enforce it   | A rule in `.agents/rules/`              | `docs-governance`       |
| A procedure someone re-derived                   | A skill in `.agents/skills/`            | `docs-governance`       |
| A behaviour the spec never specified             | A requirement in `requirements.md`      | `spec-author`           |
| Coverage: right code, nothing would have noticed | A test at the level that catches it     | `test-engineer`         |
| A version, advisory or pin                       | A catalog entry                         | `dependency-steward`    |
| A layout mistake that repeats per package        | A scaffold template change              | `package-steward`       |

**Enforcement beats awareness.** If a finding can be stated as a predicate over files, write the check, not a rule asking agents to remember. **A decision and its enforcement are two artifacts.** An ADR that no check enforces is a standard that only a tired reviewer stands behind, so the ADR ships with its check or names the check and its owner in its follow-up.

The reviewer who raised the finding names the class and the destination. The owning agent writes the artifact. A reviewer who must also write the rule quietly stops raising findings.

Every artifact written by a promotion opens with one provenance line:

```markdown
> Origin: review finding on <spec or change>, <first|second> occurrence — <the finding>.
```

Nothing checks for that line, and there is no findings ledger. A ledger would be a tracked file that goes stale the first week nobody updates it. The line makes existing rules searchable for "has this been seen before", and a rule whose origin nobody can state is a candidate for deletion. A reviewer enforces it, and that limit is stated on purpose.

## Tasks that are not specs

A spec is for work worth specifying. Day-to-day tasks use one task file per repository, not a file per agent, so two agents never disagree about what is open. A task is done only when its code is on the main branch.
