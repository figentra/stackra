## The rules

- **Every change to a member ships with a changeset.** `pnpm changeset` records it; `pnpm changeset:status` fails when a changed member has none (target: chained into `pnpm verify`).
- **`CHANGELOG.md` files are generated** by changesets and never hand-edited.
- **Versions are bumped by the release job on `main`**, not on a feature branch. `guard-bash` denies `changeset version` locally for that reason.
- **Merging the version pull request is the release decision.** A human merges it.
- **Published or tagged versions are permanent.** A version is never republished or silently replaced; roll forward with a new patch.
- **Private by default.** A package becomes publishable only through an ADR that changes this page and `.changeset/config.json` (`access`, `privatePackages.tag`).

## A normal release

<Steps>
  <Step title="Land changesets with the work">
    In each pull request that changes a member: `pnpm changeset`, pick the members, pick the bump (patch, minor, major) and write one user-facing line. Commit the generated file under `.changeset/`.
  </Step>
  <Step title="Let CI open the version pull request">
    After a push to `main` the release job runs `pnpm changeset:version` (which also refreshes the lockfile) and opens or updates one pull request titled `chore(release): version packages`.
  </Step>
  <Step title="Review it">
    Read the `CHANGELOG.md` diffs and the version bumps. Check the bump matches the change. The release job pushes and opens it as `stackra-bot` (a GitHub App token from `actions/create-github-app-token`, repo secrets `STACKRA_BOT_APP_ID` and `STACKRA_BOT_PRIVATE_KEY`), so the Quality Gate runs on it without a close and reopen.
  </Step>
  <Step title="Merge it">
    The merge to `main` is the release. The job tags each versioned member and creates the release notes.
  </Step>
  <Step title="Verify">
    `git ls-remote --tags origin` shows the new tags on the merge commit, and each member's `CHANGELOG.md` contains the entry.
  </Step>
</Steps>

## Before the first release (once, by a human)

- Branch protection on `main` requires the `verify` check ([CI](/runbooks/ci)).
- A tag ruleset on the version tag pattern blocks deletion and non-fast-forward updates for everyone. Version tags are immutable.
- The host setting that lets the workflow token create pull requests is on.
- The release job runs in a protected environment restricted to `main`, so a branch that edits the workflow cannot obtain a credential.

## If we ever publish

Publishing is a separate decision, and an ADR must record it. The procedure it must follow:

- **No long-lived publish token.** The registry trusts the workflow's OIDC identity (trusted publishing), and the package setting disallows tokens for publishing.
- Build the tarball and an SBOM with no privileges, then sign both keylessly in the one job that holds `id-token: write`.
- Publish is idempotent: the same bytes already on the registry are not published again, so re-running failed jobs is safe; different bytes fail the job.
- Read access for consumers is a read-only token held in Infisical `/ci` and fetched through OIDC ([Secrets](/runbooks/secrets)).
- A prerelease publishes under a `next` dist-tag and moves no floating tag.

## When something fails

Re-run only the failed jobs of the same run unless a row says otherwise.

| Failed step | State | Do |
| --- | --- | --- |
| Version pull request not opened | Nothing released | Check the host setting for pull requests from workflows, then push any commit to `main` or re-run |
| `verify` on the version pull request | Nothing released | Close and reopen the pull request; if it is red, fix on `main` and let the job update it |
| Tagging | Merged, not tagged | Re-run the failed job; it tags over an existing release safely |
| Wrong bump merged | Tagged | Roll forward: add a changeset and release the correction |

## Revert

- **Before merging:** close the version pull request. The next push recreates it from the remaining changesets.
- **After merging:** roll forward. For a bad release that was published, deprecate it (`npm deprecate <pkg>@<bad> "<reason; use <good>>"`), move the `latest` dist-tag back to the last good version with `npm dist-tag add` if needed, and ship a fixed patch. Prefer deprecate over unpublish.
- **A bad release record on the host:** mark it a prerelease or delete the release page; leave the tag.
- **The workflow itself:** revert the workflow file on `main`; nothing else depends on it.
