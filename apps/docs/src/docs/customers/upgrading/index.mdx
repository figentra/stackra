Before 1.0.0, a minor release (`0.y.0`) may change what your app must do. Each one that does has an
upgrade note here: what changes, the pins, the steps, how to verify and how to roll back. A patch
(`0.y.z`) changes nothing you must act on, unless its line's note names it.

## The notes

| Move                      | Note                                         | Work for an app                                                                                         |
| ------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 0.29.x → 0.30.x           | [Upgrade to 0.30](/customers/upgrading/0-30) | the most: area routes, tenant-owned tables with migrations that refuse, custom drivers, Encore app root |
| 0.30.x → 0.31.x           | [Upgrade to 0.31](/customers/upgrading/0-31) | an automation quota driver; renamed tables for plural model names                                       |
| 0.31.x → 0.32.x           | [Upgrade to 0.32](/customers/upgrading/0-32) | only a service that injects `Signer`                                                                    |
| 0.32.x → 0.33.1           | [Upgrade to 0.33](/customers/upgrading/0-33) | `stackra encore:prepare` and `stackra gen` in each service                                              |
| 0.33.1 → 0.34.0 (pending) | [Upgrade to 0.34](/customers/upgrading/0-34) | a Worker deploy's smoke and version header; a custom `IdempotencyStore`; a PWA member's peer            |

A release marked pending is not published yet: its note is written ahead of it, from the changesets
waiting on `main`, and is final when the release ships.

To cross several releases, apply the notes in order, one release line at a time, and verify after
each. Breaks released before 0.30.0 have no note; read the packages' `CHANGELOG.md` for those.

## How you pin

Every `@stackra/*` package releases at one version. Pin them all, exactly, in the `stackra` catalog
of `pnpm-workspace.yaml`, and `@stackra-pro/*` at the same version. Never mix two Stackra versions in
one repository.

## How the notes stay complete

A changeset or changelog entry that marks a break (the word "breaking", `Upgrade:`, `Bump step`,
`After upgrading`, `Before taking this version` and the like) makes its release a breaking one.
`stackra validate --repository` refuses a breaking release from 0.30.0 on, released or still
pending, until its line's note exists with the five sections, and until the note names a breaking
patch by its version. The pull request that adds the break and the version pull request are both
held, so a breaking release cannot ship without its note.
