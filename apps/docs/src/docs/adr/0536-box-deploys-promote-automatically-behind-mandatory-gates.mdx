## Context

figentra's GitHub Actions is billing-locked, so the CI deploy workflows behind the `production` Environment approval of
[0468](/adr/0468-agents-deploy-dev-and-staging-production-waits-on-one-environment-approval) cannot run. The owner chose
on 2026-11-25 a recorded exception: box 1 deploys Encore staging and Stackra's Workers (STA-2783). The owner then
separated the accounts (STA-2784): the shared Figentra services (the registry, the build cache) stay in the main
Cloudflare account and deploy through CI only, never with a box token; Stackra's own Workers move to a Stackra account
on Stackra's own domain. Asked how production promotion works for the box deploys, the owner answered **"All
automatic"**. With no person clicking, the gates carry the whole weight, so they are part of this decision.

## Decision

1. Box deploys of Stackra's own Workers in the Stackra account (`57227d408957e241465c38ebd9c3959a`: docs and edge;
   the landing is experience documents rendered by the OS landing shell, not a Worker here) promote to production
   automatically when every gate below passes. This replaces 0468 decision 2's per-deploy Environment approval **for
   those box deploys only**. The shared services in the main account (the registry, the build cache, static), Encore
   production and package releases deploy through CI with 0468 unchanged; the box holds no token for the main account.
2. Every gate is mandatory; none has a setting that skips it:
   1. **Main and verify.** Only a commit of origin/main, with a green `stackra/verify` check run from the
      stackra-verify App at that exact SHA. Until stackra/verify is live, a box-green record at that SHA stands in,
      only while `STACKRA_DEPLOY_ACCEPT_BOX_GREEN` is on, and only when written by its owner (never the deploy user).
   2. **No traffic before a proven smoke.** `wrangler versions upload`, the version joins the deployment at 0%, and the
      smoke runs on it through the version override: runway.yaml's uptime and member checks plus the Worker's own
      suite. Every smoke step proves which version answered (edge's `x-stackra-version`, docs' `/-/version`), so an
      override that does not reach the new version fails instead of passing on the old one.
   3. **Additive D1 only.** Pending migrations run before any version ships, and only when every statement is `CREATE
TABLE`, `CREATE INDEX`, `ALTER TABLE … ADD COLUMN` or `INSERT`; anything else stops for the owner, and so does an
      insert into a table that grants rights (the registry's publishers, scopes, tokens, licences and grants).
   4. **Gradual promotion with automatic rollback.** 10%, 50%, then 100%, as CI's rollout, held, with the whole smoke
      again at each step and live at the end; any failure puts the previous version back at 100%.
   5. **A bounded token.** The Cloudflare API token is the owner's, for the Stackra account only, restricted to box 1's
      egress IP, with an expiry, kept in its own scope `ci/deploy/box1-stackra` and read only by the Workers path's
      deploy user. Its blast radius is Stackra's own Workers. Secret values are fetched at run time into memory from
      Infisical by that user's own machine identity (`STACKRA_DEPLOY_SECRETS=infisical`), or read from 0400 files
      (`files`, the fallback); which one runs is the owner's choice, recorded on STA-2783 before the switch goes on.
   6. **One credential per user.** The Workers path runs wrangler and runway from a tree the build user wrote, so it
      holds only the Cloudflare token and refuses to run while it can reach the Encore credential's folder. Encore's
      Deployer role is not environment-scoped, so the Encore path and its audit run as their own user, which runs no
      tree code, cannot act as the build user and holds no Workers setting.
   7. **Pinned service code.** The service never pulls main: `service update` moves each service clone only to a main
      SHA that passed gate 1, as a fast-forward, and every deploy refuses a clone that is not at its pinned commit or
      whose code another user could change. Owner-only review of the service's own scripts (CODEOWNERS, through the
      owner-only list) is on the go-live list.
   8. **No retry loop.** The timer never repeats an SHA whose last attempt failed, needed the owner or was refused; a
      new head of main or a run by hand clears the hold.
   9. **The ledger.** Every attempt is one JSON line: SHA, trigger, verify evidence, migrations, old and new version ids,
      every step and smoke result with its version proof, rollback, and times. No secret reaches it.
3. Everything is built OFF. The path switches on only after the strict reads, with the owner's token in place and the
   go-live list of the runbook (tools/scripts/stackra-deploy.mjs) verified on the first watched deploy of each Worker
   and recorded in the ledger by Lukas.
4. `approve` stays in code (per Worker, tested): it stops after the 0% smoke until the approver user's file names the
   SHA and the version. Choosing it for a Worker is a setting change, not a new decision.

## Consequences

A Stackra Worker change on main reaches production without a person in the loop, so a gap in a smoke is a production
gap: adding a route or a failure mode to docs or edge means adding it to its suite in `worker-smoke.mjs`. A destructive
or trust-changing migration always waits for the owner. The shared services keep the owner's approval through CI, and
CI can run the same smoke suites and D1 gate (STA-2786 wires the registry's version proof). When Actions returns, the
box path is switched off and CI resumes under 0468.

## Enforcement

`tools/scripts/stackra-deploy.mjs` with `tools/scripts/worker-smoke.mjs` and `tools/scripts/d1-migration-gate.mjs`;
their tests in `tools/scripts/__tests__/` cover each gate: non-main and unverified SHAs refused, the shared services and
the main account refused, destructive and trust-changing migrations stopped, the false pass failing the version proof,
the smoke failure and its rollback at 0% and at 10%, the 10/50/100 steps, approve mode, the ledger, no secret in argv
or output, Encore production refused before any API call, the credential split, the service pin, the held SHA and
secrets fetched from Infisical.
