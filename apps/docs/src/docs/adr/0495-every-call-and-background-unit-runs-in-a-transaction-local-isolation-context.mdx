## Context

Every tenant-owned table carries the forced equality policy of 0239 on `tenant_id = current_setting('app.tenant_id')`.
Until now only `TenantIsolationService.withTenant` set that setting, and only a few drivers called it. The action
pipeline's unit of work, its queries, the queue worker, the outbox relay and inbox, the workflow journal and the
scheduler set at most the `app.scope_*` settings of `Database.withScope`. So a tenant-scoped query outside those
drivers was refused (isolation failed closed, nothing leaked), and services worked around it by writing `set_config`
themselves, where a session-level setting would survive into another tenant's transaction on a pooled connection.

## Decision

1. **One isolation context per unit of work.** `@stackra/actions` declares a `CallIsolation` port:
   `run(actor, scope, work, { readOnly })`. The pipeline runs every call inside it, actions in their unit of work and
   queries in a read-only transaction, after the tenancy check and before permission. `@stackra/tenancy` binds the
   driver, which composes `Database.withScope` and `TenantIsolationService.withTenant` in one transaction. With no
   driver bound, a call to a model with a tenant policy fails closed, as before.
2. **Background units use the stored actor.** The queue worker, outbox relay and inbox, workflow runner and
   scheduler run each job, delivery, step or run through the same port, with the actor and scope stored when the
   work was enqueued. A unit stored without an actor runs as a platform call (`app.tenant_id` = `''`), which matches
   no tenant row. The event bus is trusted for actor identity (ADR 0142), but not blindly: where `@stackra/tenancy`
   binds `ScopeOwnership`, the inbox downgrades an envelope whose actor's tenant does not own the envelope's scope to
   the platform actor and logs it by event id and type only, and an automation refuses a principal from another scope.
   The relay and the inbox give each unit a transaction of its own, and the isolation driver refuses
   (`tenant_switch_refused`) to replace the tenant of a transaction that already runs for another, so a transaction
   never carries one actor's tenant into another's unit.
   The scheduler only dispatches onto the queue. A job it pushes in a scope carries the scheduler's system actor
   acting in that scope as its `origin`, so the queue worker runs it through the port bound to that scope; a schedule
   is created in the scope its work belongs to (a tenant's own scope), and a scope that is not a tenant's matches no
   tenant row. A platform run carries no actor scope. A platform schedule that works across tenants lists them
   (`CronScopes`), so each tenant's run is its own job in its own isolation context, never one cross-tenant
   transaction.
3. **Transaction-local only.** Every `app.*` setting is written with `select set_config(name, value, true)` inside the
   unit's transaction, and nowhere else. `pnpm validate` (`tools/scripts/session-settings.mjs`) enforces two rules over
   `.ts`, `.tsx`, `.js`, `.cjs`, `.mjs`, `.mts`, `.cts` and `.sql` files under `packages/`, `services/`, `apps/` and
   `workers/`. (a) The session form is refused everywhere, with no exemption of any kind: `set_config(` with a third
   argument other than the literal `true`, `SET app.`, `SET LOCAL app.` and `SET SESSION app.` (also with `"app"`
   quoted), and a startup option `-c app.`. (b) Any `set_config(` of an `app.*` name, or of a name that is not a literal,
   is refused whatever its third argument, outside an explicit allow list: the isolation driver,
   `TenantIsolationService`, the database drivers' `withScope` and `onReplica` (and the memory twin), the iam policy
   snapshot store (it sets its own tenant in its own transaction), `src/testing/` helpers and test files.
4. **RDS Proxy (0473).** AWS documents that for PostgreSQL a `SET` statement, `SET LOCAL` included, pins the client
   connection for the rest of the session, as does using `set_config` to assign default values. It also documents
   that function calls are not inspected for session state. So `select set_config(name, value, true)` is the form
   to use. Its state ends with the transaction, so correctness never depends on pinning. A session-level
   `set_config(..., false)` would not be detected and would leak to the next client of the backend, which is why
   decision 3 forbids it. The pinning behaviour is confirmed on the first real proxy by the CloudWatch metric
   `DatabaseConnectionsCurrentlySessionPinned` under load (planned check, below). Until then this paragraph is from
   the AWS documentation (Avoiding pinning an RDS Proxy, 2026-10-31), not a measurement.
5. **Testing.** `@stackra/tenancy/testing` ships `asTenant(tenantId, work)`, which runs `work` through the real
   `CallIsolation` driver on the current database. `runAsTenant` stays the database-free helper for filling
   `BelongsToTenant`, and its docblock points to `asTenant` for isolation. Isolation is proven on real Postgres
   (`usePostgres`) under a role without `BYPASSRLS`.

6. **A `requiresNew` path keeps its tenant.** A `requiresNew` transaction runs on another connection and inherits
   no `app.*` setting, so one that touches a tenant-policy table must re-apply the tenant transaction-locally in its
   own transaction. The paths that exist today, classified:

   | Path                            | Touches a tenant-policy table? | Classification                              |
   | ------------------------------- | ------------------------------ | ------------------------------------------- |
   | rate-limit buckets              | no (no RLS)                    | needs nothing                               |
   | workflow journal (`workflow.*`) | no (no RLS)                    | needs nothing; steps re-enter the isolation |
   | `webhook_deliveries`            | no (no RLS)                    | needs nothing                               |
   | access-log sink                 | yes                            | sets its tenant transaction-locally, itself |
   | iam policy snapshot store       | yes                            | sets its tenant transaction-locally, itself |

   A new `requiresNew` path states its row in this table in the change that adds it.

## Consequences

- Services stop writing `set_config`; a hand-rolled one fails `pnpm validate`.
- Every query now runs in a short read-only transaction, which costs one round trip per call.
- Every call and unit holds a connection for the length of its transaction, so pools are sized for isolation: STA-1716.
- A queued unit must carry its actor; producers that enqueue without one get platform isolation, so their tenant
  rows are invisible to the job until they pass the actor.

## Enforcement

- `tools/scripts/session-settings.mjs` repo check (STA-1699): the two rules of decision 3.
- `@stackra/tenancy` real-Postgres isolation tests (STA-1699): tenant A sees only its rows through the pipeline, a
  platform call sees none, settings do not survive the transaction.
- planned — RDS Proxy pinning under load measured by `DatabaseConnectionsCurrentlySessionPinned` on the first
  deployed proxy (infra follow-up of STA-1699).

## Note 2026-11-01: idempotency keys join the call's transaction (decision 6)

The Postgres idempotency store no longer uses `requiresNew`, so it leaves the table of decision 6. When a call joined
an outer transaction (a listener in the inbox's unit, a workflow step), its `complete` committed on its own before
the outer transaction did; if that commit then failed, the retry replayed a success that never committed. Every claim,
completion and release now joins the running transaction (a savepoint of it), or opens its own when none runs: a key
completed inside a failed outer commit is gone and the retry runs again. A concurrent claim of the same key waits for
the transaction that inserted it. The Valkey store cannot join a transaction, so a deployment whose calls join outer
transactions uses the Postgres store. Test: `postgres-idempotency-store.driver.int.test.ts` forces the outer commit
to fail with a deferred constraint and claims the key again.
