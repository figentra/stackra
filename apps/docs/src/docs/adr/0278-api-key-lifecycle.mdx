## Context

[0207](/adr/0207-authentication-assurance-and-machine-identities) decision 2 sends every machine identity through ZITADEL, and
[0087](/adr/0087-identity-and-iam-are-driver-packages) decision 5 said tokens are shown once, stored hashed, scoped and revocable. Neither says
who issues an API key, how it is rotated, recognised when leaked, or seen in use. The owner's answers of 2026-10-21 (screenshot gap review,
item 9, and the issuer decision that followed the PR review) set the issuer and the whole lifecycle.

## Decision

1. **Stackra issues API keys.** `@figentra/service-identity` issues API keys for programmatic access by developers and integrations.
2. **Each key maps to a ZITADEL machine identity.** The gateway ([0237](/adr/0237-generated-api-gateway-in-four-layers)) validates the key and
   maps it to a ZITADEL machine identity. The machine identity is the principal; its permissions are its IAM grants
   ([0208](/adr/0208-iam-model-scope-tree-roles-conditions-deny-delegation-and-permission-names)), decided by the policy decision point
   ([0209](/adr/0209-iam-enforcement-pipeline-gate-sql-predicate-embedded-pdp-and-service-calls)). ZITADEL stays the issuer for sign-in, OIDC
   and machine-to-machine JWTs.
3. **Shown once, stored hashed.** The secret is shown once at creation and stored only as a hash.
4. **Prefix registered with GitHub secret scanning.** Every key starts with a recognisable prefix registered with GitHub secret scanning.
5. **Checksum suffix.** The key ends with a CRC32 checksum (as GitHub's suffix does). It catches typos and malformed keys, so a scanner and the
   gateway reject them without a database lookup. It does not prove a key is authentic; only the hash lookup does.
6. **Tenant tokens are bound to one tenant.** A tenant service token works only in the tenant it was issued for.
7. **Scopes.** A key carries scopes, and the gateway checks each call against them.
8. **Last used.** The key list shows each key's last-used time and IP address.
9. **Rotation with overlap.** Rotating a key issues a new one; old and new both work during an overlap window, then the old one stops.
10. **Expiry.** A key has an expiry.
11. **Revoke, and auto-revoke on a scanning report.** A key can be revoked at once. A key reported by GitHub secret scanning is revoked
    automatically and its owner is notified.
12. **Example usage.** Each key's page shows an example usage snippet for that key's scopes.

## Consequences

- A leaked key is revoked when GitHub reports it, not found by the customer weeks later.
- The key is a credential, not a second permission model: the machine identity is the principal, its permissions are its IAM grants (0208),
  and the policy decision point (0209) decides each call.
- service-identity owns key issuance, hashing, the checksum format and the secret-scanning endpoint.
- Rotation does not need a deploy at the exact moment the old key dies, because of the overlap window.
- Last-used data is written on calls, so its write path must stay cheap (sampled or batched).

## Enforcement

planned — a storage test asserts no plaintext key is persisted; a gateway test rejects a bad checksum before lookup, refuses a tenant token in
another tenant, accepts both keys inside the overlap window and only the new one after it, and refuses expired and revoked keys; a test of the
secret-scanning endpoint asserts a reported key is revoked.

## Open details

The owner did not give these; the conservative default below applies until an ADR changes it.

1. **Prefix.** `<product>_<env>_` followed by the secret and the checksum, for example `stk_live_` and `stk_test_`; the exact strings are
   fixed when the GitHub secret-scanning partnership is filed.
2. **Checksum.** CRC32 of the secret, base62-encoded, as the last 6 characters.
3. **Overlap window.** 24 hours by default, settable up to 7 days.
4. **Expiry.** Required at creation, 90 days by default, at most 1 year.
5. **Last-used IP retention.** Follows the access-log retention of
   [0212](/adr/0212-audit-evidence-access-logs-hash-chain-and-retention).

## Amendment, 2026-11-09: a key's mode and version pin (STA-2646)

A key is test or live, chosen when it is issued and written into its text after the kind's prefix:
`stackra_sk_test_…`, `stackra_pk_live_…` (open detail 1's `<env>` segment). The body is base-62, so the segment
cannot be read as part of it. A mode is never assumed: a key with no segment, or whose record has no mode, is refused
(CHECKOUT's review, leader 2026-11-09; no live keys existed), so live comes only from a key issued live. The checksum covers the segment, so
it cannot be edited, and the verifier refuses a key whose text names another mode than its stored record
(`ApiKeyRecord.mode`). `VerifiedApiKey.mode` carries it to the caller.

A key also records a version pin, the API's `Stackra-Version` date when it was issued (`ApiKeyRecord.versionPin`), which
its calls default to; an explicit `Stackra-Version` header still wins. The gateway path that turns a verified key into a
call (the actor, `CallOptions.sandbox` for a test key, the pin for versioning) is the next part of STA-2646 and amends
this ADR again when it lands.

## Amendment, 2026-11-09: the gateway reads keys from identity, cached (STA-2646 B2)

A service that answers API-key calls reads a presented key's record from the identity service by its SHA-256
(`principals.api_key.verify@1`) through `ServiceApiKeyStoreDriver`, as its own service. It keeps a verified record for
`IdentityConfig.apiKeyCacheSeconds` (30 by default, at most 300), so every call is not a round trip; a key identity does
not know is never cached. A revoke takes effect at once when identity's `principals.api_key.revoked.v1` reaches the
service (`evictPrincipal`); **the worst case is the cache window**, 30 seconds by default, when the event has not
arrived. The listener that calls `evictPrincipal` is bound with the gateway path (B3).

## Amendment, 2026-11-09: a tenant's deny rules bind an API key (STA-2646)

An `api_client` call's grants are its key's scopes, so it skips the grant search of the decision point, but its
tenant's deny rules still bind it: after the scopes pass, `PolicyDecisionPointService.denied` checks the deny rules of
the key principal's own snapshot against the operation's permission and every scope the key had to cover, in `require`
and against the record in `authorize`. A breakable deny counts too, since a key has no break-glass. A key whose
principal has no published snapshot (version 0) is refused: fail closed. The access service publishes each API-key
principal's snapshot (its tenant's deny rules, no grants); the gateway path (B3) goes live only once it does.
