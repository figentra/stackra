## Context

[0040](/adr/0040-ddd-feature-modules-in-services) put Encore primitives at each service's root, and
[0041](/adr/0041-decorated-controllers-and-build-time-generator) had `stackra gen` write static Encore declarations into
`services/<svc>/__generated__/`. That ties every service's source tree to Encore and puts generated code in review diffs. The
owner proposed the reverse: services are plain TypeScript, and the whole Encore application is a build output. This makes
Encore one target among possible others.

## Decision

1. **Services are plain TypeScript with no `encore.*` files** and no `__generated__/` folder.
2. **`stackra gen` emits a complete Encore application into a gitignored `.stackra/encore/`**: `encore.app`, one
   `encore.service.ts` per service, and generated `api()`, `Topic`, `Subscription` and `CronJob` adapters. The adapters call the
   built service packages through the container.
3. **Only `app-manifest.json` is committed.** It is the reviewable record of what gen produced: endpoints, topics,
   subscriptions and crons.
4. **`stackra gen --check` runs in CI** and fails when `app-manifest.json` is stale.
5. **`stackra dev` is `gen --watch` plus `encore run`. `stackra build` is `gen` plus `encore build docker`.** CI deploys from
   the generated application.
6. **Encore is a swappable target.** Nothing outside `.stackra/` and the generator's Encore emitter knows about Encore.
7. **Authoring is actions** ([0098](/adr/0098-actions-are-the-unit)): `@Action` and `@Query` exposed with `@AsEndpoint` and
   the other adapters, plus `@OnEvent` and `@Cron`, discovered per [0090](/adr/0090-codegen-discovery-by-root-module).
   `@Controller` with `@Get`, `@Post` and the rest remains only for raw endpoints. HTTP conventions are unchanged, generated
   files are never edited by hand, and `@Crud` is [0105](/adr/0105-crud-generates-service-methods).
8. **The dev loop imports service source (mode B).** `stackra gen --watch --src` makes `.stackra/encore/` import each
   service's source through TypeScript `paths`, and the generated `tsconfig.json` sets `experimentalDecorators` and
   `useDefineForClassFields: false`. Production and CI keep importing built `dist`. gen bundles service source with esbuild into
   a cache folder to read metadata, writes a file only when its content changes, and writes a `<svc>/dist-stamp.ts` hash file
   inside the app root on every rebuild, because Encore ignores changes outside its app root. An edit reaches a response in
   about 0.6 s.
9. **The spike passed** all six cases: `encore run` with typed, raw, cookie and bearer endpoints; Pub/Sub and cron; `encore test`; static analysis of types in `.stackra/` with handlers in external packages; `encore build docker` on arm64 and amd64; `encore gen client`. The constraints it found are listed under Consequences.

## Consequences

- Reviewers see `app-manifest.json` changes instead of generated code.
- Encore errors point into generated code under `.stackra/`, so the generator must emit source comments that point back to the authored class.
- The DDD module layout of 0040 stands, minus its decisions 3 and 4, which this ADR replaces. Encore primitives reach
  modules as container tokens provided by the generated app, which amends [0042](/adr/0042-di-first-with-one-container-per-service) decision 5.
- Constraints the spike found, which the generator and authors must respect:
  - Topics are referenced directly: the generator emits one `switch` branch per topic.
  - Classes are matched by export identity, not `class.name`, so every provider with handlers is exported from its package index.
  - Handlers carry explicit parameter and return type annotations.
  - A typed mapping from domain errors to `APIError` is required; a plain `Error` surfaces as a 500.
  - The pipeline order is `pnpm build`, then `stackra gen`, then `pnpm install`, then `encore`.
  - Each environment needs an Encore infra config once Pub/Sub exists.
  - Importing built `dist`, the generated app does not need `experimentalDecorators`; importing source (decision 8) it does.
  - `encore build docker` hangs inside git worktrees (the CLI loops on the `.git` file), so Docker builds run in CI or in a normal clone.
  - `encore run` does not run crons locally.
  - Encore watches only its app root, so source edits reach it only through the stamp file of decision 8.

## Enforcement

Planned: `stackra gen --check` in CI and in `pnpm verify`. A validator check that no `encore.*` file or `__generated__/`
folder exists under `services/`, and that `.stackra/` is gitignored. Nothing checks this today.

## Amendment 2026-11-09: the Encore app root is the member root (single-service apps)

Decision 2 put `encore.app` inside `.stackra/encore/`. On the testbed (tamo, Encore 1.58.8) that
root could not resolve the member's `#` imports or its `node_modules` packages. With the three
conditions below, `encore check` built the application graph and topology and `encore build docker`
produced an image.

1. **The app root is the service member's root.** Gen writes `encore.app`, `{ "id": <runway
providers.encore.app>, "lang": "typescript" }`, at `services/<name>/encore.app`. It is a
   generated file and is gitignored (`services/*/encore.app`; `stackra validate --repository`
   asks a repository with services to ignore it). Gen no longer writes `.stackra/encore/encore.app`
   or `.stackra/encore/package.json`. An `encore.app` at the repository root is still refused
   (`encore_app_stray`).
2. **The generated services stay in `.stackra/encore/<svc>/`.** Encore discovers them there. A
   service's migrations path stays `{ path: "./migrations" }`, relative to its folder under
   `.stackra/encore`.
3. **`encore.dev` is a literal exact version equal to the default catalog's.** Encore's
   `package_mgmt` step (`update_package_json`) rewrites any `encore.dev` spec that is not the exact
   version (or `^`, `=` or `~` plus it) to `^<version>`. `catalog:` is rewritten too, and the
   rewrite breaks pnpm's frozen install. This is the one literal the versions rule allows, in a
   `tier:service` member's `dependencies`; `stackra validate --repository` refuses a service whose
   pin differs from the catalog's. A catalog bump of `encore.dev` is a bump of every service's
   literal in the same change (`stackra encore:prepare`); no Renovate configuration exists in the
   repository, so nothing automates it yet.
4. **The service's tsconfig carries `paths` mirroring its package.json `imports`, and no
   `baseUrl`.** Encore's parser ignores package.json `imports`, and reads `compilerOptions.paths`
   only when written directly in the app root's own tsconfig.json, not through `extends` and not
   with `${configDir}`. Each key and its target array equal the `imports` entry (a string target
   is a one-element array), and the targets resolve from the tsconfig's folder. The tsconfig still
   extends its one `@stackra/typescript-config` preset. `stackra validate --repository` refuses a
   service whose `paths` differ from its `imports`, or that sets `baseUrl`: TypeScript 7 removed
   `baseUrl` (TS5102). Corrected 2026-11-09: the first version of this rule required `baseUrl`
   ".", which TypeScript 7 refuses (INVOICING). Corrected 2026-11-10 (STA-2681): each key carries
   its `imports` entry's first target only, because Encore honours only a key's first `./` target
   (the OS lane's identity app); tsc still probes extensions and `index` files through it. And
   since tsc applies `paths` to every package a service compiles (notify#71), a service's
   typecheck reads gen's `.stackra/tsconfig.typecheck.json`, its tsconfig without `paths`, so each
   package's `#` imports resolve through its own `imports`.
5. **`stackra encore:prepare`** rewrites a service's tsconfig `paths` from its `imports` and pins
   `encore.dev` to the catalog version.
6. **The Encore Cloud Root Directory is the member folder**, `services/<name>`.

Open, pending an owner decision: a product with several service members sharing one Encore app. One
app root cannot be several member roots; the options are a per-product staging build or unique
aliases. This amendment covers single-service apps only.

Upstream: the Encore issue on `imports` and `paths` resolution is being filed separately (link to
follow).

## Amendment 2026-11-10: the generated services sit outside the dot folder

Encore skips dot directories when it discovers services, so the services in `.stackra/encore/<svc>/`
were never found: `encore build docker` of Pay produced an app with only the api-gateway (RUNWAY's
spike, pay#217). Run 7 of that spike copied only the service folder to a plain folder: Encore
discovered and parsed the service, and followed its imports into `.stackra/entry` and
`.stackra/gen` without error. Dot folders are skipped only in discovery, not when resolving imports.

1. **Gen writes a service's Encore files into `stackra-encore/<svc>/` at the member root**, beside
   `encore.app`, replacing amendment 2026-11-09's rule 2. `@stackra/gen` names the folder
   (`ENCORE_SERVICES_DIR`). It is generated output: gitignored (`**/stackra-encore/*`, gen's golden
   trees excepted), owned by gen, and nobody writes a file there by hand. The member's TypeScript
   program does not include it.
2. **The runtime entry and gen output stay in `.stackra/`.** A generated Encore file imports the
   server app from `../../.stackra/entry/server`, and a sibling service's topics from
   `../../../<folder>/stackra-encore/<svc>/events`.
3. **`stackra dev` runs `encore run` in the member root**, and refuses a service whose
   `stackra-encore/` gen has not written. Runway's Encore Cloud deploy tree carries each member's
   `stackra-encore/` with its `.stackra/` and rewrites the `#` imports in both.
4. A consumer repository adds `stackra-encore/` to its `.gitignore`.
