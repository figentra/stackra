title: "0406 — Step-up is an action option checked after the permission, and the call carries its assurance"
description: "Proposed · 2026-10-26"
---

<Note>
  Proposed (STA-814). It applies [0207](/adr/0207-authentication-assurance-and-machine-identities)
  decision 1 to the action pipeline. Linear STA-814.
</Note>

## Context

ADR 0207 requires a recent strong authentication for L3 and L4 actions, and `@stackra/identity` already maps a token's
`amr` to an assurance level and checks its age (`requireAssurance`). Nothing carried the token's `amr` and `auth_time`
into an action call, and no action could say it needs a step-up, so each handler would have checked it by hand.

## Decision

1. **The call carries its assurance.** `CallOptions.assurance` (`amr`, `authTime`, `level`) is filled by the transport
   from the verified token, never from input; the pipeline hands it to `ctx.assurance`. It is absent without an
   interactive session (a job, an API key).
2. **`Action({ stepUp: AssuranceLevel.Aal2 })`** names the level an action needs. `AssuranceLevel` in
   `@stackra/actions/contracts` has the same codes as identity's, because actions depends on neither identity nor iam.
3. **A `StepUpCheck` port decides, right after the permission.** The bound driver wraps `requireAssurance`, so the
   window is `IdentityConfig.stepUpMaxAgeMinutes` (configuration). A refusal is `step_up_required`.
4. **It fails closed.** An action that declares `stepUp` with no `StepUpCheck` bound is an error, like a missing
   `AccessControl`. An action that declares none never asks.

## Consequences

- The identity service or app binds a `StepUpCheck` driver over `requireAssurance`; every transport fills
  `CallOptions.assurance`.
- A handler that needs the facts (an audit field, a risk score) reads `ctx.assurance`.

## Amendment 2026-11-03 (STA-340): step-up asks a user caller only

**Context.** Three actions that both users and services call (`identity.operator.bootstrap`,
`identity.session.end_user`, `privacy.hold.release`) are L3 or L4 and declared no `stepUp`, because decision 3 applied
it to every caller and a service or job call carries no assurance (decision 1), so it could only be refused.

**Decision.** The owner chose option A. Decision 3 now reads: when an action declares `stepUp`, the pipeline asks
`StepUpCheck` only when the caller's actor kind is `ActorKind.User`. A service, job, system or agent caller is not
asked; an agent's approvals stay ADR 0360's, and an approved call still stands on the assurance its binding recorded
(ADR 0509). Decision 4 is unchanged for a user caller: with no `StepUpCheck` bound the call fails closed. Gen refuses an
L3 or L4 action whose actors include `User` and that declares no `stepUp` (`step_up_missing`), and the three actions
declare `stepUp: AssuranceLevel.Aal2`.

## Amendment 2026-11-07 (STA-340): the first-factor enrolment exemption

**Context.** STA-2096 raised `identity.passkey.confirm` to L4, so this ADR asks AAL2 of the user who confirms a
passkey. A user enrolling their first strong factor has nothing to step up with.

**Decision.** One action may declare `stepUp: { exempt: "first-factor-enrolment" }`: those listed in gen's
`FIRST_FACTOR_ENROLMENT_ACTIONS`, today `identity.passkey.confirm` alone; gen refuses it anywhere else
(`step_up_exemption_unlisted`), and adding an entry is a reviewed gen change. The pipeline asks no `StepUpCheck` for
it. The action decides instead: a user whose enrolled methods reach AAL2 must have stepped up to AAL2, and a user with
none may enrol the first from a sign-in within `IdentityConfig.stepUpMaxAgeMinutes`; it audits every enrolment with
`firstFactor`.
