## Context

[0009](/adr/0009-secrets-two-mechanisms) (Accepted) kept production secrets in the runtime's store, set by a human, with no sync from Infisical. The owner
overrode that on 2026-10-20 (DP19 option b): Infisical is the source, and runway syncs it into Encore, Cloudflare Workers and EAS on deploy (mem L448).
The always-on rule still told agents that sync was not adopted, so the rule was wrong for every session until this change.

## Decision

1. **Source (DP19 b).** Infisical is the source of production secrets. Runway syncs them into Encore, Cloudflare Workers and EAS on deploy.
2. **Key homes.** The three key homes of [0107](/adr/0107-connections-store-and-three-key-homes) stand.
3. **Secret references.** The `secret('Name')` references of [0146](/adr/0146-package-configuration-typescript-layers-and-secret-references) stand. Gen declares them as Encore secrets.
4. **Developer machines (DC4).** Dev boxes use an instance role, an Infisical machine identity and Agent Vault. Nothing is stored on disk.
5. **CI.** CI reads Infisical through OIDC (ADR 0167, CI12).
6. **Carried forward from 0009.** Secret names are in git and values are not. There is no `.env` file. The forbidden commands stay forbidden. Verify needs zero secrets.
7. **Secret-manager agent (owner 2026-10-20 night; amends the "values are set by a human" invariant of 0009 and 0173).** A dedicated `secret-manager` agent may write secret values into Infisical for every environment without reading them. One audited script, `pnpm secrets:import`, streams a file from a single inbox folder outside the repositories into Infisical with output suppressed, verifies the write by hash, deletes the source file and logs only the names. Hooks allow that script for that agent alone. A production write is prepared with a dry run, and it is fired only after the owner answers yes. Runtime-store secrets for Encore follow the same flow once a tool exists.

## Consequences

- A rotation in Infisical reaches every target on the next deploy, so there is one rotation point.
- The always-on rule `secrets.md` changes with this ADR: "Infisical Secret Sync is not adopted" is replaced by decision 1.

## Enforcement

planned — the runway sync step is checked by the deploy job; `guard-bash` keeps the deploy sync command on its allow-list (`.agents/hooks/guard-bash.mjs`). The gitleaks
pre-commit and CI scan (ADR 0009) carry forward.

## Alternatives

- Set production secrets by hand in each runtime store: superseded by DP19; it cannot be audited.
- Infisical Secret Sync not adopted (0009 D8): superseded by DP19.

## Amendment 2026-11-04: one strict system for environment variables (STA-2104)

**Context.** Environment variables were managed by hand: code read `process.env.X` anywhere, a name could be used and
never declared, a value could sit in Infisical with no reader, and nothing told a deploy that a value was missing or
was a test key in production until the runtime failed. The owner asked on 2026-11-04 for one strict system: declare
once in code, Infisical holds every value, and tools check and sync everything. The leader agreed the design below
with the owner the same day. It reads with the Infisical plan of 2026-11-04 (stackra-notes
`plans/infisical-2026-11-04/PLAN.md`), which replaces the project layout of
[0512](/adr/0512-one-infisical-layout-projects-by-reader-agents-and-product-runtimes) for runtimes.

**Decision.**

1. **Declare once, in code.**
   - Code reads the environment only through a configuration class: `Config({ schema, env: { field: "ENV_NAME" } })`
     for a plain or public value, and `@Secret("NAME")` on a schema field for a secret
     ([0146](/adr/0146-package-configuration-typescript-layers-and-secret-references) as amended).
   - The house rule `stackra/no-raw-env` (`@stackra/coding-standard`, on in `@stackra/oxlint-config`'s base) reports a
     named read of `process.env` or `import.meta.env` (`process.env.X`, `process.env["X"]`, a computed key, a
     destructure). Passing the whole object (`hydrateEnv(process.env)`) is how a configuration gets its values and
     is allowed.
   - Exempt by path: configuration classes (`*.config.ts`), generated code (`.stackra/`, `*.generated.*`,
     `generated/`), tooling (`tools/`, `scripts/`, `.agents/`, `.github/`, root `*.config.*` files such as
     `vite.config.ts`) and tests (`__tests__/`, `*.test.*`, `*.spec.*`, `e2e/`). Any other read carries a reasoned
     `oxlint-disable-next-line stackra/no-raw-env -- <reason>`.
   - The rule ships at `warn` with a count of the current reads, as a declared exception to rule-gap B-1 (no warn
     level). It moves to `error` once step 7 below has migrated the reads, in the same change that removes the last.
   - Two more declarations stand beside code: deploy-time needs stay in `runway.yaml` `secrets:` (top level and per
     environment), and a workflow's Infisical step declares the names it reads with `secret-name:`.
   - A secret may carry per-environment rules as the second argument of `@Secret`:
     `@Secret("STRIPE_SECRET_KEY", { refuse: { staging: ["sk_live_"], production: ["sk_test_"] } })` refuses a
     live-prefixed key in staging and a test-prefixed key in production. `environments: ["staging", "production"]`
     narrows where a name is needed; without it, every environment the member deploys to needs it.

2. **Collect.** `stackra gen` writes an `env` section into each member's `stackra.manifest.json`, one row per name:
   - `name`;
   - `kind`: `secret` (from `@Secret` or `runway.yaml` `secrets:`), `public` (an `env` name with a public prefix:
     `VITE_`, `EXPO_PUBLIC_`, `RENDERER_VITE_`) or `config` (any other `env` name);
   - `rules`: the field's type and format from the schema (the field type, its validation decorators) and the
     per-environment `refuse` prefixes;
   - `environments`: where it is needed;
   - `home`: the Infisical project and path that holds the value (decision 3);
   - `from`: the class and file that declares it.
     This lists names and rules, never a schema's defaults or a value, so ADR 0305 rule 34 (no config schema in the
     manifest) still holds.

3. **Infisical is the one home of every value.** This replaces 0512 decision 4's "non-secret ids and URLs are not
   stored in Infisical" for runtimes: a config or public value is not secret, but it still has exactly one home, so a
   change is one edit. Homes follow the Infisical plan of 2026-11-04 (free plan: an identity sees whole projects):

   | Declared by                   | Project                                               | Path                |
   | ----------------------------- | ----------------------------------------------------- | ------------------- |
   | a member (code or `secrets:`) | `<product>-runtime` (dev, staging)                    | `/runtime/<member>` |
   | a member, production          | `<product>-runtime-prod` (prod)                       | `/runtime/<member>` |
   | a workflow's `secret-name:`   | `ci-build`, `ci-deploy` or `ci-production` (its step) | its `secret-path`   |

   Runway's `preview` reads `dev`. `<product>` is the root runway's product key. A public value is pushed as a build
   variable (EAS environment, Vite define, Worker var), never as a server secret, and never holds a secret
   ([0231](/adr/0231-naming-and-casing-standard) decision 4).

4. **Check.**
   - `runway env check` runs anywhere, with no login, and reads names only. It fails on a name read but not declared
     (a raw read the lint rule reports with no reasoned disable, or a `runway.yaml` name no code reads is a warning),
     and on a declared name with no home (no product key, no runtime path, or a workflow `secret-name` with no
     `secret-path`). The Quality Gate runs it on every pull request; once Flow's gate replaces the Quality Gate
     (STA-1729), Flow's gate runs it.
   - `runway env check --values --env <env>` runs only in a CI job proved by its GitHub OIDC token (as `secrets sync`
     does), logged in with that environment's identity (`figentra-ci-deploy` for dev and staging,
     `figentra-ci-production` for production). It fails when a name is missing in Infisical or a value breaks its
     rules. It is an error for the environment being deployed and a warning for the others. **It never prints a
     value**: each line is a name, its home and `pass` or `fail` with the rule that failed, and at most the first
     eight hex characters of the value's SHA-256.
   - `runway env orphans` warns on a name in an Infisical home that nothing declares. It reads names only.

5. **Sync.** `runway env sync <env>` pushes the values from Infisical into the runtimes: Encore secrets, Cloudflare
   Worker secrets and vars, and EAS environment variables, through the existing providers. It is `runway secrets sync`
   extended, not a second tool; `secrets sync` stays as its alias. GitHub and GitLab hold no value: a job reads
   Infisical over OIDC. A developer's machine gets values through `stackra dev`, from the `/agents` vault paths (d4 and
   [0267](/adr/0267-infisical-agent-vault-deferred)).

6. **Webhook.**
   - A small Worker, `env-sync`, lives in core's `workers/`. It is shared platform infrastructure that serves every
     repository, like `turbo-cache` and `registry`, and core's runway already ships those
     ([0517](/adr/0517-where-services-and-their-resources-run) decision 10: one deploy tool, one place for shared
     infrastructure; figentra/figentra's workers serve the Figentra product only).
   - It verifies Infisical's webhook signature (HMAC-SHA256 of the body with the webhook's secret) and dispatches the
     `env-sync` workflow of the repository that owns the changed project, with the project, environment and path.
     The payload carries metadata only, never a value; a payload with a value field is refused.
   - dev and staging sync automatically.
   - Production only notifies: the workflow's production job keeps the owner gate (`github.triggering_actor` must be
     the owner), as the products' `deploy.yml` does
     ([0468](/adr/0468-agents-deploy-dev-and-staging-production-waits-on-one-environment-approval)).
   - A scheduled run compares hashes of each runtime's values with Infisical's and syncs what differs, so a missed
     webhook heals on the next run.

7. **Push is the default; pull-at-boot stays opt-in.** The Infisical driver of
   [0371](/adr/0371-secret-store-drivers-which-deploy-mode-binds-which-and-how-the-bootstrap-credential-arrives)
   (`InfisicalSecretStoreDriver`) stays for on-prem and air-gapped installs that choose it. SaaS runtimes get values
   pushed by decision 5, for two reasons:
   - pull needs a machine identity per runtime, and the free plan allows 5 identities, humans included;
   - a pulling runtime cannot boot while Infisical is down, and a pushed one can.

**Consequences.**

- Nobody hand-manages a variable: a new name is a line in a configuration class, its value is set once in its home,
  and the check, sync and webhook do the rest.
- Every deploy job gains a `--values` check before it ships; a missing or wrong value fails the deploy, not the boot.
- Config and public values move into Infisical; the runway `vars` that held them become declarations only, once
  `env sync` pushes vars.
- The current raw reads are migrated package by package; the rule moves to `error` after the last one.

**Enforcement.**

- `stackra/no-raw-env` (warn until the migration ends, then error).
- `runway env check` in the Quality Gate, on every pull request.
- `runway env check --values` in each deploy job; `runway env orphans` scheduled.
- planned — the `env-sync` Worker and workflow, and the scheduled hash compare.
- The value rule is kept by the code: no command prints a value, and `guard-bash` keeps denying `infisical export`,
  `infisical secrets get` and `infisical run` to agents.
