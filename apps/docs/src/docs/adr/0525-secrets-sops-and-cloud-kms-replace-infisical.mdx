## Context

[0173](/adr/0173-secrets-infisical-is-the-source-of-production-secrets) made Infisical the source of every secret
value. On the free plan an identity sees whole projects, and the layout was bent around that: five identities in
all, one project per reader, and a rebuild runbook of ten steps that the owner had to click through in the
Infisical web app. The owner (2026-11-06): "I don't want any GUI to handle the secrets … it asks me whatever it
wants, I paste it or set it in a file, and it's automatically handled. Autonomous end to end." Infisical Pro costs
about $138 a month and still puts custom roles on Enterprise. Doppler is another vendor of the same size of move.
Self-hosting Infisical, OpenBao or a Worker of our own means running the most critical system ourselves. SOPS
with a cloud KMS needs no GUI, no vendor and no plan tier: access is IAM, every decrypt is audited, and it costs
about $1 a month.

### Why Google Cloud KMS

Google Cloud KMS rather than AWS KMS, for these reasons. Nothing here is a new decision.

- **The secrets root sits outside the estate it protects.** AWS credentials live in SOPS. If an AWS account is locked
  or held, as one was on 2026-11-06, that can't lock us out of our own secrets.
- **Nothing new to set up.** The `figentra-tools` project and the `github` Workload Identity pool already existed.
- **Cost.** One key per scope costs about $0.06 per key version a month on Google Cloud. AWS charges $1 per key a
  month.
- **A second way in.** The owner's offline `age` recipient can decrypt every file without any cloud.
- **Not a dead end.** SOPS can add AWS KMS as another recipient later without re-architecting.

## Decision

1. **Source.** Every secret value lives in the private repository `figentra/secrets`, as a SOPS-encrypted file. A
   value is never in plain text in git. The layout:

   | Path                                | Holds                                                                                     |
   | ----------------------------------- | ----------------------------------------------------------------------------------------- |
   | `.sops.yaml`                        | which KMS key and `age` recipient encrypt which path; generated by figentra/infra         |
   | `catalog.yaml`                      | names only: owner, purpose, `kind`, `rotateDays`, `expires`; generated from `runway.yaml` |
   | `products/<product>/<env>.enc.yaml` | a product's runtime secrets, one file per product and environment                         |
   | `ci/<scope>.enc.yaml`               | CI tokens: `release`, `registry`, `env-sync`, `linear-sync`, `infra` and the like         |
   | `agents/<name>.enc.yaml`            | developer and MCP tokens, read by `tools/scripts/mcp.sh`                                  |

2. **Keys.**
   - One Google Cloud KMS key per file scope, in the key ring `figentra-secrets` of project `figentra-tools`:
     `<product>-production` and `<product>-nonproduction` for each product, `ci-production`, `ci-nonproduction`
     and `agents`. Automatic key rotation is on. figentra/infra creates them.
   - Every file is also encrypted to the owner's offline `age` public key. That is break-glass: the owner can
     decrypt with no cloud at all. `pnpm secrets:age-init` makes the key pair on the owner's Mac and prints only
     the public key.

3. **Who decrypts.**
   - GitHub Actions signs in to Google Cloud through Workload Identity (pool `github`).
   - Each repository and environment gets one service account with `cloudkms.cryptoKeyDecrypter` on its own key
     only, and its trust is pinned to `repo`, `environment` and `job_workflow_ref`.
   - Nobody and nothing else decrypts, and every decrypt is in Cloud Audit Logs.

4. **Three kinds of value.** `catalog.yaml` gives each name a `kind`:
   - **(a) generated**: webhook secrets, signing keys. `pnpm secrets:generate NAME --scope S` creates the value in
     memory, encrypts it and opens a pull request in `figentra/secrets` that merges itself. No human.
   - **(b) minted**: Cloudflare scoped tokens, Stripe restricted keys. figentra/infra mints them from one parent
     credential and writes them the same way. No human after the parent.
   - **(c) human**: the agent asks in chat, "run `pnpm secrets:put NAME --scope S`", with the purpose and where
     to get the value. The owner pastes into a hidden prompt, or drops a file in `~/Secrets-inbox/`. The value is
     encrypted in memory, the file is deleted, and the pull request merges itself. The agent sees names only.

5. **Sync.**
   - A push to `figentra/secrets` runs its `sync` workflow. The workflow decrypts in CI and writes Encore secrets,
     Cloudflare Worker secrets, EAS environment variables and GitHub environment secrets through Runway's secrets
     provider. That provider is the only writer to each runtime store.
   - The env-sync Worker's Infisical webhook is replaced by that push trigger.
   - The 2026-11-04 amendment of 0173 carries forward: names are declared once in code, `stackra gen` collects
     them, and `runway env check` and `runway env sync` check and push them. The difference is the value's
     home, which is now the `figentra/secrets` file of decision 1, not an Infisical project.
   - The opt-in pull-at-boot driver of
     [0371](/adr/0371-secret-store-drivers-which-deploy-mode-binds-which-and-how-the-bootstrap-credential-arrives)
     stays for on-premises installs that choose it; it is the customer's store, not ours.

6. **Scripts.** All of them live in `tools/scripts`, and none prints, logs or passes a value on argv:
   - `secrets:put`, `secrets:generate`, `secrets:rotate`, `secrets:migrate` (Infisical to sops, once, during the
     move: names compared one to one, values by hash) and `secrets:catalog`;
   - `secrets:import` writes sops instead of Infisical;
   - `mcp.sh` decrypts `agents/` into the MCP server's process only.

7. **Rules.**
   - The model never sees a value ([0267](/adr/0267-infisical-agent-vault-deferred)). Agents run only the
     audited scripts. `sops -d`, `sops decrypt`, `sops exec-env`, `sops exec-file` and printing a decrypted file are
     denied to every agent, as 0009's forbidden commands are.
   - No static cloud keys: AWS through IAM roles, Google Cloud through Workload Identity, GitHub through Apps. A
     secret we can avoid, we avoid.
   - Least privilege: one key per scope, and one decrypter per repository and environment.
   - One writer per store: the `sync` workflow writes the runtimes, and the scripts and figentra/infra write
     `figentra/secrets`.
   - Every name has an owner, a purpose, a kind, a rotation period and, for kind (c), an expiry, in
     `catalog.yaml`. `runway validate` fails when code uses a name the catalog lacks.
   - Production changes are automatic: the policy gate of [0523](/adr/0523-humans-approve-policy-not-instances)
     reviews them, and `git revert` undoes them. Deleting a production secret, and deleting Infisical, stay
     owner-only.
   - Verify and tests need zero secrets.

8. **Carried forward from 0009 and 0173.** Secret names are in git. Values are in git only as ciphertext. There is
   no `.env` file. The forbidden commands of 0009 §6 stay forbidden.

9. **The move.** Infisical keeps working until every workflow reads sops (plan phase P4), so nothing breaks
   during the move. Infisical is deleted at P6, only when the owner says "delete Infisical".

## Consequences

- No web page holds a secret, and the owner's whole part is: make the `age` key once, let `secrets:migrate`
  read Infisical once with their own login, say "delete Infisical" at the end, and answer the agent's
  `pnpm secrets:put NAME` questions for kind (c) only.
- Secrets are reviewed and versioned like code. A changed name is a reviewed diff, and Cloud Audit Logs say who
  decrypted what.
- Old values stay in git history, encrypted. A leak means rotation, which is automated for kinds (a) and (b),
  not deletion.
- The five-identity cap and the plan tiers are gone, and so is the Infisical rebuild runbook.
- Every workflow's Infisical login step becomes the shared Google Cloud sign-in and decrypt action, one
  repository per pull request.
- figentra/infra gains the key ring, the keys, the Workload Identity service accounts and `.sops.yaml`.

## Enforcement

- planned — the `sops` denies in `.agents/hooks/_rules.mjs` (`guard-bash`) and `.claude/settings.json`, with
  their tests. A hook change needs the owner's yes.
- planned — `tools/scripts/__tests__/secrets-*.test.mjs`: every path asserts no random canary value reaches
  output, a log or argv (as `secrets-import.test.mjs` does today).
- planned — Workload Identity bindings in figentra/infra: a test workflow decrypts its own scope and is refused
  another.
- planned — `runway validate` fails on a name missing from `catalog.yaml`.
- The gitleaks pre-commit hook and CI scan carry forward.

## Amendment 2026-11-06: one file per secret (STA-2144)

**Context.** Decision 1 put a product's secrets for one environment in one file. Changing one value in a shared sops
file needs the file's data key, and sops then recomputes the file's MAC over every plaintext value, so whoever writes a
shared file can read all of it. That breaks 0257's invariant that the writer never sees a value. The leader approved the
change the same day, and figentra/infra built the keys to match (figentra/infra#18, #19).

**Decision.**

1. **One file per secret.** `products/<product>/<dev|staging|production>/<NAME>.enc.yaml`,
   `ci/<build|deploy|production|flow|infra>[/<folder>]/<NAME>.enc.yaml` and `agents/<NAME>.enc.yaml`. Each file is encrypted
   with its own data key, so a writer needs only KMS Encrypter and never decrypts anything. A name is its file name, so
   `secrets:catalog` lists names with no key at all.
2. **Keys.** 27, one per scope: `<product>-dev`, `<product>-staging` and `<product>-production` for billing, commerce,
   figentra, invoicing, os, pay and tamo, plus `ci-build`, `ci-deploy`, `ci-production`, `ci-flow`, `ci-infra` and
   `agents`. `.sops.yaml` has one rule per scope prefix. `ci/infra` holds figentra/infra's App key: the sync writes it
   to figentra/infra's `infra-apply` environment, it is not in the ciphertext mirror, and agents never write it.
3. **Writers.** `cryptoKeyEncrypter` on the key ring for the owner's login, which agents use as well (they run as the
   owner's user, and a separate service account would need a static key), and for `infra-apply` (minting, decision 4b).
4. **Decrypters.** One service account per key, `sops-<key>`, with `cryptoKeyDecrypter` on that key only. Only
   figentra/secrets' `sync.yml` on main, in the GitHub environment named after the key, can impersonate it. The owner's
   login also decrypts `agents`, for `mcp.sh`. A workflow in another repository decrypts its scope only after
   figentra/infra adds it to the table; the policy gate refuses any other binding.
5. **CI decrypts in place, with one exception.** Each CI workflow decrypts its own scope through the shared action
   (`google-github-actions/auth`, then `runway secrets decrypt --scope <s>`), pinned per (repository, environment,
   `job_workflow_ref`) in figentra/infra's decrypter table (plan phase P4, STA-2146). The one exception: figentra/infra's
   own GitHub App id and private key stay GitHub secrets. figentra/infra creates the KMS decrypters and the Workload
   Identity pins, so it cannot depend on them (bootstrap).
6. **The ciphertext mirror.** Workflows in other repositories cannot check out the private `figentra/secrets`, so its
   `sync.yml` publishes the ciphertext to `gs://figentra-secrets-ciphertext/` on every push to main: one flat prefix
   per scope (`/` becomes `.`, so `ci/production/release` is `ci.production.release/`, and a prefix-conditioned grant
   on one scope never covers a nested one), each with its `*.enc.yaml` files and a names-only `manifest.json`.
   Removed names are deleted from the mirror. The ciphertext mirror in GCS is read by callers' Workload Identity
   identities, each on its own scope's prefix; every value still lives in `figentra/secrets`, and only KMS decides
   who can decrypt. The publisher holds storage on the bucket and no KMS role.
7. **Verification.** A writer cannot read back, so `secrets:migrate` records each name's 8-hex SHA-256 prefix in
   `migration/hashes.yaml`, and a CI job with decrypt rights compares the files against it.

**Enforcement.** `SCOPE_RX` and `secretFile` in `tools/scripts/secrets-sops.mjs` (with
`tools/scripts/__tests__/secrets-sops.test.mjs`); the decrypter table and its policy-gate rule in figentra/infra
`estate/secrets.mjs`.

## Amendment 2026-11-07: no Infisical driver on-premises (STA-2146)

Decision 5 kept 0371's opt-in pull-at-boot driver for on-premises installs. That driver is retired: no install binds
Infisical, and figentra/stackra#620 removed `InfisicalSecretStoreDriver` from `@stackra/config`. Nothing bound or
defaulted to it.

- **On-premises and air-gapped** installs bind `env`, with values the customer's operator injects, or
  `aws-secrets-manager` where they run on AWS ([0371](/adr/0371-secret-store-drivers-which-deploy-mode-binds-which-and-how-the-bootstrap-credential-arrives),
  amended the same day).
- **No exception remains** for Infisical anywhere: in CI, at runtime, in an agent's tools or in a customer's install.
  Phase 0 of the master plan deletes it (P6, the owner's word).

## Amendment 2026-11-10: generated dev values on the workstation (STA-2679)

Decided by the leader under the owner's delegation, 2026-11-10. A local `stackra dev` had no secret values, so a
service that reads a required `@Secret` at boot could not start. The runtime reads each `@Secret` from its environment
by name, so a dev value only has to reach the member's own process.

- **`stackra dev secrets init`** writes one random value (32 bytes, base64url) for each required secret that dev
  needs, across the manifests of the workspace's running members, to `.stackra/dev-secrets.json` at the workspace
  root, mode 600. It prints names, never a value. It never generates a connection string (a name ending `_URL`,
  `_DSN`, `_ENDPOINT` or `_HOST`, or a url format) or the events relay's key pair; it lists those as needing a value.
  An existing file only gains its missing names unless `--rotate`; `--from <file>` copies matching names from another
  repository's file.
- **`stackra dev`** adds the file's values for a member's own declared names to that member's tool run.
- **This file is the one secret-value file allowed on a workstation.** Its values are machine-generated and serve dev
  only. They never come from or go to `figentra/secrets`, and no deployed environment reads them. The owner's "no
  `.env` files" rule is untouched, because this is a gitignored, machine-generated JSON file, not a `.env` file.
- The testbed upload excludes it. A read-deny guard entry for it and the matching text in the secrets rule are the
  owner's to add.
- `encore run` passes its own environment to the app process it starts: proven 2026-11-10 by the OS lane on identity
  (Encore 1.58.8), where two `@Secret` values set on `encore run` reached `envSecrets` and the boot passed its config.
