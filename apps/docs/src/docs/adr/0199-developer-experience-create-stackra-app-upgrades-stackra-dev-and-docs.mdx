## Context

A new developer needs one command to start, one command to upgrade, and a dev loop that runs the whole stack. The owner's answers DX1 to DX9 (mem L565–567, 2026-10-20) and the ZITADEL dev container (mem L592) fix these.

## Decision

1. **Scaffold (DX1, DX6 and DX9).** `create-stackra-app` scaffolds `runway.yaml` with its topology, the CI workflows, the agent kit and a devcontainer. The reference services are its examples. The versioned agent kit installs through `stackra agents sync`.
2. **Upgrades (DX2).** `stackra upgrade` applies codemods written with ast-grep and ts-morph.
3. **Dev loop (DX3 and DX4).** `stackra dev` runs gen in watch mode, `encore run`, and a small compose file. The compose file includes a ZITADEL container with a seeded instance (mem L592). The docs are one Mintlify site with tabs.
4. **Encore pin (DX8).** The Encore CLI is pinned through mise, and the `encore.dev` catalog is used (gap B13).

## Consequences

- A new developer runs one command, and gets the same stack the tests use.
- A version bump is applied by `stackra upgrade`, so the codemods carry the change.

## Enforcement

planned — `stackra upgrade` is tested against the codemod fixtures; the dev compose file is checked by the smoke test in CI.

## Amendment 2026-11-27: the initializer is `create-stackra`

Decision 1 named the one-command scaffold `create-stackra-app`. No such package was built: the scaffold is
`stackra create` in `@stackra/cli`. A clean machine still could not reach it with one command, because `@stackra/*`
lives only on the Stackra registry ([0453](/adr/0453-the-stackra-registry-one-npm-compatible-store-on-cloudflare-and-our-own-licence-engine)),
`npx @stackra/cli` and `npm create stackra` both answered 404 from npmjs, and pointing npm's whole registry at the
Stackra registry breaks every other package, since that registry never proxies npmjs (0453 decision 4).

1. **The name is `create-stackra`.** `npm create stackra` (and `pnpm create`, `yarn create`) runs the npmjs package
   `create-stackra`, so the initializer carries that name, unscoped: a scoped name cannot be reached that way. It is
   the member `packages/developer/create-stackra`, the only unscoped member (`UNSCOPED_PACKAGES` in
   `@stackra/repo-checks`).
2. **It maps the scope, not the registry, and only hands over.** It runs
   `npx --yes --@stackra:registry=<origin> @stackra/cli@<cli> create <arguments>` with `STACKRA_REGISTRY=<origin>`,
   where the origin is `--registry`, else `STACKRA_REGISTRY`, else the Stackra registry. It writes no file and no npm
   setting, has no dependency, and asks nothing: every question, check and file belongs to `stackra create`, which
   writes the same origin into the new app's `.npmrc`.
3. **The documented install line** is `npm create stackra@latest <folder>`. Until the package is on npmjs, the same
   run is `npx -y --@stackra:registry=https://npm.stackra.figentra.com/ @stackra/cli create <folder>`.
4. **Publishing waits on the owner.** The npmjs name `create-stackra` is to be claimed by the owner, and publishing it
   to npmjs is an exception to 0453's "only the Stackra registry", which the owner rules on. Until both, the member
   stays `"private": true`, so the release workflow (which publishes every non-private member to the Stackra
   registry, which takes scoped names only) leaves it out. Tracked in STA-2897.
