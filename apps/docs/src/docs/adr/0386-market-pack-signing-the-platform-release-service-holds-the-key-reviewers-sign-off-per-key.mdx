## Context

0370 makes a service refuse to start on a pack whose signature does not verify against a trusted key, so whoever holds
the private key can change tax, fiscal and legal behaviour in every tenant. Two different things were called "signing":
a person vouching that a value is legally right, and the cryptographic signature that proves the bytes came from the
release. Alternatives weighed: counsel or each local reviewer holding a key (rejected: many keys, held on laptops, and a
reviewer's approval is per value, not per file), a key per product for its sections (rejected for now: every service
would trust several keys and a product could ship a section the platform never saw), and a CI secret variable
(rejected: anyone who can change a workflow can read it).

## Decision

1. **Two acts, two records.** A reviewer's approval is a sign-off per entry key in the pack version (`reviews`,
   0370 decision 8): who, on what date. The Ed25519 signature is the release's proof that the bytes are the reviewed
   ones. A reviewer never holds a signing key.
2. **One holder.** The platform release service (OS) holds the private key in a managed key store (a cloud KMS or HSM
   with an Ed25519 key that cannot be exported). No person, repository, CI variable or tenant holds it. `signPack`
   runs inside that service with a non-exportable `CryptoKey`.
3. **What may be signed.** The release service signs a pack version only when `unreviewed` lists no key and its
   status is `beta` or `live`. Drafts are never signed. Product sections are signed by the same service after the
   product's own reviewers sign off their keys.
4. **Key ids and rotation.** Each key has an id (`packs-2026`). Deployments list trusted public keys by id
   (0370 decision 2); during a rotation two ids are trusted, and the old one is removed once every live pack is
   re-signed. A compromised key is removed from every deployment at once; packs it signed stop loading.
5. **Who may promote.** Moving a signed version to `live`, and pinning a tenant, remain operator actions with their own
   permissions and audit; holding the key gives no right to promote.

## Consequences

- The blast radius of a leaked reviewer account is one unsigned draft; a forged pack needs the release service.
- A pack change always needs both a reviewer sign-off and a release run; there is no "quick fix" path that skips
  either.
- Rotation is routine data work (a new trusted id, re-signing), not a code change.
- A product that wants to ship sections without the platform's release service needs a new ADR.

## Enforcement

planned — the release service's sign step refuses a draft or a version with unreviewed keys; deployments read trusted
keys from configuration only. Nothing checks either yet.

## Amendment 2026-11-09: an interim bundled source until the release service signs

The release service's sign step is not built, so no deployment can resolve a live pack: `store` serves only signed
packs, and nothing signs them or publishes their hashes. Until it is built, a deployment may run the interim `bundled`
source (`market_packs.source: bundled`), owner ruling of 2026-11-09:

1. **The pin replaces the signature.** `bundled` serves only the packs `@stackra/market-packs` ships in
   `assets/data/packs/` whose content hash (`contentHash` of the pack as shipped, the hash `verifyPack` checks) the host
   names in `packHashes`. An unpinned file is never read. `BUNDLED_PACK_HASHES` lists the live bundled packs so a host
   can copy its pins, but it is never a default.
2. **Live only.** A pinned pack that is not `live` is refused (`not_live`). Turning a bundled pack live is a reviewed
   change of its own, beside the hash it produces. Drafts stay for authoring only (0385 decision 7).
3. **Not production by default.** In production (`STACKRA_ENVIRONMENT=production`) the driver refuses when it is built
   (`BundledPackSourceRefusedError`) unless the host sets `allowBundledInProduction`, and it warns once when that is
   set.
4. **Signing comes before production.** This decision's release-service signing (decisions 1 to 3) is still the
   target. A production deployment moves to `store` with signed packs once the sign step exists, and this amendment
   lapses then.

Decisions 1 to 3 and the consequences above stand. Enforcement: the `bundled` driver and its tests; still planned for
the release service's sign step.
