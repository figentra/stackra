## Context

Better Auth was the identity choice (0051, 0093). The owner's identity answers of 2026-10-20 (mem L587–592, L604–616) make ZITADEL the one identity provider for every Stackra product and for Figentra OS, and remove Better Auth from the stack.

## Decision

1. **One provider.** ZITADEL is the identity provider. Better Auth leaves the stack.
2. **Provider-neutral client.** `@stackra/identity` is the OIDC client, the SDK and the contracts, with provider-neutral ids and claims mapping.
3. **Control plane, not login.** The identity service is a control plane: the app registry, the tenant to ZITADEL org mapping, the IdP metadata, the identity events and the service identities. It never proxies a login.
4. **Hosting.** ZITADEL Cloud serves SaaS. ZITADEL is self-hosted, unmodified, for on-prem and air-gap (AGPL is accepted). `stackra dev` runs a ZITADEL container. _Amended by [0493](/adr/0493-runway-resources-and-workloads-one-runway-provisions-the-product-runtime) (owner, 2026-10-30): a SaaS region that residency forces (KSA in-country) self-hosts ZITADEL as a runway workload; ZITADEL Cloud stays the default elsewhere._
5. **One instance (I1).** Staff have one global account. Each tenant gets a ZITADEL org for its end customers.
6. **Sign-in methods (I2).** All the sign-in methods of memory L605.
7. **Login app (I3).** One login app of ours, on ZITADEL session APIs, serves every hostname through Cloudflare for SaaS, with the brand cascade.
8. **Sessions (I4).** The web uses a BFF with an HttpOnly cookie, code and PKCE. Mobile uses PKCE with a rotated refresh token in SecureStore. JWT access tokens last 5 to 15 minutes and are verified by JWKS.
9. **IdP outage (I12).** Existing sessions keep working during an identity provider outage.

## Consequences

- The provider can change behind `@stackra/identity`, because no product calls ZITADEL directly.
- The identity service never sits on the login path, so an identity outage does not stop a signed-in user.

## Enforcement

planned — the contract tests of `@stackra/identity` run against a ZITADEL container in CI; the validator rejects a direct `zitadel` import in a product.

## Amendment 2026-11-08: one instance per region; staff and customer organisations

**Context.** Decision 5 ("one instance; staff have one global account") predates
[0353](/adr/0353-data-residency-a-region-fixed-at-sign-up-a-login-directory-that-only-routes-and-copies-within-a-jurisdiction)
and [0361](/adr/0361-principals-and-parties)'s one ZITADEL instance per region, and the two disagreed. The owner's
sign-in decision settles it. Source: the owner's decision and answers of 2026-11-08 (owner ledger).

**Decision.** Decision 5 becomes: **one ZITADEL instance per region.** Merchant staff are in one shared staff
organisation per region, with access per merchant by IAM memberships; each merchant's end customers are in that
merchant's own customer organisation; an Enterprise merchant's staff may be in a dedicated organisation with its own
IdP ([0361](/adr/0361-principals-and-parties) amendment 2026-11-08). Decision 7 stays amended by 0268: ZITADEL's hosted
login with each organisation's label policy is the branded login.

## Amendment 2026-11-26: the dev issuer, accepted only under `stackra dev`

**Context.** Decision 8 verifies every access token by the issuer's JWKS, and decision 4 runs a ZITADEL container
under `stackra dev` (STA-2683, not built yet). A new app therefore answers 401 on every protected route and a
developer cannot try a write, a permission or a tenant rule locally (STA-2795, found in the STA-2794 create proof).
Source: STA-2795's "Done when" (owner, 2026-11-26): a documented, dev-only way to call protected routes that a deployed
environment refuses, with a test; ZITADEL and OIDC stay the only path outside local development.

**Decision.**

1. **A local issuer.** `stackra dev` keeps one ES256 key pair and a seeded dev user per workspace in
   `.stackra/dev-issuer.json` (git-ignored, mode 600) and hands each service it runs the public key set in
   `STACKRA_DEV_ISSUER_KEYS` with `STACKRA_ENVIRONMENT=dev`. `stackra dev token` prints a dev token: a JWT issued by
   `https://dev-issuer.stackra.invalid` for the audience `stackra-dev`, carrying the same provider-neutral claims a
   ZITADEL token carries, so `actorOf`, the scope chain and IAM see it as a real caller.
2. **Same checks.** `verifyCallToken` (`@stackra/app/server`), the one check behind `CallAuthenticator` and
   `BearerTokenGuard`, verifies a dev token under the dev keys with every decision-8 check (algorithm, signature,
   issuer, audience, expiry, leeway). The configured issuer keeps working beside it.
3. **Never deployed.** Dev keys count only when the one environment reader (`readEnvironment` of `@stackra/config`,
   [0296](/adr/0296-runway-v3-member-requires-and-root-topology-groups) amendment of 2026-11-26, STA-2844) answers
   `dev`, the developer machine of [0170](/adr/0170-deployment-what-deploys-where-and-how-a-release-is-promoted)
   decision 5. The gate never reads a configuration value: `BearerConfig` holds the dev key set only and no
   environment, so neither a values layer nor a host override can turn dev sign-in on. A process that carries the keys
   where the reader answers anything else (`test`, `preview`, `staging`, `production`, including a deployed platform
   that set no variable) fails boot with `ConfigInvalidError` naming `STACKRA_DEV_ISSUER_KEYS` (`createApp` checks
   before the generated boot runs), and so does one the reader refuses (a misspelt name, `dev` on a deployed platform,
   a self-hosted image that reports nothing), so a deployment never answers a dev token. `CallAuthenticator` and
   `BearerTokenGuard` ask the reader again on every call. Without the keys a dev token is checked only against the
   real issuer, which refuses it. A private key never travels in the variable. The key set itself is runtime-only,
   like the running environment: `STACKRA_DEV_ISSUER_KEYS` is a safety-critical variable (`SAFETY_CRITICAL_VARIABLES`
   of `@stackra/config`), so `buildConfig` refuses `app.bearer.devKeys` from a values layer and `runway validate`
   refuses it in a runway `config` block before a deploy; only `stackra dev` sets the variable, on the process it
   runs.
4. **ZITADEL stays.** Decision 4's local ZITADEL remains the full-fidelity path (sign-in pages, refresh, real
   organisations); the dev issuer is the zero-setup one.

**Enforcement.** `@stackra/app` tests: `devIssuerKeys`, `verifyCallToken`, `runningEnvironment`, `BearerConfig` (no
environment field; the dev key set refused as a value), `CallAuthenticator`, `BearerTokenGuard` (a host override naming `environment = "dev"` on a
production platform still refused) and `createApp` (boot refused in `test`, `preview`, `staging`, `production` and on a
production platform with no variable); `@stackra/cli` tests: `stackra dev token`, `ensureDevIssuer`, `devIssuerEnv`
(nothing handed under another or a misspelt environment) and the `stackra dev` run of a service; `@stackra/config`
(`SAFETY_CRITICAL_VARIABLES` holds `STACKRA_DEV_ISSUER_KEYS`) and `@stackra/runway` (`runtimeOnlyFields` and
`checkRuntimeOnlyConfig` refuse `app.bearer.devKeys` in a runway `config` block).
