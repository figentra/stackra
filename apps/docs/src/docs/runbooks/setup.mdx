## Where each secret name lives

Every value lives in `figentra/secrets`; a runtime store holds only what the sync copies there. Application code reads a value from the runtime, never from a file. No `.env` ([Secrets](/runbooks/secrets)).

### Encore `secret()` (application secrets, per environment)

Declared as `secret("NAME")` in the service that uses it. The value goes into `products/<product>/<env>` with `pnpm secrets:put` (or `secrets:generate`), and the deploy's `runway secrets sync` writes it into Encore. A new name must exist in its scope before the deploy that declares it, or the sync fails with nothing changed.

| Name                                           | Purpose                       | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ResendApiKey`, `ResendWebhookSecret`          | Email send, delivery webhooks | Planned                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `StripeSecretKey`, `StripeWebhookSecret`       | Payments                      | Planned; test keys outside prod                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `BetterAuthSecret`                             | Session and cookie signing    | Planned; generated per environment                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `SentryDsn`                                    | Crash reporting               | Planned; not confidential                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `ScanAwsAccessKeyId`, `ScanAwsSecretAccessKey` | Malware-scan callbacks        | TODO: likely replaced by role-based access                                                                                                                                                                                                                                                                                                                                                                                                           |
| `PostHogApiKey`                                | Server-side analytics         | Planned                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `APPLE_SIGN_IN_KEY`                            | Sign in with Apple `.p8` key  | Not an Encore secret: the identity Pulumi stack reads it as `zitadel:APPLE_SIGN_IN_KEY` (the name the seed's `appleSignIn.privateKeySecret` gives), `figentra/secrets` first ([ADR-0525](/adr/0525-secrets-sops-and-cloud-kms-replace-infisical)). The team id, services id and key id are public, in the seed. Each other social provider's client secret follows the same pattern, one stack config secret per provider, held by ZITADEL. STA-1578 |

This repository has no runtime secret (`runway.yaml`: "core has no runtime secret"). A package driver reads a secret by name through its secret store (`this.secret("NAME")`), and the product that binds the driver declares the name; in a product the authoritative list is what `git grep 'secret("'` finds, and `runway env check` checks that every name is declared and has a scope.

The Quality Gate reads `UNIWIND_AUTH_TOKEN` from `ci/build` ([0310](/adr/0310-stackra-ui-pro-private-heroui-pro-wrappers) decision 11). Stackra installs no HeroUI Pro ([0469](/adr/0469-stackra-ships-no-heroui-pro-free-heroui-and-stackras-own-components-only)), so no workflow here reads a HeroUI token.
`HEROUI_PERSONAL_TOKEN` in `agents` is for the HeroUI MCP servers only.

| Visibility | Names                                                                                                                             |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Plain      | `EXPO_PUBLIC_API_URL`, `EXPO_PUBLIC_APP_ENV`, `EXPO_PUBLIC_SENTRY_DSN`, `EXPO_PUBLIC_POSTHOG_KEY`, `SENTRY_ORG`, `SENTRY_PROJECT` |

EAS signing credentials live in EAS credentials. The submit keys CI uses (App Store Connect, Google Play) are in `ci/deploy/store` and `ci/production/store`.

### GitHub repository variables (not secrets)

`REGISTRY_D1_DATABASE_ID`, `REGISTRY_KV_NAMESPACE_ID` and `REGISTRY_READ_ONLY` (`deploy-registry.yml`). CI needs no identity id: the `secrets-decrypt` action signs in as the job itself. This repository deploys no console, so it has no public build-time keys; a product names its own (`VITE_SENTRY_DSN` and the like).

A few GitHub App and Linear credentials are still GitHub **secrets** that workflows read directly: `STACKRA_BOT_APP_ID` and `STACKRA_BOT_PRIVATE_KEY` (`release.yml`, `linear-sync.yml`), `LINEAR_AGENT_CLIENT_ID`, `LINEAR_AGENT_CLIENT_SECRET` and `LINEAR_API_KEY` (`linear-sync.yml`), and `FFLOW_APPROVER_APP_ID` and `FFLOW_APPROVER_PRIVATE_KEY` (`fflow-approve.yml`).

### Cloudflare Worker bindings

Workers hold their own secrets as bindings, set by their deploy workflow from `figentra/secrets`, never by hand: `REGISTRY_SIGNING_KEY` on `stackra-registry` (`deploy-registry.yml`, from `ci/production/registry`) and `TURBO_CACHE_TOKEN` on the cache Worker (`deploy-turbo-cache.yml`, from `ci/build/turbo` `TURBO_TOKEN`). The static Worker has none.

## Tools

Pinned in `mise.toml` ([ADR-0027](/adr/0027-cli-tools-pinned-in-mise)): `node`, `pnpm`, `gitleaks`, `shfmt`, `oxlint`, `oxfmt`, `actionlint`, `zizmor`, `osv-scanner`, `sops`, `age`, `uv`, `maestro` (needs a JDK) and the Session Manager plugin. Run `mise install` once.

Not pinned (no mise backend carries them; `mise.toml` says so): `opencode`, `encore`, `aws` and `claude`. The Google Cloud CLI (`gcloud`) is not pinned either; install it once. `wrangler` runs from each Worker's dev dependencies (`pnpm exec wrangler`), and only CI deploys with it. `pnpm doctor` lists what is missing and how to install it.

## Ordered setup

<Steps>
  <Step title="Toolchain">
    Install mise, then `mise install` and `pnpm install`. Confirm with `pnpm verify`.
  </Step>
  <Step title="GitHub (owner)">
    Org `figentra`, repo `stackra`, branch protection on `main`, push protection and secret scanning
    on, squash merge only.
  </Step>
  <Step title="Linear">
    Team `STA` exists. Create a project per deliverable. Agents label their issues `agent`.
  </Step>
  <Step title="Secrets on this machine (owner)">
    Clone `figentra/secrets` to `~/.stackra/secrets` (or set `STACKRA_SECRETS_DIR`): `gh repo clone
    figentra/secrets ~/.stackra/secrets`. It holds encrypted files only. Sign in as the owner's
    Google account with `gcloud auth application-default login`, then `gcloud auth
    application-default set-quota-project figentra-tools`; sops uses that login to decrypt the
    `agents` scope, and only that account can. `sops` comes from `mise install`. There is no
    Infisical login. `pnpm doctor` checks all three.
  </Step>
  <Step title="Break-glass key (owner, once)">
    `pnpm secrets:age-init` makes the `age` key pair and prints only the public key. Store the
    private key file in your password manager and delete it; figentra/infra takes the public key
    into `.sops.yaml`.
  </Step>
  <Step title="Developer tokens (owner)">
    Put each `agents` name above with `pnpm secrets:put NAME --scope agents`. `tools/scripts/mcp.sh`
    and the pnpm scripts read them; nobody prints them.
  </Step>
  <Step title="AWS and Bedrock (owner)">
    Choose the AWS account. Create the profile named `bedrock`, then `aws sso login` with
    `AWS_PROFILE=bedrock`; OpenCode bills Bedrock through it. Create the monthly AWS Budget for
    Bedrock. The daily agent cap is $150 ([Agents](/agents)).
  </Step>
  <Step title="Cloudflare (owner)">
    Create the scoped API token and put it with `pnpm secrets:put CLOUDFLARE_API_TOKEN --scope
    ci/deploy` (and `--scope ci/production` for the production Workers). Deploy the registry
    and the cache Workers by running "Deploy registry" and the cache deploy workflow (owner runbooks
    in `workers/registry/README.md` and `workers/turbo-cache/README.md`).
  </Step>
  <Step title="Remote cache and registry in CI">
    Put `TURBO_TOKEN` in `ci/build/turbo` and `REGISTRY_SIGNING_KEY` in `ci/production/registry`
    with `pnpm secrets:put` (the owner runs the registry one; agents never write a `registry`
    scope). Publishing needs
    no token (GitHub OIDC, [Release](/runbooks/release)); reading `@stackra` needs none either.
  </Step>
  <Step title="Encore Cloud (owner)">
    Create the org and app, connect the AWS account, create environments `staging` and `prod` (PR
    previews are automatic). Do this only once the deploy path (DP2) is decided.
  </Step>
  <Step title="Application secrets">
    For each environment, put every declared name into `products/<product>/<env>`: `pnpm
    secrets:generate` for a generated one, `pnpm secrets:put` (owner) for a human one. The deploy's
    `runway secrets sync` writes them into Encore. Check with `runway env check` and `pnpm
    secrets:catalog --check` (names only).
  </Step>
  <Step title="Email (owner)">
    Add the sending domain in Resend. Add the SPF, DKIM and return-path records and a DMARC record
    in Cloudflare DNS. Create the API key and the webhook.
  </Step>
  <Step title="Observability">
    Sentry org and projects (backend, console, mobile, landing), Better Stack uptime and phone
    alerts, PostHog project.
  </Step>
  <Step title="Mobile (owner)">
    Apple team access, App Store Connect API key, Google Play Console forms and service account, EAS
    project and robot token. The first Play upload is by hand ([Mobile
    release](/runbooks/mobile-release)).
  </Step>
  <Step title="Payments and notifications (owner)">
    Stripe test keys first, live keys at launch. Slack app install and channels. Authorize
    connectors as needed.
  </Step>
</Steps>

## Owner-only steps

These cannot be done by an agent, whatever the brief says:

- Creating any account, accepting any vendor terms, any payment or billing setting.
- Putting a human secret value in (`pnpm secrets:put`), any write to `ci/flow`, `ci/infra` or a `registry` scope, deleting a production secret, and the break-glass `age` key. Agents may generate and rotate kind `generated` values.
- Apple and Google Play console forms, store credentials, the first store upload.
- DNS and Cloudflare token creation; AWS account, SSO and budget settings.
- The Google login that decrypts `agents`; Encore Cloud org and AWS linking.
- Authorizing connectors (Slack) and approving production promotions.

## Daily sign-in

```bash
AWS_PROFILE=bedrock aws sso login
```

This gives OpenCode its Bedrock session. `mise.toml` `[env]` sets `AWS_PROFILE=bedrock`, so `aws sso login --profile bedrock` is enough inside the repository. Secrets need no daily login: the Google login stays until it expires. When a pnpm script says `sops was refused (sign in, or this identity lacks the key)`, run `gcloud auth application-default login` again.
