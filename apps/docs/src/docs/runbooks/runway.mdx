Runway is the deploy layer of Stackra: the runway files say what each member needs and where it runs ([0296](/adr/0296-runway-v3-member-requires-and-root-topology-groups)), and public reusable workflows in this repository deploy it ([0168](/adr/0168-runway-public-reusable-workflows-build-order-and-runway-yaml)). Promotion, rollback and records follow [0170](/adr/0170-deployment-what-deploys-where-and-how-a-release-is-promoted); secrets follow [0525](/adr/0525-secrets-sops-and-cloud-kms-replace-infisical).

## Runway files

| File                                                    | Kind    | Holds                                                                                                                          |
| ------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `runway.yaml` at the root                               | root    | providers, environments and their destinations, topology, targets with their caller workflows, CI secret names, release policy |
| `apps/<name>/runway.yaml`, `workers/<name>/runway.yaml` | app     | the member's ports, hosts, vars and secret names per environment                                                               |
| `services/<name>/runway.yaml`                           | service | what the service `requires`, its secret names and its sizes per environment                                                    |

`pnpm validate` reads every one of them, checks it against the version 3 schema of its kind with `@stackra/runway`, and checks that a grouped topology places each service member exactly once (`checkRunwayFiles`). A `runway.yaml` anywhere else is a finding. The check uses the built package: the Quality Gate builds before it validates, and a local `pnpm validate` before a build prints a notice instead.

Core's root runway declares only `dev` and `production`: Stackra deploys only its own infrastructure, the static Worker, the docs and the npm packages ([0170](/adr/0170-deployment-what-deploys-where-and-how-a-release-is-promoted) decision 1). The docs member has its runway ([0299](/adr/0299-docs-runway) decision 6); `apps/playground`, `apps/mobile` and `workers/static` have one for their dev port only (STA-2081), and `workers/static` gets the rest with gen, when its hand-written `wrangler.jsonc` goes ([0284](/adr/0284-hosted-static-files-one-cloudflare-static-assets-worker) decision 8).

## Local servers for Claude and VS Code

The runways are the one list of what runs locally. `stackra gen` at the workspace root (`pnpm gen:workspace`) writes it
twice: Claude Code's `.claude/launch.json`, which the desktop app's preview tools read, and one `dev: <name>` task per
server in `.vscode/tasks.json` (Tasks: Run Task). Both files are committed, because a Claude session opens in a fresh
worktree before any gen has run ([0295](/adr/0295-build-and-entry-stackra-config-generated-tool-configs-and-entries),
amendment of 2026-11-03). Never edit the generated entries: change the runway and run gen.

| Source                                                                         | Server          | Command                                                                                 | Port                              |
| ------------------------------------------------------------------------------ | --------------- | --------------------------------------------------------------------------------------- | --------------------------------- |
| each `surfaces.<key>` of the root runway (`ops` aside)                         | `surface-<key>` | `stackra build --product --surfaces-only`, then `stackra preview serve --surface <key>` | 4173 plus its place in `surfaces` |
| `apps/<name>/runway.yaml` with `environments.dev.port` (or `mobile.metroPort`) | `<name>`        | build what the member imports, then its `dev` script                                    | the runway's                      |
| `workers/<name>/runway.yaml` with `environments.dev.port`                      | `worker-<name>` | build the Worker and what it imports (`wrangler dev` serves `dist/`), then `dev`        | the runway's                      |

- Each command runs through `sh -c` and builds first, so it starts on a clean checkout after `pnpm install`. In core a
  surface also builds `@stackra/cli`; a product runs its installed `stackra`.
- The port is stable: it comes from the runway, and a surface keeps its port while new surfaces are added at the end of
  `surfaces`. The member's `dev` script must listen on its runway port; gen passes no port to it. Worktree lanes
  (`environments.dev.lanes`) are not applied: the file holds lane 0.
- A member without a dev port in its runway is not listed: services (their Encore dev command waits for gen) and
  `apps/console` today.
- `stackra validate --repository` refuses a generated file that differs from what gen writes (parsed JSON, so oxfmt's
  layout never counts) and two servers on one port; `stackra gen --check` fails on a stale file. In `.vscode/tasks.json`
  gen owns only the `dev: …` tasks and keeps the others and the comment lines at the top.
- OpenCode has no dev-server list to write; its agents start these servers with the same commands, through `pnpm`.
- Vitest needs nothing here: the recommended `vitest.explorer` extension finds each member's `vitest.config.ts`, which
  imports the `.stackra/vitest.config` gen already writes.
- Later: a surface serves a production build through the local edge today. When `stackra dev --surface <key>` runs
  without an OS checkout (gen writes the bundle-mode Vite config, [0436](/adr/0436-products-ship-packages-and-figentra-os-ships-the-shells)
  decision 6), the `surface-<key>` entries switch to it with the same name and port, and nothing else changes for Claude.

## Provider workflows

Each provider is a `workflow_call` workflow in `.github/workflows/`. Its job takes its GitHub environment from an input, so the environment's protection, its OIDC subject and GitHub's deployment record apply to every deploy. Each job decrypts the `figentra/secrets` scopes it needs with the shared `secrets-decrypt` action, signed in to Google Cloud as itself through GitHub OIDC, and takes only the names it uses from each. figentra/infra's `estate/secret-callers.mjs` grants each caller workflow, in its environment, its scopes; a job with no row is refused at the decrypt ([Secrets](/runbooks/secrets#reading-in-ci)).

| Provider                        | Caller here                            | Does                                                                                                                        |
| ------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `runway-cloudflare-workers.yml` | `deploy-static.yml`, `deploy-docs.yml` | refuses a commit that is not on main, tests and builds the member, `wrangler deploy`, smoke test with readiness per attempt |
| `runway-npm.yml`                | `release.yml`                          | Trivy scan of the lockfile, version PR or trusted publish with provenance, a cosign-signed SBOM on each new release         |

npm checks the calling workflow, not the reusable one, so each package's trusted publisher names `release.yml`.

### Calling a provider from another repository

A release of the providers is the tag `runway-v<n>` on a commit of main. Pin the commit, with the tag in a comment, as for every action ([0019](/adr/0019-supply-chain-hardening) D1):

```yaml
jobs:
  deploy:
    permissions:
      contents: read
      id-token: write
    uses: figentra/stackra/.github/workflows/runway-cloudflare-workers.yml@<full-sha> # runway-v1
    with:
      member: workers/edge
      package: "@acme/worker-edge"
      environment: production
      scope: ci/deploy
```

The calling job grants the permissions the provider's job asks for; `id-token: write` is the decrypt's sign-in. The caller workflow needs its row in figentra/infra's `estate/secret-callers.mjs` before its first run. zizmor fails any `uses:` that is not a full SHA.

## The deploy command

`pnpm runway` is the one way to start a deploy, for people and CI alike (STA-268). It never builds or deploys on your machine: it checks the commit and dispatches the same caller workflow a merge runs.

```bash
pnpm runway plan production
```

```bash
pnpm runway deploy cloudflare-workers --dry-run
```

```bash
pnpm runway promote <sha>
```

- `plan [env]` prints, as JSON, each target in build order with its caller workflows, the CI secret names the jobs read and the member secret and var names a deploy syncs. Names only.
- `deploy <target>` needs a clean checkout at the head of `origin/main`; it prints that SHA and dispatches each caller workflow of the target.
- `promote <sha>` needs a commit on `origin/main`; it dispatches every production caller that takes a `sha` input. That is also the rollback: promote the last good release's SHA. A caller with a `message` input (`deploy-static.yml`) gets `rollback to <sha>`, which `wrangler deploy --message` records on Cloudflare beside GitHub's deployment record; the script prints it as `record: rollback to <sha>`. A caller with no `sha` input is listed as skipped.
- `--dry-run` prints the `gh` commands instead of running them. An agent's `deploy` or `promote` without it asks the owner (the guard's `runway-deploy` rule).

## Secrets and vars sync

`pnpm runway secrets sync <env>` is the secret half of this design (STA-606). It prints each member's secret names,
the sops scope that holds them and who writes them, then, in a CI deploy job only, reads every service's values from the
job's environment and writes each into the Encore Cloud environment (`environments.<env>.encore.environment`, else the
runway environment's name) with `encore secret set`, the value on stdin. `--dry-run` prints the names and reads nothing;
outside CI the sync refuses to read. Every value is read before anything is written, and an Encore secret is app-wide,
so two services that name one secret share its one value. A Worker's secrets are set by the Workers provider at deploy, through the same
reader (`readMemberSecrets` in `@stackra/runway/node`, STA-1990). A mobile app's wait for STA-2009, and vars and drift
are not built yet. When the root runway says `secrets.sync: on-deploy`, `stackra deploy --env <env>` runs the same sync
inside its deploy lock before it ships anything, whenever the deploy includes services; a failed sync ships nothing,
and `--dry-run` prints the sync's names with the plan.

1. **Source.** figentra/secrets holds every value as a sops file ([0525](/adr/0525-secrets-sops-and-cloud-kms-replace-infisical)). Member runways name secrets; a product's runtime values for an environment live in the scope `products/<project>/<dev|staging|production>`, where `project` is the root runway's and a preview reads dev's. CI-only names are root `secrets.ci` and never reach a runtime. `providers.infisical` and `secrets.defaultPath` are ignored, and `runway validate` warns until they are removed.
2. **Who reads.** Before the deploy step, the job runs `.github/actions/secrets-decrypt` for its scope. The decrypt is pinned per repository, environment and workflow in figentra/infra, so a staging job cannot decrypt production. The values are masked in the job's environment, and the sync reads them from there.
3. **Plan first.** Before writing, the job prints the names it will write and where (`pnpm runway plan <env>` shows the same list). A name the member declares and the job's environment lacks fails the deploy before anything changes.
4. **Write from stdin only.** A value never appears in argv, a file, `GITHUB_ENV`, an output, an artifact or a log:

   | Runtime            | Secrets                                                 | Vars                                     | Waits for                                                      |
   | ------------------ | ------------------------------------------------------- | ---------------------------------------- | -------------------------------------------------------------- |
   | Encore             | `encore secret set --type <env> <NAME>`, value on stdin | config values through gen, not a sync    | the generated app (STA-59), the deploy path (STA-136)          |
   | Cloudflare Workers | `wrangler secret bulk` with a JSON document on stdin    | `vars` in the generated `wrangler.jsonc` | gen writing the Workers config; no Worker needs a secret today |
   | EAS                | `eas env:create --visibility secret`                    | `eas env:create --visibility plaintext`  | the EAS project (STA-17)                                       |

5. **Vars.** A member's per-environment `vars` are public values. A `ref:<path>` value resolves from the stacks repository's Pulumi config at deploy time ([0171](/adr/0171-infrastructure-as-code-pulumi-typescript-owned-by-stackra)); a `${pr}` value from the build environment.
6. **Drift.** A name in the runtime that no runway declares is reported, never deleted, until a prune rule is decided.

## Resources and workloads

One root runway declares the runtime a product needs beside its services (ADR 0493). A managed resource first; a
container workload only when nothing managed fits, residency forces it, or for on-prem parity, and its `reason` says
which.

```yaml
resources:
  identity-db:
    kind: postgres
    size:
      production: medium
workloads:
  zitadel:
    image: ghcr.io/zitadel/zitadel@sha256:<digest>
    command: [start-from-init, --masterkeyFromEnv, --tlsMode, external]
    port: 8080
    health: /debug/healthz
    expose: public
    uses: [identity-db]
    env:
      ZITADEL_EXTERNALDOMAIN: login.<region>.<product-domain>
      ZITADEL_EXTERNALPORT: "443"
      ZITADEL_EXTERNALSECURE: "true"
    aliases:
      ZITADEL_DATABASE_POSTGRES_DSN: IDENTITY_DB_URL
    secrets: [ZITADEL_MASTERKEY]
    size:
      staging: medium
      production: medium
    scale:
      production:
        min: 2
        max: 4
    reason: "Residency: KSA in-country tenants cannot use ZITADEL Cloud"
environments:
  production:
    limits:
      monthly: 900
```

This is self-hosted ZITADEL (ADR 0206 decision 4 as amended by 0493), planned in dev for about $75 a month and in
staging for about $105. `command` replaces the image's default arguments. `aliases` hands the image a resource
variable under the name it reads: here the database URL as `ZITADEL_DATABASE_POSTGRES_DSN`. An alias may name only a
variable of a Postgres resource the workload uses. `ZITADEL_MASTERKEY` (32 characters, fixed after the first start) goes
into the product's `products/<product>/<env>` scope with `pnpm secrets:put` or `pnpm secrets:generate` before the first
apply.

A service member names what it uses in its own runway (`uses: [main-db]`). The plan prints each item's monthly
estimate; dev ($150) and staging ($500) refuse a plan over their cap, production only warns until it has a `limits`.
Kafka, OpenSearch and SES are reserved kinds. `pulumi preview` shows the change; only the owner applies it.

Postgres runs major 18 (ADR 0238, amendment of 2026-10-31). Before the first apply in each region the environment
deploys to, confirm AWS offers it there:

```bash
aws rds describe-db-engine-versions --engine postgres --engine-version 18 --region me-central-1
```

An empty answer means the region lacks 18: set that environment's resource `version: "17"` for that region only, and
tell the owner.

## Owner steps

Agents cannot do these (STA-605):

1. Restrict the `static` environment to `main` and `schemas@*` tags, and add the required reviewers `runway.yaml` lists for `static`, `registry` and `release` (`figentra-usr` until a second maintainer joins).
2. Create the `docs` environment (main only). figentra/infra's `estate/secret-callers.mjs` already grants the `docs` and `release` callers their scopes.
3. Before the first docs Worker deploy (ADR 0514), remove the docs.stackra.figentra.com CNAME that points at Mintlify, so Cloudflare can attach the `stackra-docs` custom domain; then cancel the Mintlify project.
4. Apply `.github/rulesets/release-tags.json` to the `release-tags` ruleset.
5. After the merge, tag `runway-v1` on the merge commit.
