## The rules

- **Every change to a member ships with a changeset.** `pnpm changeset` records it; `pnpm changeset:status` fails when a changed member has none (target: chained into `pnpm verify`).
- **`CHANGELOG.md` files are generated** by changesets and never hand-edited.
- **Versions are bumped by the release job on `main`**, not on a feature branch. `guard-bash` denies `changeset version` locally for that reason.
- **Merging the version pull request is the release decision.** Claude prepares it; the owner merges it ([0119](/adr/0119-merge-policy-and-release-authority) D7) and approves the `release` environment.
- **One version for everything.** `@stackra/*` is one changesets `fixed` group, and `@stackra-pro/*` releases at the same version (0453 decision 18).
- **Published versions are permanent.** The registry refuses a version that exists and refuses unpublishing; roll forward with a new patch.
- **Only packages are versioned.** Apps and services deploy by commit SHA (`privatePackages: { version: false, tag: false }`, [0025](/adr/0025-packages-publish-to-private-registry) decision 4).
- **Only CI publishes.** No person, laptop or long-lived token can publish; a fix is a new run of the workflow.

## A normal release

<Steps>
  <Step title="Land changesets with the work">
    In each pull request that changes a member: `pnpm changeset`, pick the members, pick the bump
    (patch, minor, major) and write one user-facing line. Commit the generated file under
    `.changeset/`.
  </Step>
  <Step title="Let CI open the version pull request">
    After a push to `main` the release job runs `pnpm changeset:version` (which also refreshes the
    lockfile) and opens or updates one pull request titled `chore(release): version packages`, pushed
    as `stackra-bot` (repository secrets `STACKRA_BOT_APP_ID` and `STACKRA_BOT_PRIVATE_KEY`), so the
    Quality Gate runs on it.
  </Step>
  <Step title="Review it">
    Read the `CHANGELOG.md` diffs and the version bumps. Check the bump matches the change. A major (or,
    before 1.0, a breaking minor) needs its human release note first ([0013](/adr/0013-versioning-and-release)
    decision 5).
  </Step>
  <Step title="Merge it and approve the run">
    The merge to `main` starts the release job, which waits in the `release` environment until the
    owner approves it.
  </Step>
  <Step title="The job publishes">
    1. Trivy scans the lockfile; a critical vulnerability with a released fix stops the run ([0174](/adr/0174-supply-chain-images-signing-sbom-dependency-policy-and-rotation)).
    2. It installs and builds what `build-args` selects.
    3. For each package with `"private": false` whose version is not on the registry yet, it asks GitHub
       for an ID token with audience `npm:npm.stackra.figentra.com`, exchanges it at
       `/-/npm/v1/oidc/token/exchange/package/<name>` for a publish token bound to that one name
       (15 minutes by default), and runs `pnpm publish --provenance` with it as `NODE_AUTH_TOKEN`.
    4. The registry matches the token's repository (by numeric id too), workflow `release.yml`, ref
       `refs/heads/main` and environment `release` against the scope's publisher row, then checks the
       publish (below), stores the tarball and its provenance bundle, and signs the version.
    5. The job tags `<name>@<version>`; changesets pushes the tags and creates the GitHub releases.
    6. The `sbom` job writes a CycloneDX SBOM, signs it keylessly with cosign and attaches it to every
       new release.
  </Step>
  <Step title="Verify">
    `git ls-remote --tags origin` shows the new tags on the merge commit. In a clean folder with the
    `@stackra` scope mapped, `npm view @stackra/<name> versions --registry https://npm.stackra.figentra.com/`
    lists the version and `npm audit signatures` passes.
  </Step>
</Steps>

## What the registry refuses at publish

From 0453 decision 7 and `workers/registry/README.md`: a version that already exists; a tarball over 50 MiB (the
`registry.maxTarballBytes` default); a `package.json` name or version that differs from the request; an unknown
`stackra.kind`; a licence that does not fit the scope (`@stackra-pro` must carry the commercial licence and no `src`
or `.map`; `@stackra` must be MIT, or an open licence with a `NOTICE`); integrity or shasum that differs from what the
registry computes; and a missing provenance bundle, or one for another digest or another workflow. Every publish,
tag change, deprecation and token exchange is an audit row naming the workflow run.

## Dispatch runs

Actions → "Release" → Run workflow on `main`:

| Input        | Does                                                                                                                                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dry_run`    | packs every published package through the `.pnpmfile.mjs` hook and runs `pnpm -r publish --dry-run`; nothing leaves the runner                                                                                                        |
| `prerelease` | publishes only `packages` (default: the five `*-config` presets) at `<base_version>-<dist_tag>.<run number>` under `dist_tag` (default `next`, never `latest`); the version is set on the runner only, nothing is committed or tagged |

A prerelease waits for the same approval and publishes through the same OIDC exchange. A re-run skips versions that
are already there.

## Before the first release (once, by the owner)

- The registry is deployed and its D1 migrations seeded the `publishers` rows (`workers/registry/README.md`, owner
  runbook). Nothing is registered per package: the publisher row covers the whole scope.
- The `release` GitHub environment exists, is restricted to `main` and has a required reviewer, so a branch that edits
  the workflow cannot obtain a token.
- Branch protection on `main` requires the `Quality Gate` check ([CI](/runbooks/ci)).
- A tag ruleset on the version tag pattern blocks deletion and non-fast-forward updates.
- The `stackra-bot` App secrets above exist.

There is no npm account, no `npm trust`, no npm token and no manual first publish: a new package publishes on its
first release run like any other.

## When something fails

Re-run only the failed jobs of the same run unless a row says otherwise.

| Failed step                      | State                      | Do                                                                                                                    |
| -------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Version pull request not opened  | Nothing released           | Check the App secrets and the host setting for pull requests from workflows, then push any commit to `main` or re-run |
| Trivy                            | Nothing released           | Update the vulnerable dependency on `main`; the next run retries                                                      |
| OIDC exchange answers 401 or 403 | Nothing for that package   | The publisher row does not match: check the run is `release.yml` on `refs/heads/main` in the `release` environment    |
| Publish refused (400 or 422)     | Earlier packages published | Read the registry's message (decision 7 above), fix on `main`, release again; published versions stay                 |
| Run stopped half way             | Some packages published    | Re-run: versions already on the registry are skipped                                                                  |
| Tagging                          | Published, not tagged      | Re-run the failed job; it tags over an existing release safely                                                        |
| SBOM job                         | Published, no SBOM         | Re-run the `sbom` job                                                                                                 |
| Wrong bump merged                | Tagged                     | Roll forward: add a changeset and release the correction                                                              |

## Revert

- **Before merging:** close the version pull request. The next push recreates it from the remaining changesets.
- **After publishing:** roll forward with a fixed patch. Deprecating a version or moving `latest` back needs a
  publish token, which only the release workflow can obtain; no workflow does either yet, so until one exists the
  patch is the remedy.
- **A bad release record on GitHub:** mark it a prerelease or delete the release page; leave the tag.
- **The workflow itself:** revert the workflow file on `main`; nothing else depends on it.
