This page names secrets and steps. It never holds a value, and neither may a file, a test, a fixture, a log, a comment, a commit, a chat message or an agent prompt. The law is [Constitution: secrets](/constitution/secrets) and the decision is [ADR-0525](/adr/0525-secrets-sops-and-cloud-kms-replace-infisical).

## The idea

Every secret is one small encrypted file in the private repository `figentra/secrets`. Google Cloud KMS holds the keys, one key per area, called a **scope**. The owner's offline `age` key can also decrypt every file: that is the break-glass door. A GitHub Actions job proves who it is to Google Cloud with its OIDC token, so no password is stored, and only the jobs figentra/infra lists may decrypt a scope. Nobody reads a value: not the owner in chat, not an agent, not a log.

## The layout

```
figentra/secrets (private)
├── .sops.yaml        which key encrypts which scope
├── catalog.yaml      names only: owner, purpose, kind, rotation, expiry
├── agents/<NAME>.enc.yaml
├── ci/{build,deploy,production,flow,infra}[/<folder>…]/<NAME>.enc.yaml
└── products/<product>/{dev,staging,production}/<NAME>.enc.yaml
```

| Piece        | What it is                                                                                                                                                                      | Where                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| Scope        | A folder of secrets for one area: `agents`, `ci/<build\|deploy\|production\|flow\|infra>[/<folder>]` or `products/<product>/<dev\|staging\|production>`                         | `figentra/secrets`                           |
| Secret file  | `<scope>/<NAME>.enc.yaml`, one file per secret, each with its own data key, so a writer never needs to decrypt anything                                                         | `figentra/secrets`                           |
| Catalog      | `catalog.yaml`: each name with its scopes, `owner`, `purpose`, `kind`, `rotateDays` and, for a human value, `expires`                                                           | `figentra/secrets`                           |
| KMS keys     | One per scope, in key ring `figentra-secrets` of project `figentra-tools`, with automatic rotation                                                                              | Google Cloud, created by figentra/infra      |
| Break-glass  | The owner's `age` key pair from `pnpm secrets:age-init`: the public half in `.sops.yaml`, the private half in the owner's password manager                                      | the owner                                    |
| Who decrypts | `estate/secret-callers.mjs`: one row per repository, GitHub environment and workflow, with its scopes                                                                           | figentra/infra                               |
| CI copy      | On every push to main, `sync.yml` copies the ciphertext to `gs://figentra-secrets-ciphertext/`, one flat prefix per scope (`ci/production/release` is `ci.production.release/`) | Google Cloud                                 |
| CI reader    | The shared action `secrets-decrypt`, which runs `runway secrets decrypt`                                                                                                        | core `.github/actions/secrets-decrypt`       |
| Runtime sync | `runway secrets sync <env>`, run by the deploy job                                                                                                                              | `@stackra/runway`                            |
| Reminders    | `reminders.yml`, once a day                                                                                                                                                     | `figentra/secrets`, issues in figentra/infra |

Names are `SCREAMING_SNAKE` as `<PROVIDER>_<PURPOSE>` (`CONTEXT7_API_KEY`, `CLOUDFLARE_API_TOKEN`). A name is its file name, so listing names needs no key. Never a customer name, never a value-shaped string.

There is no `.env`, no `.env.example` and no second store. A name lives in git; its value lives only in `figentra/secrets` and in the runtime stores the sync writes.

## Three kinds of value

`catalog.yaml` gives each name a `kind`:

| Kind        | Examples                                         | How it gets in                                                                                                |
| ----------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `generated` | webhook secrets, signing keys, data keys         | `pnpm secrets:generate`. No human; an agent may run it.                                                       |
| `minted`    | Cloudflare scoped tokens, Stripe restricted keys | figentra/infra mints them from one parent credential and writes them the same way. No human after the parent. |
| `human`     | a provider key only a person can get             | The agent asks; the owner runs `pnpm secrets:put`. The agent sees names only.                                 |

## Putting a value in

Run these in a checkout of `figentra/stackra` on main. Each one encrypts the value in memory, hands it to `sops` on stdin, and opens a pull request in `figentra/secrets` that merges itself. None prints a value, logs it or puts it on argv. A writer holds only KMS Encrypter, so it never sees any other value.

<Steps>
  <Step title="A value a person has (kind human)">
    The agent asks in chat: "run `pnpm secrets:put NAME --scope S`", with the purpose and where to
    get the value. The owner runs it. It reads `~/Secrets-inbox/<NAME>[.ext]` if that file exists
    (and deletes it on success), or else asks for the value on a hidden prompt. A multi-line value,
    such as a PEM key, goes through the inbox file.
  </Step>
  <Step title="A random value (kind generated)">
    `pnpm secrets:generate NAME --scope S` makes the value with `node:crypto` (`--bytes 16..128`,
    default 32; `--encoding base64url|hex`). An existing name is refused. `pnpm secrets:generate
    --missing [--dry-run]` makes every `kind: generated` catalog name that has no file yet, in one
    pull request; a catalog `generator: vapid` makes a Web Push key pair, and `generator: ed25519` a
    signing key whose public half and key id are the only things printed.
  </Step>
  <Step title="Rotate a generated value">
    `pnpm secrets:rotate NAME --scope S` (that is `secrets:generate --rotate`) replaces the existing
    value.
  </Step>
  <Step title="Several files at once (the inbox)">
    `pnpm secrets:import --scope S [FILE…]` takes files directly in `~/Secrets-inbox/`;
    `pnpm secrets:import --tree` takes files in scope-shaped folders under it
    (`agents/`, `ci/deploy/`, `products/<product>/<env>/`). `--list` prints the inbox file names and
    `--dry-run` checks names and scopes and writes nothing. All files go in one pull request; each
    inbox file is deleted once the pull request is open, and kept on a refusal.
  </Step>
</Steps>

The inbox file name is the secret name, one extension stripped: `STACKRA_REVIEWER_PRIVATE_KEY.pem` becomes `STACKRA_REVIEWER_PRIVATE_KEY`. A short value such as an App ID is a file holding just that value. Files must be regular files of at most 64 KB. Every write appends a names-only line to `~/.stackra/secrets-audit.log`.

An agent never writes the gate, registry or infra scopes (`ci/flow`, `ci/infra` and any `registry` folder): the scripts refuse, and the owner runs those. Only the owner runs `pnpm secrets:age-init`.

No agent reads, lists, copies or moves anything in `~/Secrets-inbox/`. `guard-bash` and `guard-paths` refuse the obvious attempts. They are an **accident guard, not a security boundary**: the scripts are written so that no caller can get a value out of them.

### Keeping the catalog

`pnpm secrets:catalog` reads a clone of `figentra/secrets` (`--repo`, default `$STACKRA_SECRETS_DIR` or `~/.stackra/secrets`) and rewrites `catalog.yaml`: `scopes` comes from the files, and the other fields you wrote are kept. `pnpm secrets:catalog --check [runway.yaml…]` prints one problem per name: a missing field, a file the catalog lacks, or a name a `runway.yaml` declares with no file. It never decrypts, so it needs no key. Open a pull request in `figentra/secrets` with the change.

## Reading in CI

A job decrypts its own scope in place with the shared action. It needs `permissions: id-token: write` and mise on `PATH` (`jdx/mise-action`).

```yaml
permissions:
  contents: read
  id-token: write
steps:
  - uses: figentra/stackra/.github/actions/secrets-decrypt@<full-sha> # @stackra/runway@<version>
    with:
      scope: ci/deploy
      names: CLOUDFLARE_API_TOKEN
```

The action signs in to Google Cloud as the job itself (Workload Identity, no service account key), copies the scope's ciphertext from the bucket and runs `runway secrets decrypt`. That command decrypts each file with Cloud KMS in memory and exports the values, masked, into the job's environment for the steps after it. It prints names and a count, never a value. `names` limits it to those names; empty means the whole scope. The ciphertext and the credentials file are removed right after.

**The caller grant.** A job decrypts a scope only when figentra/infra's `estate/secret-callers.mjs` has a row for its repository, GitHub environment and workflow file that lists that scope (main only, outside `ci/build`). A staging job cannot decrypt production. For a new workflow or a new scope, open a pull request in figentra/infra that adds the row; the policy gate refuses any other binding. Two exceptions: every figentra repository reads `ci/build/registry`, and figentra/infra's own GitHub App key stays a GitHub secret, because figentra/infra creates the grants and cannot depend on them.

What CI may never do: print a value or its length, write one to `GITHUB_ENV` by hand, an output, an artifact or a cache, or run `printenv`, a bare `env` or `sops -d`. The `verify` stage and every test need no secret at all.

## Reading on a workstation

On a workstation only the `agents` scope is read, and only the owner's Google login can decrypt it. A token reaches a process only through the pnpm script that needs it:

| Script                                                                               | Names                                                                                          |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `pnpm linear`, `pnpm spec:linear`                                                    | `LINEAR_AGENT_TOKEN`, `LINEAR_AGENT_CLIENT_ID`, `LINEAR_AGENT_CLIENT_SECRET`, `LINEAR_API_KEY` |
| `pnpm bot:gh`, `pnpm bot:git`, `pnpm bot:token`, `pnpm pr:merge`, `pnpm adr:reserve` | `STACKRA_BOT_APP_ID`, `STACKRA_BOT_INSTALLATION_ID`, `STACKRA_BOT_PRIVATE_KEY`                 |

Each runs `node tools/scripts/secrets-exec.mjs --names A,B -- <command>`. It fast-forwards the local clone (`$STACKRA_SECRETS_DIR`, default `~/.stackra/secrets`), decrypts only the listed `agents/<NAME>.enc.yaml` files in memory, and puts them in the child's environment only. A listed name with no file is skipped, so a command that takes one of several credentials gets whichever exists. A new flow that needs a token gets its own pnpm script that names its secrets. An agent never runs `secrets-exec.mjs` or `sops` itself: either would hand a value to a command the agent chose.

### How `mcp.sh` works

`.mcp.yaml` passes a secret to an MCP server as a bare `$NAME` argument, for example `"--api-key", "$CONTEXT7_API_KEY"`. Use the bare form, not `${NAME}`: Claude Code expands the braced form itself and silently disables the server when the variable is unset. `tools/scripts/mcp.sh` runs `secrets-exec.mjs --expand-args` with only the names the arguments reference and the names a server reads from its environment, and expands them inside the server's own process. A server that needs no token starts unchanged.

There is no `.env` fallback on purpose: a second source is a second place a token goes stale, and the failure it causes is the quiet kind.

## The runtime sync

A product's runtime values for an environment live in `products/<product>/<dev|staging|production>`. The deploy job decrypts that scope with the action, then runs `runway secrets sync <env>`:

- It prints each member's secret names, the scope and who writes them.
- It reads every value from the job's environment before it writes anything, so a missing name fails the sync with nothing changed.
- It writes each service secret into the Encore environment with `encore secret set`, the value on stdin.
- A Worker's secrets are set by the Workers provider at deploy. A mobile app's wait for STA-2009.
- It writes only in a CI job its GitHub OIDC token proves. `--dry-run` prints the names and writers anywhere, and reads nothing.

`runway env check` checks names: every environment name in the code is declared and has a sops scope. It needs no login, and the Quality Gate runs it on every pull request. `runway env check --values --env <env>` checks values in a deploy job after the decrypt, and prints at most a SHA-256 prefix, never a value. Details: [Runway](/runbooks/runway#secrets-and-vars-sync).

Nobody sets a runtime value by hand (`encore secret set`, `wrangler secret put`, `eas env:create`): the sync is the one writer to each runtime store. To change a value, put the new one in `figentra/secrets` and redeploy.

## Reminders

Once a day, `reminders.yml` in `figentra/secrets` reads `catalog.yaml` and the git history of the files, and opens an issue in figentra/infra:

- `secrets-expiry`: a human secret that expires within 30 days. The issue gives the `pnpm secrets:put NAME --scope S` command for each scope.
- `secrets-rotation`: a generated secret older than its `rotateDays`. The issue gives the `pnpm secrets:rotate NAME --scope S` command.

An issue already open under the same title is not opened again. The job has no Google identity and reads no ciphertext. A name the catalog does not list gets no reminder.

## Checking without seeing a value

| Question                             | Command                                                                                                            | Needs        |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------ | ------------ |
| Which secrets exist?                 | `gh api 'repos/figentra/secrets/git/trees/main?recursive=1' --jq '.tree[].path \| select(endswith(".enc.yaml"))'`  | GitHub       |
| Does one exist?                      | `gh api repos/figentra/secrets/contents/products/pay/staging/<NAME>.enc.yaml --jq .path` (404 means no)            | GitHub       |
| What is it for, who owns it?         | `gh api repos/figentra/secrets/contents/catalog.yaml -H 'Accept: application/vnd.github.raw'`                      | GitHub       |
| Who may decrypt a scope (as written) | search figentra/infra `estate/secret-callers.mjs` for the scope                                                    | GitHub       |
| Who may decrypt (live)               | `gcloud kms keys get-iam-policy pay-staging --keyring figentra-secrets --location global --project figentra-tools` | Google Cloud |
| Keys and rotation                    | `gcloud kms keys list --keyring figentra-secrets --location global --project figentra-tools`                       | Google Cloud |
| Open reminders                       | `gh issue list -R figentra/infra --label secrets-expiry --state all`                                               | GitHub       |
| Did the sync and reminders run?      | `gh run list -R figentra/secrets -L 10`                                                                            | GitHub       |
| Is the catalog complete?             | `pnpm secrets:catalog --check`                                                                                     | a clone      |

Never run `sops -d` on these files, not even with the owner's login.

## Rotation

Overlap, never revoke-first:

<Steps>
  <Step title="Create the new value">
    For a generated value, `pnpm secrets:rotate NAME --scope S` does this and the next step. For a
    human value, create a second token, key or client secret at the vendor, with the same minimum
    scope.
  </Step>
  <Step title="Put it in figentra/secrets">
    The owner runs `pnpm secrets:put NAME --scope S` for each scope the catalog lists. The pull
    request that merges is the record.
  </Step>
  <Step title="Let the consumer pick it up">
    A CI job reads the new value on its next run. A runtime gets it on the next deploy, whose sync
    writes it. A running service does not see a new value on its own.
  </Step>
  <Step title="Prove it works">
    One real call that uses the new value (`whoami`, a read-only API call, one test email). Confirm
    by metadata, never by printing the value.
  </Step>
  <Step title="Revoke the old value at the vendor">
    Only now. Where a vendor cannot hold two values, declare the single-value window before you
    start and keep it as short as the roll allows.
  </Step>
</Steps>

`catalog.yaml` holds each name's `rotateDays` and, for a human value, `expires`; the reminders read them. The usual periods:

| Token                                                        | Scope                                                 | Period                                                    |
| ------------------------------------------------------------ | ----------------------------------------------------- | --------------------------------------------------------- |
| Cloud-provider and hosting API tokens                        | `ci/deploy`, `ci/production`                          | 180 days, or on exposure                                  |
| `EXPO_TOKEN` (robot token)                                   | `ci/deploy`, `ci/deploy/store`, `ci/production/store` | 365 days                                                  |
| Registry read tokens                                         | `ci/build/registry`                                   | 365 days                                                  |
| MCP and developer tokens                                     | `agents`                                              | 365 days                                                  |
| Apple App Store Connect key, Google Play service-account key | `ci/deploy/store`, `ci/production/store`              | On exposure or personnel change; the `.p8` downloads once |
| Application secrets (Stripe, OAuth, webhook signing, Resend) | `products/<product>/<env>`                            | On exposure; Stripe offers a roll with an expiry window   |

## A value was exposed

Old values stay in the git history of `figentra/secrets`, encrypted. A leak means rotation, not deletion. See also [Token rotation after exposure](/runbooks/token-rotation).

<Steps>
  <Step title="Revoke at the vendor first">
    The leaked value stays valid until the vendor revokes it. Rewriting git history does not un-leak
    it.
  </Step>
  <Step title="Rotate">
    Follow the rotation steps above: `pnpm secrets:rotate` for a generated value, `pnpm secrets:put`
    for a human one.
  </Step>
  <Step title="Purge">Delete the CI run logs, artifacts and any cache key that held it.</Step>
  <Step title="Record and close the gap">
    Open a finding against the step that leaked it. Add the pattern to `guard-bash` and
    `.gitleaks.toml`.
  </Step>
</Steps>
