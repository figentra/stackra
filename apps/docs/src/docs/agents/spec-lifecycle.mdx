Not every change needs a spec. Work that touches money, permissions, data integrity, external contracts, concurrency or state machines does, and so does anything several agents will implement or that will outlive its author's memory. Everything else is a direct change reviewed at the gates on [Working with agents](/agents).

The spec engine is Figentra Flow (`@figentra-oss/flow`, binary `fflow`, [ADR 0510](/adr/0510-flow-replaces-spec-kit)), pinned through the pnpm catalog like any other dependency. It ships the templates, the `stackra` preset (chosen with `preset` in `fflow.config.json`) and the eight command texts, and does the work spec-kit's bash scripts used to do as subcommands (`fflow spec paths|setup-plan|setup-tasks|template`); nothing runs the `specify` binary. `pnpm spec:sync` (`fflow sync`) renders the `flow-*` skills into `.agents/skills/`, which `pnpm agents:sync` projects into `.claude/skills/` (OpenCode reads `.agents/skills/` directly), and records a hash of every rendered file in `.flow/lock.json`. Tasks become Linear sub-issues inside `/flow-tasks` (through `pnpm spec:linear`), and the constitution is generated by `pnpm agents:sync`, so there is no separate command for either. A repository-specific template or command goes in `.flow/overrides/`. A change that is not specified starts at `/flow-specify`: the prompt-hints hook nudges an ad-hoc feature request there.

## Where specs live

Every spec lives in `.agents/specs/sta-<n>-<slug>/`, named by its Linear issue ([ADR 0120](/adr/0120-sdlc-spec-location-lanes-and-change-risk) D1). Each command first runs `pnpm spec:gate dir` (`fflow gate dir`), which reads the STA key from the branch name (`figentra/sta-<n>-…`, or `--key STA-n`), prints the folder and writes the git-ignored `.flow/current.json`, which every `fflow spec` call reads. `/flow-specify` adds `--slug <short-name>` to name a new folder. Nothing auto-numbers. Root `specs/` is not used, and `fflow gate ci` fails a change that adds to it.

`fflow gate ci` also runs the install check: it fails when a rendered skill or command differs from `.flow/lock.json`, when the lock names another Flow version than the installed one, or when `.specify/`, `.agents/speckit/` or a `speckit-*` file remains. Upgrade Flow only in a dedicated pull request: bump the catalog entry, run `pnpm spec:sync`, then `pnpm validate`. A repository still on spec-kit moves over with `fflow migrate [--dry-run]`.

Specs are public on GitHub and are not published here (D17). They never hold secrets, customer data or details of an unfixed vulnerability.

## Tiers

Every change takes one of four tiers ([ADR 0502](/adr/0502-spec-tiers-and-approval-stops)), declared as `**Tier**:` in the
spec header:

- **trivial**: a typo, format, lint, docs wording, test-only fix, approved version bump or obvious one-line bug. No spec: the
  commit message and the Linear issue. Nothing blocks it.
- **small**: a bug or small change in one package with no contract, data or permission change. A lite spec, 5 to 10
  answered questions, with a short `## Design` and `## Tasks` in the same file. No stop.
- **feature**: new behaviour, a contract or API, a migration, permissions, money, security or personal data, or more than
  one package. Spec, plan.md, tasks.md; one approval stop after the spec and plan.
- **big**: a new service, module or product, a new ADR, brand or pricing. Questionnaire, ADR, spec, plan, tasks; stops
  after the spec and after the plan.

The lane check computes a floor from the diff and refuses a lower declared tier. An approval is `Approved by <who>
<YYYY-MM-DD>` on the Status line of the stage it approves, asked for with the question tool (Approve, Revise with notes,
Reject); `**Approver**` names the owner (product, money, legal, security, brand, pricing) or the leader (technical-only
stops).

## The flow

```text
/flow-specify ──▶ /flow-clarify ──▶ /flow-plan ──▶ /flow-tasks ──▶ /flow-implement
 spec.md + Impact   marks "complete"   gate runs first  tasks → Linear
```

| Command                            | Writes                               | Stackra rule                                                         |
| ---------------------------------- | ------------------------------------ | -------------------------------------------------------------------- |
| `/flow-specify`                    | `.agents/specs/sta-n-<slug>/spec.md` | Interviews the **Impact** questionnaire. Never plans                 |
| `/flow-clarify`                    | Answers in `spec.md`                 | Sets `**Clarifications status**: complete` only when nothing is open |
| `/flow-plan`                       | `plan.md`, research, contracts       | **Refuses** until the spec gate passes                               |
| `/flow-tasks`                      | `tasks.md`                           | Tasks become Linear sub-issues of the spec's issue                   |
| `/flow-analyze`, `/flow-checklist` | reports                              | Optional                                                             |
| `/flow-implement`                  | code                                 | Executes `tasks.md`                                                  |
| `/flow-converge`                   | spec, plan and tasks                 | Converges the three documents; appends a task, never deletes code    |

## The clarify-before-build gate

Every `spec.md` carries three things the template provides:

- `**Linear**: STA-n`, the issue for the spec (team STA). Optionally `**Linear project**`.
- `**Clarifications status**: pending | complete`, and `**Status**`: Draft, Clarified, Planned, Tasked, Implementing, Done, or Abandoned / Superseded (owner decision OR12). Each change appends a line to `## Status history`; an amendment appends to `## Amendments` and never renumbers an ID.
- An `## Impact` questionnaire, every line answered (`none` is an answer): apps, services and packages touched, cross-service events, tenancy and data, secrets (names, never values), whether an ADR is needed, new dependencies, deploy modes (what differs in SaaS, on-prem and air-gapped), the lane (full, lite, bug or chore) and the change risk (R0 to R3), both from [ADR 0120](/adr/0120-sdlc-spec-location-lanes-and-change-risk).

`fflow gate plan` passes only when the status is `complete`, a real `STA-n` is set, every Impact line is answered and no `[NEEDS CLARIFICATION` marker remains. It is enforced twice:

1. **Locally.** `fflow spec setup-plan` runs it first, so `/flow-plan` fails before it writes anything.
2. **In CI.** `pnpm validate` runs `fflow gate ci` and `fflow trace ci` over every `.agents/specs/<folder>/` changed since `origin/main`, at the stage its `**Status**` claims. A status may lag behind the artifacts but never run ahead of them.

| Status       | `spec-gate check` requires                                                                                                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Draft        | A `sta-<n>-<slug>` folder and, once set, a `**Linear**` key equal to the folder's                                                                                                                                              |
| Clarified    | The plan rules above, and a Status history line for the status                                                                                                                                                                 |
| Planned      | `plan.md`: every Constitution Check row PASS or N/A with a reason, SaaS, on-prem and air-gapped rows, every FR validated by a `P-###` or `example-only`                                                                        |
| Tasked       | `tasks.md` passes `spec-gate tasks`: unique ids, `covers:` naming defined IDs, a `route:` from `.agents/routing.yaml`, acyclic `deps:`, every FR covered, no path shared by two `[P]` tasks of a phase                         |
| Implementing | At least one task ticked; `spec-trace drift`: every member the diff changes is named in Impact, and ticked tasks' paths exist                                                                                                  |
| Done         | Every task ticked or struck; every FR and `P-###` covered by a test tagged `@covers sta-<n>:FR-###` (an FR may be covered through a tested P); every SC names its verification method; Impact's "Docs to update" pages touched |

`spec-gate ci` also checks the lane (a `feat` commit needs a spec reached through the branch key or its `Refs:` keys), the bug lane (`.agents/specs/bugs/sta-<n>-<slug>/` with a regression test tagged `@covers sta-<n>:BUG`) but not the branch name: `pnpm linear check-pr` owns that, with its `chore-lane` label escape, and the pre-push `spec-gate branch` only warns. A ready-for-review PR (`SPEC_GATE_REQUIRE_READY=1`) needs its own spec (the folder keyed by the branch's STA key) at Tasked or later, so a spec PR stays a draft until then; an edit to another spec only has to pass `check`. `pnpm spec:trace trace <dir>` prints the FR → task → test matrix.

Answers that raise an ADR go to `docs-adr-steward`; a new dependency goes through the catalog (`dependency-steward`).

## Linear

**Work isn't done until its Linear issue is in the right state; agents use `pnpm linear`.** That includes subagents and OpenCode executors that have no Linear MCP.

| Moment        | Command                                                           | Issue state                   |
| ------------- | ----------------------------------------------------------------- | ----------------------------- |
| Start         | `pnpm linear start STA-n`                                         | In Progress, branch commented |
| PR opened     | `pnpm linear review STA-n <pr-url>`                               | In Review, PR attached        |
| Merged        | `pnpm linear done STA-n <link>` (or `Fixes STA-n` in the PR)      | Done                          |
| Anything else | `pnpm linear comment STA-n "…"`, `link`, `create`, `mine`, `open` | unchanged                     |

`pnpm linear` runs `tools/scripts/linear.mjs` under `tools/scripts/secrets-exec.mjs` (the sops `agents` scope). It acts as the **Stackra Agent** Linear app, which becomes the issue's _delegate_, never its assignee. The token is `LINEAR_AGENT_TOKEN`, re-minted from `LINEAR_AGENT_CLIENT_ID`/`LINEAR_AGENT_CLIENT_SECRET` when it expires. The personal `LINEAR_API_KEY` is the fallback. `create` adds the `agent` label when an agent runs it.

Stage transitions report themselves. `fflow gate plan` comments "clarified" on the spec's issue when it passes. `fflow gate stage <spec.md> planned|tasked|implementing|done` comments the later stages, and `implementing` also moves the issue to In Progress. `pnpm delegate` requires `--issue STA-n`: it starts the issue at dispatch and comments the result. None of these calls can fail a gate. Linear sync never blocks (ADR 0065 rule 7), and `STACKRA_LINEAR=off` turns them off.

Keys are enforced offline. A `feat`, `fix`, `refactor` or `perf` commit needs a `Refs: STA-n` footer, checked by commitlint in lefthook and over the PR range in CI. The Quality Gate also fails a PR whose title and branch both lack an STA key, unless it is labelled `chore-lane` or comes from `renovate/*` or `changeset-release/*`.

The **Linear sync** workflow (`.github/workflows/linear-sync.yml`, nightly and on push to main) runs `figentra linear reconcile` (`@figentra/cli`). It moves an issue to In Review when an open PR mentions it (in the title, the branch, `Refs`/`Fixes`, or an attachment). It moves an issue to Done only when a merged PR closes it, through the branch name or `Fixes`/`Closes`/`Resolves`. A `Refs` mention never closes an issue, so an issue that spans several PRs stays open. Fork PRs are ignored. It closes "Decide ADR NNNN" once that ADR is Accepted or Superseded. It labels In Progress issues `stale` after 3 days without branch or PR activity, and comments on Backlog issues whose ADR is now Accepted. Each comment carries a `linear-reconcile (<tag>)` marker, so a re-run, or a human reopening an issue, is never overridden. `--dry-run` writes nothing.

`pnpm spec:linear issue <spec.md>` creates the spec's issue and writes the key into `spec.md`. `pnpm spec:linear tasks <tasks.md>` creates one sub-issue per `T###` task and appends ` [STA-n]` to the line. Both take `--dry-run` (no token, no calls) and use the same tokens as `pnpm linear`, which `pnpm spec:linear` reads from the sops `agents` scope itself. No token is ever stored in a file.

## The constitution

`.flow/constitution.md` is **generated** from [the laws](/constitution) in `apps/docs/src/docs/constitution/*.mdx` by `stackra constitution`. Edit the laws, run `stackra constitution`, and `pnpm validate` fails on drift. Never edit the generated file.

## Review checklist

A spec passes review when every row is **PASS** or **N/A with a reason**. Reviewers check against the real tree, not the prose.

1. **Decisions honoured.** Each applicable law and ADR is cited where the plan honours it. See [Constitution](/constitution/boundaries) and [Architecture decisions](/adr).
2. **Cross-package consistency.** Every symbol the plan imports exists in that package's current barrel. Dependency direction has no cycle. Events a package emits are listed once, and ones it consumes exist in the owner.
3. **Hygiene.** Every requirement is covered by a task. No `TBD`, `later`, `for now`, `temporary` or `stub`. The plan has no open question at approval.
4. **Impact is true.** The Impact answers match the files the plan actually touches.

`/flow-analyze` is the mechanical half: it cross-checks spec, plan and tasks. It does not judge whether the requirements were the right ones. That is what the human gate is for.

## When a finding becomes a rule

The `failure-loop` skill handles a gate failing in front of you: classify it, route it to the owner, fix the cause, re-run. For most findings that is the end. For some it is not. A finding about the repository rather than the diff will recur on the next spec, raised by a different reviewer, unless something changes.

A finding is **durable** when any one of three holds:

1. It has been raised before. The second occurrence, not the third.
2. A check could have caught it, and none exists. This is the highest-value trigger.
3. It touches an area where the first occurrence is already too many: secrets, generated artefacts, the CI gate, tier and layer boundaries, a published export surface.

Anything else is one-off. Fix it in the change and write nothing. Promoting a one-off is a real cost, because every rule is read by every agent in every session.

| What was missing                                 | Where it goes                           | Who writes it            |
| ------------------------------------------------ | --------------------------------------- | ------------------------ |
| A decision                                       | An ADR                                  | `architecture-guardian`  |
| Enforcement: a decision exists and nothing fails | A check wired into `pnpm verify` and CI | `release-operations`     |
| Awareness: only a human reading can enforce it   | A rule in `.agents/rules/`              | the lead                 |
| A procedure someone re-derived                   | A skill in `.agents/skills/`            | the lead                 |
| A behaviour the spec never specified             | An amendment to the spec's `spec.md`    | the lead                 |
| Coverage: right code, nothing would have noticed | A test at the level that catches it     | `test-engineer`          |
| A version, advisory or pin                       | A catalog entry                         | `dependency-steward`     |
| A layout mistake that repeats per package        | A scaffold template change              | `code-standards-steward` |

**Enforcement beats awareness.** If a finding can be stated as a predicate over files, write the check, not a rule asking agents to remember. **A decision and its enforcement are two artifacts.** An ADR that no check enforces is a standard that only a tired reviewer stands behind, so the ADR ships with its check or names the check and its owner in its follow-up.

The reviewer who raised the finding names the class and the destination. The owning agent writes the artifact. A reviewer who must also write the rule quietly stops raising findings.

Every artifact written by a promotion opens with one provenance line:

```markdown
> Origin: review finding on <spec or change>, <first|second> occurrence — <the finding>.
```

Nothing checks for that line, and there is no findings ledger. A ledger would be a tracked file that goes stale the first week nobody updates it. The line makes existing rules searchable for "has this been seen before", and a rule whose origin nobody can state is a candidate for deletion. A reviewer enforces it, and that limit is stated on purpose.

## Tasks that are not specs

A spec is for work worth specifying. Other work is a Linear issue on a Linear-named branch, in the bug or chore lane of [ADR 0120](/adr/0120-sdlc-spec-location-lanes-and-change-risk). A task is done only when its code is on the main branch.
