This guide makes help-centre articles searchable: every word of a phrase must match, case and accents do not matter, a
category narrows the result, and a draft is never found. The code is copied from `apps/docs/scripts/guides/search`,
which the docs site's tests run.

Search in Stackra runs in Postgres (full-text, trigram and, if you opt in, vector lanes, fused by rank). The index lives
in the model's own table, so a search runs in the caller's transaction under the same row-level security as every
other read: a tenant only ever finds its own rows. The service depends on `@stackra/search`.

## 1. Declare what is searchable

```ts src/modules/help/models/article.model.ts
import { HasPublicId, Model, Searchable, Timestamps } from "@stackra/model";
import { Str } from "@stackra/validation";

/** A help-centre article; only a published one can be found. */
@Searchable({
  text: ["title", "body"],
  filters: ["category"],
  when: { status: ["published"] },
})
export class Article extends Model.with(HasPublicId("art"), Timestamps) {
  /** The headline; its words weigh most, being the first text field. */
  @Str({ max: 200 })
  title!: string;

  /** The article itself. */
  @Str({ max: 20_000 })
  body!: string;

  /** Where it is filed (`billing`, `account`). */
  @Str({ max: 40 })
  category!: string;

  /** `draft` until it is published. */
  status = "draft";
}
```

- `text` lists the fields whose words are searched, heaviest first (`boost` sets a weight explicitly). A dotted path
  such as `variants.sku` reaches a related model.
- `filters` lists the fields a search may filter on exactly; a list of values matches any of them.
- `sortable` and `ranges` (not used here) name number or date fields a search may sort by or bound.
- `when` keeps rows out of the index unless the field holds one of the values.

## 2. Add the search columns

```ts src/modules/help/database/migrations/0001-create-articles.migration.ts
import { type Blueprint, Migration, type SchemaBuilder } from "@stackra/database";

/** Creates the articles table with its search columns. */
export class CreateArticlesMigration extends Migration {
  /** The table, the facet's columns and the full-text index. */
  up(schema: SchemaBuilder): void {
    schema.create("articles", (t: Blueprint) => {
      t.hasPublicId("art");
      t.timestamps();
      t.string("title", 200).notNull().comment("The article's headline.");
      t.string("body", 20_000).notNull().comment("The article itself.");
      t.string("category", 40).notNull().comment("Where the article is filed.");
      t.string("status", 20).notNull().default("draft").comment("draft or published.");
      t.searchable({ text: ["title", "body"], filters: ["category"] });
      t.index(["search_vector"]).using("gin");
    });
  }
}
```

`t.searchable(...)`, a macro of `@stackra/search`, adds three nullable columns the search engine writes; your code never
writes them:

```sql
  "search_vector" tsvector null,
  "search_text" text null,
  "search_filters" jsonb null,
```

The GIN index serves the full-text lane. On a table that already exists, write `t.searchable(...)` in a
`schema.table(...)` migration and create the index `concurrently()` in its own migration; the `@stackra/search` README
("The columns") also shows the trigram index that serves typo-tolerant matches and per-language columns
(`locales: ["en", "ar"]`).

## 3. Index and query in a service

```ts src/modules/help/services/article.service.ts
/** The help centre's articles. */
export class ArticleService extends CrudService<Article> {
  /** The search reader. */
  private readonly search: Search;

  /**
   * @param search - finds and indexes articles.
   */
  constructor(search: Search) {
    super();
    this.search = search;
  }

  /** Writes a published article and indexes it in the same transaction. */
  async publish(title: string, body: string, category: string): Promise<Article> {
    const article = await this.insert({ title, body, category, status: "published" });
    await this.search.in(Article).index([article]);
    return article;
  }

  /** Takes an article back to draft; indexing it again removes its document, as `when` asks. */
  async unpublish(id: Article["id"]): Promise<Article> {
    const article = await this.update({ id }, { status: "draft" });
    await this.search.in(Article).index([article]);
    return article;
  }

  /** The published articles matching every word of `phrase`, within `category` when given. */
  async lookup(phrase: string, category?: string, cursor?: string): Promise<ArticlePage> {
    return this.search.in(Article).page(phrase, {
      filters: category === undefined ? {} : { category },
      cursor,
      limit: 10,
    });
  }
}
```

- `search.in(Article).page(phrase, options)` returns loaded rows, best first, with `hasMore` and `nextCursor`;
  `find(phrase, options)` returns rows only. `limit` is 1 to 100.
- `index(rows)` writes or removes each row's document; `remove(ids)` drops documents, for erasure.
- A filter key must be one of the facet's `filters`; anything else is refused.

### Keeping the index in step

Calling `index` after a write, as above, puts the document in the same transaction as the row, so the next read finds
it. A service whose wiring enables the outbox does not need to: gen registers its `@Searchable` models
(`registerSearchableModels`), and every committed change of a row reaches the search consumer, which re-indexes it or
removes its document. Delivery is at least once and idempotent, so an explicit `index` and the consumer can both run.

After you change the facet (a new text field, a new filter), rebuild the documents with
`stackra search:reindex Article`.

## 4. Test it

Tests use the `memory` search driver (`search.driver: memory`), which applies the same normalisation as Postgres; rows
still load from the `memory` database. In an app, `createTestingModule(HelpModule).useDrivers("memory")` binds both.
The guide's test builds the reader itself:

```ts
const search = new Search(
  new MemorySearchDriver(),
  database,
  new SettingsReader(new MemorySettingValueStoreDriver()),
);
const articles = new ArticleService(search);
```

A published article is found by any case of its words, a filter narrows the result, and a draft is never indexed:

```ts
const refund = await database.transaction(() =>
  articles.publish("Getting a refund", "Ask for a refund within 30 days.", "billing"),
);
await database.transaction(() =>
  articles.publish("Change your password", "Open settings to reset it.", "account"),
);
await database.transaction(async () => {
  articles.create({ title: "Refund policy draft", body: "Not ready.", category: "billing" });
});

const found = await articles.lookup("REFUND");
expect(found.items.map((article) => article.title)).toEqual(["Getting a refund"]);

const inAccount = await articles.lookup("refund", "account");
expect(inAccount.items).toEqual([]);
```

Taking an article back to draft removes it from the index:

```ts
await database.transaction(() => articles.unpublish(refund.id));
expect((await articles.lookup("refund")).items).toEqual([]);
```

The same test checks that `cafe hours` finds "Café opening hours" (accents fold) and that twelve matches come back as a
page of ten with `hasMore` and a second page of two.
