## One source, two kinds of reader

Every secret value lives in the private repository `figentra/secrets`, one SOPS file per secret, encrypted with a Google Cloud KMS key per scope ([ADR 0525](/adr/0525-secrets-sops-and-cloud-kms-replace-infisical)). Secret names are in git. Values are in git only as that ciphertext.

| Kind                                                                                                    | Scope in `figentra/secrets` | How code reads it                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Application secret** (payment keys, OAuth client secrets, webhook signing secrets, provider API keys) | `products/<product>/<env>`  | By name at runtime through the runtime's binding, for example `secret("NAME")` once Encore lands. The deploy's `runway secrets sync` writes the runtime store. Never from a file. |
| **CI or developer token** (CI vendor tokens, MCP server tokens, bot keys)                               | `ci/…`, `agents`            | CI: the `secrets-decrypt` action, for the scopes figentra/infra grants that job. Developers: the pnpm script that names it, through `secrets-exec.mjs`.                           |

There is no other place. No `.env` file, no `.env.example`, no second vault, and no value set by hand in a runtime store. A local override for development goes in a gitignored file that holds no value anyone else needs. Rationale: [ADR 0525](/adr/0525-secrets-sops-and-cloud-kms-replace-infisical) and [ADR 0009](/adr/0009-secrets-two-mechanisms). Procedures: [secrets runbook](/runbooks/secrets).

<Note>
  Stackra has no deployed runtime yet, so the CI and developer scopes and the repository checks are
  live. The application-secret rules apply from the first service that declares a secret.
</Note>

## What an agent may do

| An agent may                                                                                                                                                          | An agent may not                                                                                  |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Declare a secret name in code and its runway, and name the key and its purpose in its report.                                                                         | Read a value, in any form, into the transcript.                                                   |
| Make or rotate a generated value: `pnpm secrets:generate NAME --scope S`, `pnpm secrets:rotate NAME --scope S`.                                                       | Run `sops -d`, `sops decrypt`, `sops exec-env`, `sops exec-file`, or `secrets-exec.mjs` directly. |
| Ask the owner to run `pnpm secrets:put NAME --scope S` for a human value, with its purpose and where to get it.                                                       | Write the `ci/flow`, `ci/infra` or any `registry` scope.                                          |
| Reference a developer token in `.mcp.yaml` as a bare `$NAME`. Not `${NAME}`: Claude Code expands that form itself and disables the server when the variable is unset. | Set a runtime store by hand (`encore secret set`, `wrangler secret put`, `eas env:create`).       |
| Check names: `pnpm secrets:catalog --check`, `runway env check`, the file list of `figentra/secrets`.                                                                 | Write a value into a file, test, fixture, log, comment, commit message or chat message.           |
| Use sentinel test values such as `sentinel-<topic>-never-printed`.                                                                                                    | Add a `.env` file, a second vault, or a sync into the code host.                                  |

| S4  | CI authenticates by OIDC only. A job decrypts only the scopes its repository, environment and workflow are granted. A staging or pull-request job can never decrypt production. | **Enforced.** Cloud KMS, with the grants in figentra/infra `estate/secret-callers.mjs`, which its policy gate reviews.                                                                                                                      |
| S5  | A value lives only in memory and, masked, in the job's environment. It is never written to an output, an artifact, a cache, a log or a comment, and never on argv.              | **Partial.** `runway secrets decrypt` masks every value it exports and prints names only; the `secrets:*` scripts hand values to `sops` on stdin, with tests. The agent hook denies `printenv`. A CI write check is planned.                |
| S6  | No `.env`, no `.env.example`, no second vault in any repository.                                                                                                                | **Planned.** `secrets-no-dotenv` check in the validator. The agent hook already denies reading `.env` and `.dev.vars`.                                                                                                                      |
| S7  | Nobody reads a value: not the owner in chat, not an agent. Agents see names, never values, and never run `sops -d`.                                                             | **Partial.** `.agents/hooks/guard-bash.mjs` denies `.env`/`.dev.vars` reads, `printenv` and a bare `env`, `encore secret set` and `wrangler secret put`. The `sops` denies are planned (ADR 0525); until then an agent must never run them. |
| S8  | A value goes in only through the `secrets:*` scripts, as a pull request in `figentra/secrets`. A human value is the owner's to put. Deleting a production secret is owner-only. | **Partial.** The scripts refuse an agent's write to `ci/flow`, `ci/infra` or a `registry` scope. The pull request is reviewed by the policy gate ([ADR 0523](/adr/0523-humans-approve-policy-not-instances)).                               |
| S9  | A test needs zero secrets. `verify` and every test run with no credential. A test that needs a real one is a design finding.                                                    | **Partial.** `pnpm verify` takes no secret. gitleaks scans fixtures.                                                                                                                                                                        |

| S11 | The image never bakes a value.                                                                                                                                                  | **Planned**, with the first deployable image.                                                                                                                                                                                               |
| S12 | Every name has a catalog entry: owner, purpose, kind, rotation period and, for a human value, an expiry.                                                                        | **Partial.** `pnpm secrets:catalog --check`; `runway env check` checks that every environment name has a scope. `runway validate` failing on a name the catalog lacks is planned.                                                           |

## When a secret leaks

1. Revoke at the vendor and rotate first, investigate second. The value is compromised the moment it is printed or pushed. Rewriting history does not un-leak it, and old values stay in `figentra/secrets`' history as ciphertext.
2. Record what, when and when it was rotated. Never paste the value.
3. If gitleaks missed the pattern, add it to `.gitleaks.toml`.

## Not allowed

- A second place for a value "just for this one case".
- A `${KEY}` placeholder that a tool or shell expands into a file.
- A secret in a commit message, PR description, chat message, issue or AI prompt.
- Lowering an article so a gate passes. Change the law through an ADR, or fix the code.
