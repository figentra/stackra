title: "0230 — Reviews come from a separate reviewer identity, never the author"
description: "Accepted · 2026-10-20 · amended 2026-10-21 (STA-208)"

## Context

[0119](/adr/0119-merge-policy-and-release-authority) lets an agent merge only through `pnpm pr:merge`, which needs an
`AI-REVIEW: PASS <head sha>` comment. Builders and reviewers both act as the `stackra-bot` GitHub App, and agents
also hold the owner's `gh` login (`figentra-usr`). `pr-merge` trusted verdicts from both identities. So it could not
tell an author from its reviewer. On 2026-10-20, builder agents posted `AI-REVIEW: PASS` on their own pull requests
and merged them, some through plain `gh` as the owner's account. That breaks
[0021](/adr/0021-ai-engine-and-agent-write-safety) rule 6: agents are not their own approvers.

We weighed two designs. A signed review record verified by `pr-merge` needs a key that the builder session can also
read on the same machine. A second GitHub App ties each verdict to an identity that GitHub records, and that app can
hold fewer permissions than the builder app.

## Decision

1. **A second GitHub App, `stackra-reviewer`**, is the only identity whose verdict counts. Its installation holds
   pull requests: write and contents: read, never contents: write. It can comment and review, and it cannot push.
   Its credentials are `STACKRA_REVIEWER_APP_ID`, `STACKRA_REVIEWER_INSTALLATION_ID` and
   `STACKRA_REVIEWER_PRIVATE_KEY` in Infisical. Reviewer agents post through `pnpm bot:review`, which runs only
   `gh pr view|diff|checks|comment|review` and read-only `gh api` (no `-X`, `--method`, fields or `--input`, alone or bundled as in `-iX`).
2. **`pr-merge` counts a verdict only from the `stackra-reviewer` App**, identified by what GitHub records, never by
   a login string: a REST issue comment with `user.type` `Bot` and `performed_via_github_app.slug`
   `stackra-reviewer`. It never counts when the verdict's author is the PR author or the head commit's author or
   committer. A verdict from the builder app `stackra-bot`, or from a user account named `stackra-reviewer`, is
   ignored, and the refusal says why. The verdict format is binding:
   - the first line is `AI-REVIEW: PASS <full 40-hex head sha> base=<base ref>` or `AI-REVIEW: FAIL <head sha>`. A
     PASS counts only while the PR still targets that base ref, so re-targeting the PR voids it. The base is a ref
     name, not a SHA, because `main` moves under every open PR and the merge is a squash onto its tip;
   - PASS is parsed strictly and FAIL loosely (amended 2026-10-21, STA-208): any reviewer-app first line that starts
     `AI-REVIEW: FAIL` counts. A short SHA, no SHA, trailing text, `FAILED`, or Markdown around it
     (`**AI-REVIEW: FAIL**`) still counts. A FAIL with no SHA blocks every later head until the owner deletes it. Only a FAIL that names a hex SHA of 7 or
     more characters that is not a prefix of the head is read as a FAIL for an older commit and skipped;
   - an edited verdict never counts, and an edit to any reviewer comment voids every reviewer verdict posted before
     it. Anyone with write access can edit another account's comment, so the reviewer always posts a new comment;
   - a FAIL for the head SHA is sticky: it beats every PASS for that SHA, older or newer. A wrong FAIL is cleared by
     a new commit or by the owner. Minimized comments are not visible to REST and still count, which is safe for a
     FAIL; a reviewer retracts a PASS by posting a FAIL.
3. **The owner approves by hand only with a pull request review**: an APPROVED review by the owner user on the head
   SHA whose body ends with the token `owner-approval`, and not on a commit the owner account authored. An
   `AI-REVIEW:` comment from the owner account never counts. A counted reviewer FAIL on the same SHA overrides the
   owner's approving review: the owner clears it with a new commit or by deleting the FAIL, never by approving over
   it. The owner submits the review only in the GitHub web or mobile UI, signed in with 2FA (amended 2026-10-21).
4. **Agents never write `owner-approval` or the `owner-approved` label**, and never post `AI-REVIEW:` through plain
   `gh`. The bash guard denies all three. This is a tripwire, not the control: the guard cannot see a `--body-file`.
5. **Agents never use the owner's GitHub login** (owner decision 2026-10-20, amended 2026-10-21, STA-208). Every
   agent-side GitHub call, the coordinator's read-only queries included, runs on an app token: builders and the
   coordinator through `pnpm bot:gh` and `pnpm bot:git` (`stackra-bot`), reviewers through `pnpm bot:review`
   (`stackra-reviewer`), merges through `pnpm pr:merge` (as `stackra-bot`). The wrappers fail closed: no token, no
   command. There is no `GH_TOKEN=… gh` form, because `gh` falls back to the owner's stored login when `GH_TOKEN` is
   empty. The bash guard denies plain `gh` in any form, every network `git` outside `pnpm bot:git`, and anything that
   prints or stores a bot token. It also checks `$(…)`, backtick, `sh -c` and `eval` bodies. The owner's own `gh`
   login stays for the owner's own terminal. The structural fix is the owner's: move that login to a separate
   `GH_CONFIG_DIR` and remove `gh auth git-credential` from the global git config, so an agent's plain `gh` or `git`
   finds no owner credential. The [GitHub identities runbook](/runbooks/github-identities) lists the commands and
   the owner's steps.

## Consequences

- A PR built by `stackra-bot` needs a reviewer agent's PASS posted as `stackra-reviewer`. Self-review is refused
  with a reason that names the identity.
- The owner created the `stackra-reviewer` app on 2026-10-20 (installed on `figentra/stackra`, and on `figentra/os` since 2026-10-21; pull requests:
  write, contents: read) and stored its credentials in Infisical `/agents`, which accepted this record. Reviewer
  agents post every verdict through `pnpm bot:review`; a verdict posted through `pnpm bot:gh` no longer counts.
- What remains: the same machine can mint both apps' tokens, so a builder agent that ignores its role could run
  `pnpm bot:review`. Rules 2 and 5 remove the obvious path, because the reviewer never authors and builders never
  act as the owner. Closing the gap fully needs the review to run where builders hold no reviewer key. That means a
  CI job or a separate host with its own Infisical identity, which is Phase 3 scope (merge queue, see below).
- The owner path is still forgeable on this machine. The guard denies the common accidental forms of plain `gh` and
  network `git`. It does not follow aliases, shell functions, variables used as a command name, or `npx`. Agents run
  as the owner's macOS user, so the keychain and `~/.config/gh` stay readable. The guard is an accident guard, not
  isolation. The owner's two runbook steps (separate `GH_CONFIG_DIR`, no global `gh auth git-credential`) remove the
  fallback for plain commands. Full isolation needs agents to run as a separate OS user or on the EC2 agent host,
  where the owner's login does not exist. Until then the owner-approval path is only as strong as agents'
  compliance with rules 4 and 5.
- Deleted comments are invisible to `pr-merge`: deleting a reviewer FAIL makes an older PASS count again. Only
  accounts with write access can delete another account's comment: the owner, or an agent that works around the
  guard to reach the owner's login (see above).

## Enforcement

- `tools/scripts/pr-merge.mjs` (`aiReview`, `blockers`, tests in `tools/scripts/__tests__/pr-merge.test.mjs`): the
  App identity check, the author and committer exclusion, the full head SHA and base ref, edited and sticky-FAIL
  verdicts, and the owner's approving review with the `owner-approval` token.
- `tools/scripts/bot-gh.mjs` (`reviewerAllows`): the reviewer's command allowlist, reading bundled short flags letter by letter and refusing `--edit-last` and `--delete-last`.
- `.agents/hooks/guard-bash.mjs`: denies agent commands that write `owner-approval` or `owner-approved`, or post
  `AI-REVIEW:` through `gh` or `pnpm bot:gh`. For rule 5 it denies plain `gh`, network `git` outside `pnpm bot:git`
  (push, fetch, pull, clone, ls-remote, submodule, subtree, remote update/show/prune, archive `--remote`),
  `pnpm bot:token`, `$GH_TOKEN`, `bot:gh -- auth`, `git credential` and `git credential-<helper>` (bare or through
  `bot:git`), pack plumbing (`send-pack`, `receive-pack`, `fetch-pack`, `upload-pack`), a bot push to `main` read in
  the push's own checkout (`cd`, `-C`, `--git-dir`, `--work-tree`), and any merge outside `pnpm pr:merge`
  (`bot:gh -- pr merge`, `api …/pulls/<n>/merge` with any method and its `//` and `%2F` spellings, the GraphQL merge
  mutations), also inside `$(…)`, backticks, `sh -c` and `eval`; the quoted `--title`, `--body`, `-m` text and
  `pnpm linear comment` text are prose and not scanned. STA-216 adds: `git config` is read-only (the first option
  must be a read mode and no write flag may follow; every other form is denied), git `-c` is an allow-list of
  exact display and identity keys (also inside `$(…)` at any depth or backticks within prose values), `--config-env`, the `GIT_CONFIG*`, `HOME=`, `XDG_CONFIG_HOME=`, pager, `GIT_ASKPASS=`,
  `SSH_ASKPASS=`, `GIT_EXEC_PATH=`, `GIT_SSH[_COMMAND]=` and `GIT_PROXY_COMMAND=`, `GIT_EDITOR=` and `GIT_SEQUENCE_EDITOR=` (except as `true`, `:` or `cat`), `GIT_EXTERNAL_DIFF=` and `GIT_TEMPLATE_DIR=` env prefixes, and `man -P|-H|-B|-T|-C`
  and their long forms; merge paths are
  percent-decoded and dot segments resolved before matching; quoted `-c` values and `GIT_DIR=` / `GIT_WORK_TREE=` in the push-target resolution (an
  unresolvable checkout counts as `main`); `git-*-pack` binaries by path; `bot:gh -- api graphql` from a file
  (`-F query=@f`, `--input`) or substitution, and `bot:gh -- alias`. Tests in `.agents/hooks/__tests__/guard-bash.test.mjs`.
- `tools/scripts/bot-gh.mjs` (`leaksToken`, `mergesPr`, `unsafeArgs`): the wrappers refuse `gh auth`, `git credential`,
  `git credential-*`, every merge (which only `pnpm pr:merge` performs), git `-c` outside an allow-list, any `git config` that is not a read, `--config-env`, `gh alias`
  and file-sourced `gh api graphql`.
- `.opencode/plugins/guard/decide.ts`: executors run no `gh`, none of those network `git` commands, no pack
  plumbing, no `git credential` or `git-credential-*`, no `git-*-pack` binary, no `git -c alias.*` / `--config-env`, and no
  `pnpm bot:*` or `pr:merge`, with the same substitution bodies checked. The subcommand is read past spaced
  `--git-dir`, `--work-tree`, `--namespace`, `-C` and `-c` values.
- Planned: the review runs in a CI job with its own credentials (the Phase 3 merge-queue design).
