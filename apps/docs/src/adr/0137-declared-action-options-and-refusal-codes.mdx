title: "0137 — Declared action execution options and refusal reasons"
description: "Proposed · 2026-10-20"
---

<Note>
  Amends [0098](/adr/0098-actions-are-the-unit): actions declare options, and each option runs in a
  step the pipeline already has.
</Note>

## Context

An action needs to say how it is consent-checked, rate-limited, locked, cached or limited in includes. The owner's intent-map
item P5 set these as declared options, each run by one pipeline step. Two refusal codes came from later answers (I5 and EN3).
The refusal codes do not share a casing: P5 uses kebab-case, and the two later codes use snake_case (contradiction C-14). The
owner has not chosen one casing, so this ADR is Proposed.

## Decision

1. An action may declare these optional options: `consent`, `rateLimit`, `lock`, `cache` and `maxInclude`. Each is run by an
   existing pipeline step (ADR 0138, wave 1 part 2, fixes the order).
2. The stable refusal codes are `module-disabled`, `entitlement-missing`, `flag-off`, `consent-missing`, `rate-limited`,
   `region-unsupported` and `maintenance` (P5).
3. Two more codes are added from later answers: `step_up_required` (I5, mem L609) and `limit_exceeded`, with an upgrade hint
   (EN3, mem L676).
4. **Open:** the casing. One of the two forms must be chosen for all nine codes (C-14). Until the owner chooses, the codes
   above are as the sources spell them.

## Consequences

- Clients can branch on a stable code. A code added later is a new ADR, so the list does not drift silently.
- Until the casing is chosen, the code list cannot be used as a contract by generated clients.

## Enforcement

planned — gen reads the option declarations and rejects an unknown refusal code. Nothing checks the codes today.

## Alternatives

- Free-text refusal messages: rejected, clients need stable codes.
