## Context

[ADR 0168](/adr/0168-runway-public-reusable-workflows-build-order-and-runway-yaml) decision 4 gives each repository one root `runway.yaml`, and its decision 5 lists the sections that file holds: deployables and providers, resources and scaling, the release policy, domains and the secrets map. Topology, which packs logical services into deployables, is decided in [ADR 0169](/adr/0169-topology-runway-yaml-packs-logical-services-into-deployables). The JSON Schemas in `tools/schemas/` already go further. `runway-root.schema.json`, `runway-app.schema.json` and `runway-service.schema.json` describe runway format version 2, which splits the root from member runways. In version 2 both member schemas require a `member` key that names the member, and the service schema also holds facts about where a service runs: for each environment, its `deployable`, its `isolate` flag and its `resources`. The app schema has none of those three fields. A service that needs a dedicated cache or search index has no field that says so or why, and the facts about placement are split between the member and the root.

Those are two different facts. What a member needs changes with its code. Where a member runs, and which processes it shares, changes with the environment and the account. Splitting them lets a member state its requirements beside its code, and lets the root decide placement once for each environment.

## Decision

1. **A member runway states WHAT.** A member that needs runtime resources has a `runway.yaml` at its member root. The member is the one whose folder holds the file, so the file does not name it. It declares `version: 3` and three things:
   - `requires`: one entry per resource the member needs beyond what gen derives from `stackra.manifest.json`. An entry names an `engine` and whether the resource is `dedicated`. A dedicated resource also has a `reason`, one line that says why the member cannot share a resource.
   - `secrets`: the names of the secrets the member reads. The file holds names only, never values ([ADR 0173](/adr/0173-secrets-infisical-is-the-source-of-production-secrets)).
   - `environments.<name>`: the member's sizes and values for each environment. These are a port, the database storage and extensions, the cache size, replicas and eviction policy, queue settings, and the `config` values that set the member's config classes for that environment. Those values are the last layer of configuration.

   A member runway never holds `member`, `deployable`, `isolate`, `group`, `cpu`, `memory` or `instances`. Those are root facts.

2. **The root runway states WHERE and HOW PACKED.** The repository's root `runway.yaml` holds the providers, destinations, shared pools, domains, defaults and the topology of each environment. A topology has:
   - `mode`: `monolith`, `grouped` or `split`;
   - `isolate`: the members that keep their own database server and network policy;
   - `default`: the group for members that no group lists;
   - `groups`: for each group, its `members`, its `cpu`, `memory` and `instances` (`min` and `max`), and `workers.split` where its workers run apart.

   In a grouped environment every member is placed in exactly one group.

3. **Groups are process allocations.** Each group is a process allocation inside the one generated Encore application ([ADR 0091](/adr/0091-generated-encore-app-in-stackra-folder)). This is the one-app rule of [0289](/adr/0289-runway-and-environments-workers-one-encore-app-previews-and-publishing) decision 5: the groups are not separate Encore applications. Whether a group scales on its own is not decided here.

4. **A dependency with one user belongs to that user.** A dependency that only one member needs is declared by that member, not by the root. The identity provider ([ADR 0206](/adr/0206-zitadel-is-the-identity-provider-and-stackra-identity-is-provider-neutral)) belongs to the identity member, and a development container belongs to the driver package that needs it.

5. **Engines follow ADR 0227.** `requires.<resource>.engine` accepts only an engine that ADR 0227 neither defers nor rejects. A dedicated search resource takes `postgres`, and the schema refuses the deferred engines. A dedicated search engine returns only through a new record, once the revival trigger of ADR 0227 has fired.

6. **Both files are block-style YAML.** They follow the repository's YAML rule: no flow mappings, and flow sequences only for short scalar lists on one line.

A member runway looks like this:

```yaml
# services/commerce/runway.yaml
version: 3

requires:
  cache:
    dedicated: true
    engine: valkey
    reason: price snapshots and cart sessions need their own eviction policy
  search:
    dedicated: true
    engine: postgres
    reason: storefront search must not compete with order writes

secrets: [PRICING_API_KEY]

environments:
  production:
    database:
      storageGb: 100
      extensions: [ltree, pg_trgm]
    cache:
      memoryMb: 2048
      eviction: allkeys-lru
    config:
      commerce:
        storefrontBaseUrl: https://www.acme.example
```

The root holds the topology of each environment, in the same block style:

```yaml
# runway.yaml (root, production topology)
environments:
  production:
    topology:
      mode: grouped
      isolate: [identity, payments-ledger]
      groups:
        identity:
          members: [identity]
          instances:
            min: 2
            max: 6
        commerce:
          members: [commerce, pricing, invoicing]
          instances:
            min: 2
            max: 10
          workers:
            split: true
```

## Consequences

- A requirement sits beside the code that needs it, and a dedicated resource cannot be declared without a reason.
- The root is the one file that decides where members run and how they are packed, so it is the file a reviewer checks for placement.
- Adding a member to an environment is one line in one group of the root file. The validator fails until the member is placed, so nothing runs unplaced. This is the cost of having the root pack.
- A group's size has one source, the root, because member runways carry no sizes for groups.

## Enforcement

Today the only check that reaches these files is `checkYamlFlowMaps` in `tools/scripts/validate-repository.mjs`, which covers the block-style rule for repository YAML. No runway file is committed yet. The schemas on main describe format version 3 since stackra#136 (STA-417): `tools/schemas/runway-root.schema.json`, `tools/schemas/runway-app.schema.json` and `tools/schemas/runway-service.schema.json` fix `version` at 3, the member schemas have no `member` key, and the root schema carries the topology groups of decision 2. Editors read these schemas, and the static Worker serves them; `pnpm validate` does not check runway files against them yet.

Planned, tracked in STA-339:

- planned — STA-339: `pnpm validate` checks every runway file against the version 3 schemas. It fails when a member runway holds a root key, when a grouped environment does not place each member exactly once, when an engine is not allowed by ADR 0227, and when `dedicated` has no `reason`.
- planned — STA-339: gen fails when a `requires` entry has no driver.
