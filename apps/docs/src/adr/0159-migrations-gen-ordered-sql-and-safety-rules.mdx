<Note>
  Amended 2026-10-24 (STA-408): the spike that the 2026-10-23 note waited on is done. Encore's
  runner (v1.58.6) sends each migration file and its own bookkeeping insert as one query string,
  so Postgres runs them in an implicit transaction, and every concurrent index build fails with
  SQLSTATE 25001. The runner has no option to change that. A constraint added `NOT VALID` and
  validated in a later step works, but that covers constraints, not index builds.

Decision 2 is amended: `stackra db migrate` applies the migrations as a release step in every
environment, SaaS and on-prem. Encore's runner is not used. Rollback stays as the 2026-10-23
note says: `stackra db rollback` on dev, preview and test databases only, and production stays
forward-only.

The runner keeps the `N_name.up.sql` numbering of the compiled SQL and the
`schema_migrations(version, dirty)` table shape. It closes the gaps the spike found in
Encore's runner:

- **Steps outside a transaction.** A compiled step that cannot run in a transaction (a
  concurrent index build, which sits in its own step under decision 3) carries a per-file
  marker. The runner sends each of its statements as its own query and writes the bookkeeping
  row separately.
- **Timeouts.** Every session sets `lock_timeout` and `statement_timeout`, as decision 3
  requires.
- **Failed concurrent builds.** After a concurrent index build fails, the runner detects the
  INVALID index it left, drops it concurrently, and then retries the step or reports it.
- **Dirty versions.** A dirty version fails loudly and names the file. The runner never retries
  it silently.
- **Positions.** An error names the statement's position in the file.

</Note>

  [0305](/adr/0305-programming-model-v3-1-names-partners-files-and-class-components), with the v3.1
  migration rules. A migration is a frozen snapshot: it imports only `@stackra/database` and

  rewrite history. Authors write `up()` only. Gen derives an inverse for every step and stores it
  beside the compiled SQL. Rollback runs on dev, preview and test databases only, through `stackra
  db rollback`; production stays forward-only. Decision 4 (forward fix only) and the rejected
  alternative of rolling back data apply to production only.

A raw SQL step takes `schema.sql(x, { inverse })`. `inverse: false` marks an irreversible step, and a missing `inverse` is a gen error.

Order is the number within a module, plus `after:` across members and the edges that macros imply;
a released prefix does not move, and there is no `before`. Gen locks each compiled step with a
SHA-256 hash in `stackra.manifest.json`. Operations belong to classes (Additive, Online, Contract
and Banned), and gen enforces the class of each step. Stackra's column conventions are a `Macro`
kind in `database/macros/`, named after its partner. Decision 2 (Encore's runner applies the SQL)
stands until the spike on single-statement concurrent index builds decides whether one Stackra
runner runs everywhere. Decision 3 applies: concurrent index builds sit in their own step.

</Note>

## Context

[0124](/adr/0124-encore-is-the-generated-runtime-target) left open how MikroORM migrations, including migrations shipped in packages,
reach the runner (DP12 and FW4). The owner answered on 2026-10-20: gen produces the migrations, and the runner applies them. The
owner also set expand-and-contract rules and a forward-only policy (DP13 and DP14, mem L443–444, L355–356).

## Decision

1. **Package migrations (FW4 a).** Gen pulls the migrations shipped in packages into the host's migration stream.
2. **Ordered SQL (DP12 a).** Gen writes ordered SQL files. Encore's runner applies them in SaaS. On-prem runs them as a pre-upgrade job.
3. **Safety (DP13 a).**
   - expand-and-contract, with destructive steps deferred to a later release;
   - lock and statement timeouts on every migration;
   - concurrent index builds in their own migration;
   - a squawk lint in CI;
   - backfills run as queue jobs ([0148](/adr/0148-queue-and-scheduler-full-job-features-fair-queuing-and-tenant-schedules)).
4. **Forward fix only (DP14).** Data is never rolled back by a migration. A bad migration is fixed by a new migration.

## Consequences

- An on-prem upgrade runs migrations as a job before the new code starts, so a failed migration stops the upgrade.
- Destructive changes take two releases, so a rollback never meets a dropped column.

## Enforcement

planned — the squawk lint in CI, the lock and statement timeouts in the migration runner, and `stackra gen --check` for stale SQL.
The upgrade runbook is a final-pass item (`runbooks/upgrade.mdx`).

## Alternatives

- Migrations applied by MikroORM at boot: not chosen; the runner is Encore in SaaS and a job on-prem.
- Rolling back data: rejected by DP14.
