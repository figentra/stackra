## Context

The service questionnaires used service-prefixed event names (`identity.user.created.v1`, `tenancy.tenant.<state>.v1`). The owner's
later answer C27 (mem L855, 2026-10-20) removes the service prefix. It wins over the earlier names (contradiction C-12). The OS documents
will be renamed to match. The owner's naming table of 2026-10-20 then fixed the form as `ns.entity.verb.vN`, which adds a namespace
segment to C27's form.

## Decision

1. Events are named `ns.entity.verb.vN` (ADR 0231):
   - `ns` is the module namespace of [0131](/adr/0131-module-key-version-and-deprecation), so it names the owning module, not a service;
   - `entity` is the aggregate the event is about;
   - `verb` is the event;
   - `vN` is the version.
     Names are globally unique through the registry (C27).
2. The envelope fields are `id`, `type`, `version`, `occurredAt`, `tenant`, `actor`, `onBehalfOf`, `correlation` and `causation`,
   `traceId`, and `data`. The envelope lives in `contracts`.
3. An in-process event maps one-to-one to an integration event at the outbox.

## Consequences

- An event name carries its module namespace, so a reader sees the owner in the name. The registry still enforces uniqueness.
- Consumers depend on `contracts`, not on another service's source.
- Existing `<aggregate>.<verb>.v<n>` names need the namespace segment before they are published.

## Enforcement

planned — the registry rejects a duplicate event name, and the validator rejects a name that does not match `ns.entity.verb.vN`.

## Alternatives

- Service-prefixed names (I10, T2, T10): superseded by C27 (C-12).
- `<aggregate>.<verb>.v<n>` with no namespace (C27 as first written): amended by the owner's naming table (ADR 0231).
