Timeouts and waits (decision 1): `timeout` applies to a step or to a whole run, as an option of
the `Workflow` or of `@Step`. `@Step({ waitFor, correlate, timeout })` parks the run durably until
the named `Signal` class, or the event, arrives. A signal that arrives early is held until the
step reaches its wait. A long step reports liveness with `heartbeat`. A step that misses its
heartbeat is dead, and elapsed time alone does not make it dead. A retry resumes from the progress
the step reported through `ctx.heartbeat({ ... })`, which the retry reads from `ctx.progress`.

Signals: a signal is a class with fields in the `workflows/` folder, extending `Signal`. An action
or a listener sends it with `ctx.signal(Signal, key, payload)`.

Approval (decision 3) is not part of the v3 pipeline order in
[0138](/adr/0138-pipeline-order-is-fixed), and this note does not settle it. Decision 5 (one graph
format for coded and studio workflows) is restated only as far as this: a coded workflow is the
class form above. How studio automations map onto it is not settled here.

Enforcement of this note: planned — STA-340 (gen errors for `undo<Step>` naming no step, for
`waitFor` without `correlate`, for a run timeout shorter than its waits, and for a signal that no
action or listener sends), and the conformance suite of
[0151](/adr/0151-workflow-engine-is-a-port-with-native-and-temporal-drivers).

</Note>

## Context

Workflows needed waits, timeouts, versioning and operations. The owner's answers P10, WF1 and WF4 (mem L770 and L773, 2026-10-20)
fix these. Coded workflows and studio automations were to share one format.

## Decision

1. **Timeouts and waits (P10).** `timeout` applies to steps and runs. `@Step({ waitFor: event | signal })` parks a run durably until
   the event or signal arrives.
2. **Pinned versions (P10).** A run is pinned to the version it started on.
3. **Approval (P10).** Approval is the pipeline's approval park ([0136](/adr/0136-action-runtime-contract) and the approval rules
   of the pipeline).
4. **Operations (P10).** Inspect, retry and cancel are actions. Cancel is at risk level L4.
5. **One graph format (WF1).** Coded workflows and studio automations compile to one graph format, which runs on the
   driver-agnostic engine ([0151](/adr/0151-workflow-engine-is-a-port-with-native-and-temporal-drivers)).
6. **Guards and quotas (WF4).** Quotas use meters. Loop and recursion guards apply. Steps are idempotent. Test runs are supported.
   Drafts are versioned and published. Run history and replay are available. Failure alerts and kill switches exist.

## Consequences

- A run keeps its version when a workflow is republished, so an in-flight run is never changed underneath.
- Operators can inspect and cancel a run through the same action pipeline as everything else.

## Enforcement

planned — the workflow conformance suite checks timeouts, waits and the run-version pin on both drivers.

## Alternatives

- Separate formats for coded and studio workflows: rejected by WF1.
