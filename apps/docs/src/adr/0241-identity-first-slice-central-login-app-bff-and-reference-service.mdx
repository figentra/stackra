## Context

Every product (console, Academorix, Juristra and the rest) sends its users through one central login, the way a large platform's sign-in works. The owner's identity answers (mem L933–934, 2026-10-20) fix the model. The first slice (ADR 0205) needs to know where each piece runs.

## Decision

1. **Central login app.** One login app at an identity domain. Every product redirects to it for OIDC single sign-on. ZITADEL sits behind it.
2. **Web BFF.** The BFF is only for the browser session: an HttpOnly cookie, tokens kept out of JavaScript. It is not the place for cross-device data.
3. **Cross-device data.** Data such as a cart or preferences is server state in the service that owns it, updated in real time by push, with an offline mutation queue on the client (ADR 0252).
4. **Mobile and desktop.** OIDC with PKCE.
5. **Identity reference service.** It holds the apps, the organisations, the mapping from tenant to ZITADEL org, and the identity events. Login stays with ZITADEL (ADR 0206).
6. **Customisation.** The login is customisable per tenant.

## Consequences

- A user signs in once for every product, and a product never sees a password.
- The BFF is small, so a change to cross-device data does not touch the session code.

## Enforcement

planned — the single-sign-on test runs two products against the same login app in staging.
