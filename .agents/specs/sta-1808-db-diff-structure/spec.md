# Feature Specification: `stackra db diff` and `stackra db structure`

**Feature Branch**: `figentra/sta-1808-db-diff-structure`

**Created**: 2026-11-01

**Status**: Accepted (US1 in build; US2 and US3 later)

**Linear**: STA-1808

**Linear project**: none yet (the leader assigns an owner and a project)

**Clarifications status**: complete

**Input**: Product gates expect `stackra db diff` to exist. The invoicing#4 gate runs
`cd services/invoicing && pnpm exec stackra db diff`, and its check reads "migration 0002 compiles, and `stackra db
diff` agrees with the model on `idx_tax_documents_tenant_id_source_key_channel`". The command fails with
`stackra: unknown command: db` on core main, and it is missing on the 0.3.1 train (`land/022-stack`) too. "db diff and
structure not on main" is on the 0.3.0 open-gaps list. Nobody owns it yet.

Clarifications status is `complete` in one sense only: every question the code and the ADRs can answer is answered
below. The questions that need a decision are owner decisions, listed under "Open questions". The spec stays **Draft**
until the leader answers them, and `/speckit.clarify` then folds the answers in.

## What exists today (land/022-stack, a7ed7a65)

- **CLI** (`packages/developer/cli`): `db migrate` (`db-migrate-command.constant.ts`) and `db rollback`
  (`db-rollback-command.constant.ts`) only. Both load the member's own `@stackra/database/node` through
  `loadDatabaseRunner(cwd)` ("the CLI holds no database driver"), and the runner shape is `DatabaseRunner`
  (`migrate`, `rollback`). `commands.constant.ts` and the README both say "`stackra db diff` and `seed` land with
  `@stackra/database`".
- **`stackra structure` already exists, and it is something else.** `structure-command.constant.ts` prints the
  repository structure standards page (it was `tools/scripts/structure.mjs`). That is the "structure" ADR 0282
  decision 3 lists beside `db diff`. No ADR, skill or note defines a **`db structure`** command.
- **Migrations** (`packages/data/database`): authors write `up(schema)` with the `Blueprint` DSL.
  `compileMigration` (pure, `core/functions/compile-migration.function.ts`) records the operations and returns ordered
  SQL steps with derived inverses. It returns **SQL text only, with no structured schema state**. `migrate`,
  `rollback` and `readMigrationFiles` live in `node/functions/`.
- **Gen** (`packages/developer/gen`): `compileMigrations` (node) → `orderMigrations` → `emitMigrations` write
  `.stackra/migrations/<seq>_<module>_<NNNN>_<stem>.up.sql` and `.down.sql`. `emitEntities` writes one MikroORM
  `EntitySchema` per model. Its contract says "Column types, lengths, indexes and foreign keys are the migration's (ADR
  0159), so none is written here". Gen's `MemberIR` holds each model's fields (`FieldIR`: type, nullability, rules
  such as `@Str({ max })`) and class facets (`@Index`, `@Searchable`). `checkBlindIndexes` and `checkTableIndexes`
  already read `@Index` from it. **Nothing compares models with migrations today.**
- **Postgres without a server**: `@electric-sql/pglite` 0.5.8 and `@mikro-orm/pglite` 7.2.5 are in the catalog, as
  optional peers of `@stackra/database` (its `./testing` memory driver, ADR 0266). `@mikro-orm/postgresql` 7.2.5 is a
  direct dependency, and it can introspect a schema.
- **Contracts already written against `db diff`**:
  - ADR 0159, note for ADR 0294: "`stackra db diff` writes them" (each module's `NNNN-<name>.migration.ts`).
  - ADR 0282 decision 3 lists `db diff` among the CLI commands.
  - The `db-models-and-migrations` skill.
  - FD-13 of the programming-model review: "The model is the one source. `stackra db diff <name>` writes the
    blueprint migration".
  - The docblocks of `@Index`, `@Searchable`, `searchable.macro.ts`, `loyalty-account.model.ts`,
    `access-log-entry.model.ts` and `audit-log-entry.model.ts`: "every index is declared here, so `stackra db diff`
    never proposes dropping one".
  - `check-doc-file.function.ts` in `@stackra/repo-checks` already skips a file that opens with
    `// generated by stackra db diff`.

## Proposed behaviour (draft, pending the open questions)

1. `stackra db diff` runs in a member folder. It builds the **migrated schema** by applying the member's ordered
   compiled migrations (its own and its declared packages', in gen's order) to a throwaway in-process Postgres
   (PGlite), then introspecting it.
2. It builds the **modelled schema** from gen's `MemberIR`: each model's table in its module's Postgres schema, its
   columns with their nullability, and its `@Index` and `@Searchable` indexes with their derived `idx_` names.
3. It compares the two and prints one line per difference, grouped by module. It exits 0 when they agree and 1 when
   they differ, so a gate can run it with no database and no secret.
4. `stackra db diff --write <name>` writes the additive differences as the next
   `database/migrations/NNNN-<name>.migration.ts` of each affected module. The file opens with
   `// generated by stackra db diff`. Destructive differences are never written: they are reported as a later
   contract step (ADR 0159 decision 3). A concurrent index build goes in its own migration.
5. `stackra db structure` prints the DDL the committed migrations build, normalised and in a stable order. With
   `--write` it writes that DDL to a file. It reads no live database.

- **Apps touched**: `apps/docs` (CLI reference page and the `db-models-and-migrations` skill page, only if the skill

- **Services touched**: none in core. Product services gain a gate step (invoicing#4 already runs it)
- **Packages touched**: cli, database and gen (skills only if its text changes):

  - `packages/data/database/node`: a `structure` (replay and introspect) entry on the runner, next to `migrate` and
    `rollback`.
  - `packages/developer/gen`: a pure modelled-schema builder from `MemberIR`, the comparer, and the migration writer.
  - `packages/developer/skills`: the skill text, only if behaviour differs from what it says today.
- **Cross-service events**: none
- **Tenancy and data**: reads model metadata and committed migrations only. The replay database is in memory and
  thrown away, and nothing touches a real database or tenant row. `--write` creates migration source files, which a

- **New dependencies**: none in the catalog. `@electric-sql/pglite` and `@mikro-orm/pglite` are already catalog

- **Deploy modes**: developer and CI tooling only. Nothing ships to SaaS, on-prem or air-gapped runtimes. Both
  commands work offline
- **Licence tier**: free (MIT, `@stackra/cli` basic commands, ADR 0282 decision 8)
- **Docs to update**: the CLI README and reference, and the migrations skill:
  - `packages/developer/cli/README.md` (drop "db diff lands with @stackra/database").
  - The doc comment of `commands.constant.ts`.
  - The CLI reference page in `apps/docs`.
  - The `db-models-and-migrations` skill, which says Encore's runner applies migrations in SaaS; that is stale since
    ADR 0159's 2026-10-24 note and is fixed in passing.
- **Lane**: full (two commands across three members: cli, database, gen)
- **Change risk**: R2 (a public CLI contract across several members, and a new runner entry in `@stackra/database`)

## User Scenarios & Testing

### User Story 1 - A gate proves migrations agree with models (Priority: P1)

A product gate runs `pnpm exec stackra db diff` in a service, with no database and no secret. It needs exit 0 when
every model's table, columns, nullability and declared indexes are what the committed migrations build, and exit 1
with each difference named when they are not.

**Independent Test**: `packages/developer/cli/src/node/constants/__tests__/db-diff-command.constant.test.ts`, plus the
comparer's unit tests in gen.

**Acceptance Scenarios**:

1. **Given** invoicing's `TaxDocument` model declares `@Index(["tenantId", "sourceKey", "channel"], { unique: true })`
   and migration 0002 creates `idx_tax_documents_tenant_id_source_key_channel` unique, **When** `stackra db diff`
   runs, **Then** it prints `db diff: invoicing agrees with its models` and exits 0.
2. **Given** a model gains `dueAt: Date | null` and no migration adds the column, **When** `stackra db diff` runs,
   **Then** it prints `invoicing  tax_documents  missing_column  due_at` and exits 1.
3. **Given** a migration creates an index no model declares, **When** `stackra db diff` runs, **Then** it reports
   `undeclared_index` and exits 1. That is the case the `@Index` docblocks promise to catch.

### User Story 2 - A developer writes the next migration from the models (Priority: P2)

After changing a model, a developer runs `stackra db diff --write add-tax-due-at`. The command writes the next
`NNNN-add-tax-due-at.migration.ts` in each affected module. The file is additive only and opens with
`// generated by stackra db diff`. It compiles under `compileMigration`, and a second `stackra db diff` then exits 0.

**Independent Test**: gen's migration-writer test (the source text for a fixed difference) and a CLI test that runs
`--write` on a fixture member, then runs `db diff` again.

### User Story 3 - A reviewer reads the schema the migrations build (Priority: P3)

`stackra db structure` prints the whole schema of the member's migrations as normalised DDL, so a reviewer or an agent
can read the schema without replaying migrations in their head.

**Independent Test**: `db-structure-command.constant.test.ts` on a fixture member with two modules. The output is
byte-identical across two runs.

### Edge Cases

- **A member with no models and no migrations** prints `nothing to compare` and exits 0.
- **A model in a declared package** is compared against that package's migrations. A difference there is reported,
  and it is never written into the host (the package owns its migrations, ADR 0159 decision 1).
- **Columns that come from macros and traits** (`t.tenant()`, `t.publicId()`, `t.timestamps()`, `t.userStamps()`)
  count as declared by the model trait that implies them. They are never a `missing_column` or an `undeclared_column`
  (open question Q3 on how this mapping is sourced).
- **Raw `schema.sql(...)` steps** apply in the replay, so their effect is introspected like any other step. Objects
  that no model can declare (functions, triggers, policies, extensions, comments) are outside the comparison
  (open question Q2).
- **A migration that fails to compile or replay** makes the command exit 2 with the migration id and the statement
  position. This is distinct from drift (exit 1).
- **`--write` when the only differences are destructive** writes nothing, prints the contract steps and exits 1.
- **PGlite is not installed in the member**: exit 2 with a message naming the missing package and the fix, as
  `loadDatabaseRunner` does today.

## Requirements

- **FR-001** `stackra db diff [--module <key>] [--json]` builds the migrated schema by applying the member's ordered
  compiled migrations (own and declared packages', in `orderMigrations` order) to an in-process PGlite. It then
  introspects tables, columns (type, nullability, default) and indexes (columns, uniqueness, predicate) for every
  module schema.
- **FR-002** It builds the modelled schema from gen's `MemberIR`: one table per model in its module's schema
  (snake_case plural), one column per persisted field with its nullability, and one index per `@Index` and per
  `@Searchable` filter, under the derived `idx_<table>_<columns>` name with `unique` and `where` as declared.
- **FR-003** It compares the two schemas and prints one line per difference: `<module>  <table>  <kind>  <subject>`.
  The kinds are `missing_table`, `undeclared_table`, `missing_column`, `undeclared_column`, `nullability`,
  `missing_index`, `undeclared_index` and `index_shape`, plus `column_type` if Q3 puts types in scope. Exit 0 when
  there is no difference, 1 on a difference, and 2 when a migration fails to compile or replay or a dependency is
  missing. `--json` prints the same findings as a JSON array.
- **FR-004** `stackra db diff --write <name>` writes each affected module's next
  `database/migrations/NNNN-<name>.migration.ts`, numbered per module from the last committed number with no gap. The
  file has a `Migration` class with `up()` only, literal table and column names, and an explicit nullability and
  `.comment()` from each field's docblock (ADR 0334 rule 1). It opens with `// generated by stackra db diff`, and it
  holds additive operations only.
- **FR-005** `--write` never writes a drop, a type narrowing or a nullability tightening. It prints each such
  difference as a contract step for a later release and exits 1 when one remains (ADR 0159 decision 3). An index
  build on an existing table is written as its own migration with a concurrent build.
- **FR-006** `stackra db structure [--module <key>] [--write]` prints the DDL the member's committed migrations build:
  schemas, tables, columns, constraints and indexes, normalised and sorted so two runs are byte-identical. `--write`
  writes it to the path Q5 settles. It never reads a live database.
- **FR-007** Neither command reads a connection string, an environment variable or a secret, and neither touches a
  real database. The CLI holds no database driver: the replay and the introspection run in the member's own
  `@stackra/database/node` through `loadDatabaseRunner`, which gains a `structure` entry (FR-001, FR-006).
- **FR-008** Both commands are listed in `COMMANDS` after `db rollback`, with `summary` and `usage`. The README and
  the `commands.constant.ts` docblock stop saying that `db diff` is pending.

## Success Criteria

- **SC-001** The invoicing#4 gate step `pnpm exec stackra db diff` runs and exits 0 on its branch.
- **SC-002** On every core package that ships migrations (database, search, access-log, loyalty-kit and the others),
  `stackra db diff` exits 0, or each difference it reports is filed as a fix.
- **SC-003** `stackra db diff --write` followed by `stackra db diff` exits 0 on a fixture with one added column and one
  added index.

## Open questions (for the leader; not decided here)

- **Q1 - What is `db structure`?** No ADR names it. ADR 0282's "structure" is the repository structure page, which
  already ships as `stackra structure`. Proposed: a print of the schema the migrations build, like Rails
  `structure.sql` or Laravel `schema:dump`. Is that the intent? Does it need an ADR, or an amendment to ADR 0282
  decision 3?
- **Q2 - Comparison scope.** Proposed: tables, columns, nullability and indexes. Out: foreign keys (links have none,
  ADR 0294 d28; relations do), check constraints, RLS policies, triggers, functions and comments. Should foreign keys
  or RLS (`tenant_id` with RLS enabled and forced) be in scope for the first cut?
- **Q3 - Column types and macro columns.** `EntitySchema` leaves column types to the migration, and no table maps
  `FieldIR` types and rules (`@Str({ max })`, `Money`, `PublicId`, `Translated`, `Link`) to Postgres types, or trait
  macros to their columns. Should the first cut compare types at all? If yes, should the mapping live in
  `@stackra/database` (beside `Blueprint`, which already knows its types) or in gen?
- **Q4 - Replay engine.** Proposed: PGlite, which is real Postgres and is already the `./testing` memory driver. It
  forces each member that runs the command to install two optional peers. The alternative is a pure structured
  schema state recorded by `SchemaRecord`: no dependency, but it duplicates Postgres semantics and misses raw
  `schema.sql` steps. A third option is the Testcontainers Postgres that `usePostgres` uses, which needs Docker.
  Which one?
- **Q5 - Where `db structure --write` writes, and whether it is committed.** Options: `.stackra/structure.sql`
  (gitignored, no ADR), or a committed `structure.sql` at the member root. A committed file would be a third
  committed generated contract next to `stackra.manifest.json` and `openapi.json` (ADR 0294 R10), so it needs an
  ADR, and `stackra gen --check` would have to keep it fresh.
- **Q6 - Should `db diff` run inside `stackra gen --check` or `stackra check`,** or stay a separate gate step? The gen
  phase already compiles every migration.
- **Q7 - A live-database mode.** Should either command compare against a real environment
  (`--env <environment>`, reading the connection the way `db migrate` does) to catch drift in a deployed database?
  Proposed: not in the first cut, because it adds a secret path and R3.
- **Q8 - Owner and release train.** Which session builds it, and does it land on 0.3.1 (`land/022-stack`) or wait for
  0.3.2? invoicing#4 is currently gated on it.

## Decisions (the leader, 2026-11-01)

- **Q1** `db structure` prints, and with `--write` writes to gitignored `.stackra/` only. It is not in US1.
- **Q2** The first cut compares tables, columns, nullability, indexes and foreign keys. RLS comes later.
- **Q3** Column types are compared, through a gen-side field-to-Postgres type map (`postgresTypeOf`). A field type with
  no agreed mapping is reported as `type_unmapped`, never guessed.
- **Q4** The replay runs on PGlite, loaded lazily by `@stackra/database/node` (`readMigratedSchema`) the way
  `requireTestPeer` loads its peers.
- **Q5** Gitignored (`.stackra/`).
- **Q6** `db diff` is its own gate step, not inside `gen --check`.
- **Q7** No live-database mode.
- **Q8** Ship on 0.3.1 if it fits.

US1 shape as built: the replay and catalog read live in `@stackra/database/node` (`readMigratedSchema`); the expected
schema, type map and differ are pure gen (`expectedSchema`, `postgresTypeOf`, `diffSchemas`); `checkMigrationDrift`
(`@stackra/gen/node`) joins them over the member's compiled migrations; the CLI command only prints and sets the exit
code. Only the member's own modules are compared (a declared package's tables are its own models').

## Out of scope

- `stackra db seed` (separate command, ADR 0190).
- Applying anything: `db migrate` stays the only command that writes to a database.
- The squawk lint (ADR 0159 enforcement, planned separately).
- Data backfills (queue jobs, ADR 0159 decision 3).
