**Input**: A migration that needs a Postgres extension (`vector`, `postgis`, `pg_trgm` …) failed on a fresh managed
server: the runtime plan carried each server's extensions, but nothing ran `create extension` with the admin login
before the migrations, and a service's own login may not create one. ADR 0160 decision 2 and its note of 2026-11-03
say the infrastructure pre-creates them; that note left it unbuilt. This spec is written after the fact from the PR's
diff (#1143, two commits), built before the spec gate (ADR 0502) required one.

## Impact _(mandatory, answer every line before /flow-clarify completes)_

- **Apps touched**: none
- **Services touched**: none (a service names its extensions in `environments.<env>.database.extensions` of its runway,
  as before)
- **Packages touched**: packages/developer/runway (`plannedExtensions`, `createExtensionsScript`),
  packages/infrastructure/infra-aws-runtime (`awsDatabases`, `awsWorkloads`, `awsRuntime`, `runtimePlan`, the
  migration run provider, `WorkloadMigrationInputs`, `DATABASE_SETUP_SETTINGS`), packages/infrastructure/infra-gcp
  (`gcpRuntimeConfig`, `GcpRuntimeConfig`, `gcpRuntime`, `databaseExtensions`, `DEPLOY_ROLES`,
  `DATABASE_SETUP_SETTINGS`)
- **Public contract change**: additive. New exports `plannedExtensions` and `createExtensionsScript` from
  `@stackra/runway`. `awsDatabases` takes an optional `ready` map and `awsWorkloads` an optional map it waits on;
  `WorkloadMigrationInputs` gains `purpose?: "migrate" | "extensions"`. `gcpRuntimeConfig` takes the parsed service
  runways as an optional fourth argument and `GcpRuntimeConfig.database` gains `extensions`; `gcpRuntime` takes
  optional `adminPassword` and `subnet` and refuses planned extensions without `adminPassword`. `DEPLOY_ROLES` gains
  `roles/secretmanager.admin`.
- **Cross-service events**: none
- **Tenancy and data**: extensions are created in `template1` and every database that takes connections (never
  `template0`, `rdsadmin` or `cloudsqladmin`); no row is read or written.
- **Security and privacy**: the admin password is the one secret. On AWS it is read at run time from the RDS Proxy
  secret, never put in the task definition or state. On GCP it arrives as a Pulumi secret input, goes only to the
  Cloud SQL admin user and an in-region Secret Manager copy that only the job's service account reads, and is never
  logged, returned or put in the job. Each setup task runs in its own outbound-only security group (AWS) the database
  admits. The script refuses any name outside `PostgresExtension`, so nothing unchecked reaches SQL or the shell.
- **Secrets**: the database admin password (no value in the repo; generated by the deploy job and kept in the vault,
  ADR 0493 decision 4, ADR 0525)
- **ADR needed**: no new ADR; ADR 0160 gains a note of 2026-11-26 recording the build
- **New dependencies**: none (a pinned Postgres client image at deploy time, named in `DATABASE_SETUP_SETTINGS`)
- **Deploy modes**: SaaS and on-prem cloud deploys on AWS and GCP; air-gapped installs pre-create extensions by their
  own runbook as before
- **Licence tier**: free (MIT, this repo)
- **UI surfaces**: none
- **Docs to update**: `apps/docs/src/docs/adr/0160-raw-sql-at-runtime-and-the-approved-postgres-extensions.mdx` (note

- **Change risk**: R3 (a secret input, a new IAM role for the deploy identity, and a step that can fail a deploy)

## Glossary _(full lane)_

- **Planned extensions**: the sorted union of the extensions the service runways name for an environment
  (`plannedExtensions`), narrowed to a database's consumers.
- **Extensions run**: the one-shot job (a Fargate task on AWS, a Cloud Run job on GCP) that runs the extension script
  with the admin login inside the apply.
- **Extension script**: `createExtensionsScript`: an idempotent psql script running `CREATE EXTENSION IF NOT EXISTS`
  for each extension in `template1` and every database that takes connections, stopping non-zero at the first failure.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - A migration that needs an extension succeeds on a fresh server (Priority: P1)

An operator deploys a project whose service names `vector` to a new environment. The apply creates the server, runs
the extensions run with the admin login, and only then runs the service's migrations, which find `vector` installed.

**Why this priority**: today the first deploy fails at the migration.

**Independent Test**: `awsDatabases` / `awsWorkloads` and `gcpRuntime` under Pulumi mocks with a service that names
extensions; the script against a real Postgres.

**Acceptance Scenarios**:

1. **Given** an AWS Postgres resource whose consumers name extensions, **When** the runtime is planned, **Then** a
   one-shot Fargate task with the admin login (password from the proxy secret) is declared, run once per revision in
   its own security group the database admits, and every workload migration and service using the resource depends
   on it.
2. **Given** a GCP server whose services name extensions, **When** `gcpRuntime` runs with `adminPassword`, **Then** it
   declares `stackra_admin`, the in-region secret, a reader service account and a Cloud Run job run to completion
   inside the apply (private IP with TLS, or the connector socket without a VPC).
3. **Given** the script, **When** it runs twice against Postgres 18, **Then** every extension exists in every database
   and a database created later from `template1` inherits them.

---

### User Story 2 - A failure stops the deploy before any migration (Priority: P1)

**Acceptance Scenarios**:

1. **Given** a login without CONNECT on one database, **When** the script runs, **Then** it stops with a non-zero exit
   and the run's failure says no migration ran.
2. **Given** planned extensions on GCP and no `adminPassword`, **When** `gcpRuntime` runs, **Then** it refuses with a
   message naming the extensions.

---

### User Story 3 - The deploy identity may create the job's secret (Priority: P1)

**Acceptance Scenarios**:

1. **Given** `gcpRuntime` with planned extensions on the private-IP and connector paths, **When** every provider module
   it declares is mapped to a role, **Then** each maps to a role in `DEPLOY_ROLES`, `roles/secretmanager.admin`
   included, and owner or editor is never granted.

---

### Edge Cases

- **EC-01**: A database whose consumers name no extension gets no run, and its environment no setup resources.
- **EC-02**: A member key without a runway (a workload) names none.
- **EC-03**: The GCP job runs again only when the extensions, the client image or the server change.
- **EC-04**: An empty list or a name outside `PostgresExtension` is refused by `createExtensionsScript`.
- **EC-05**: A migration's own `schema.createExtension` stays valid and finds the extension already there.
- **EC-06**: Direct VPC egress needs no compute role for the deploy identity; the Cloud Run service agent uses the
  subnet.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: `plannedExtensions(services, environment, members?)` SHALL return the sorted, deduplicated extensions the
  given members' runways name for the environment.
- **FR-002**: `createExtensionsScript(extensions)` SHALL return an idempotent psql script creating each extension in
  `template1` and every connectable database except `template0`, `rdsadmin` and `cloudsqladmin`, stopping non-zero at
  the first failure, and SHALL refuse an empty list or a name outside `PostgresExtension`.
- **FR-003**: `awsDatabases` SHALL give each Postgres resource whose consumers name extensions a one-shot Fargate run
  with the admin login, the password read from the RDS Proxy secret, in its own outbound-only security group the
  database admits, once per revision, and SHALL hand the run back by resource name through `ready`.
- **FR-004**: `awsWorkloads` SHALL start a workload's migration and service only after the extensions runs of the
  databases it uses.
- **FR-005**: THE AWS migration run provider SHALL run `purpose: "extensions"` as its own run whose failures say that no
  migration ran.
- **FR-006**: `gcpRuntimeConfig` SHALL return the services' planned extensions as `database.extensions`.
- **FR-007**: WHEN extensions are planned THE `gcpRuntime` SHALL declare the admin user, the in-region secret, the
  reader account and a Cloud Run job run to completion inside the apply, over private IP with TLS or the connector
  socket.
- **FR-008**: IF extensions are planned and no `adminPassword` is passed THEN `gcpRuntime` SHALL refuse.
- **FR-009**: `DEPLOY_ROLES` SHALL cover every provider module the extensions path declares
  (`roles/secretmanager.admin`) and never grant owner or editor.
- **FR-010**: WHEN no extension is planned THE runtimes SHALL declare no login, secret, job or setup resource.

## Acceptance criteria _(mandatory for a tiered spec, ADR 0502)_

- **AC-001**: WHEN a server's services name extensions THE infrastructure SHALL create them with the admin login in
  every database before any migration runs, on AWS and on GCP.
- **AC-002**: IF the extensions run fails THEN the apply SHALL fail and no migration SHALL run.
- **AC-003**: THE admin password SHALL never appear in a task or job definition, a log, an output or the state in plain
  text.
- **AC-004**: WHERE no extension is named THE runtimes SHALL declare nothing new.
- **AC-005**: THE deploy identity's roles SHALL cover every resource the extensions path declares.
- **AC-006**: THE script SHALL refuse a name outside the approved list.

## Compatibility and migration

- A project that names no extension sees no change.
- On GCP, a project that names extensions must pass `adminPassword` to `gcpRuntime` (the deploy job's, from the vault),
  enable the Secret Manager API (and the Compute Engine API for a private server), and re-apply the foundation stack
  (`ciAccess`) so the deploy identity holds `roles/secretmanager.admin` before the first runtime apply.
- On AWS, nothing changes for the caller beyond the new optional maps, which `awsRuntime` wires.

## Risks

- **R-1**: `roles/secretmanager.admin` is broader than the one secret the job needs; it is the only predefined role
  that covers `secrets.create`, `versions.add` and `setIamPolicy`. Mitigated: the deploy identity is already
  project-scoped and audited (ADR 0172); a custom role is a possible narrowing later.
- **R-2**: The admin login can create any approved extension in every database; the script refuses names outside
  `PostgresExtension`.
- **R-3**: The setup job adds time to the first apply of each revision; it runs once per revision (AWS) or only on a
  change (GCP).

## Out of scope

- Dropping an extension a service no longer names.
- Air-gapped installs (their runbook pre-creates extensions).
- A custom, narrower Secret Manager role.

## Assumptions

- The deploy job holds the server's admin password in the vault and passes it as a Pulumi secret.
