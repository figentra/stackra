# Implementation Plan: a tenant's login policy and MFA enforcement as an audited admin action

**Spec**: `.agents/specs/sta-2817-login-policy-action/spec.md` · **Linear**: STA-2817 · **Date**: 2026-11-26

**Input**: Feature specification from `.agents/specs/sta-2817-login-policy-action/spec.md`

## Summary

`@stackra/identity` gains a query and an action over the `IdpAdmin` login policy: `ShowLoginPolicyQuery` (L1) and
`SetLoginPolicyAction` (L3, `aal2` step-up, audited). The organisation comes from a new host port, `IdpOrganizations`,
given the session's scope. A pure check (`loginPolicyRejectionOf`) refuses a lock-out policy before any write. The
ZITADEL driver gains `getLoginPolicy`, writes in a sign-in-safe order, and manages `forceMfaLocalOnly` so a forced
second factor covers everyone.

## Correctness properties

- **P-001**: a set at the root scope with the permission and step-up writes the policy and answers it — Validates: AC-001
- **P-002**: the audit entry holds before and after and is recorded even when the provider write fails — Validates: AC-002
- **P-003**: no scope, an unmapped scope, or a descendant scope is `NotFoundError` for both calls — Validates: AC-003
- **P-004**: each lock-out shape and an unknown provider is `LoginPolicyRejectedError` with no write — Validates: AC-004
- **P-005**: the query answers the policy in force with its providers and factors — Validates: AC-005
- **P-006**: a failed factor or provider add leaves MFA unforced and methods on — Validates: AC-006
- **P-007**: forcing MFA writes `forceMfaLocalOnly: false`, after the factors are added; a local-only policy reads as
  not forced — Validates: AC-007
- **P-008**: kept settings survive an add and an update; 101 linked providers are all read — Validates: AC-008

## Architecture overview

The pipeline checks the permission and the step-up, then `SetLoginPolicyAction` asks `IdpOrganizations` for the
scope's organisation, refuses unless it belongs to that exact node, reads the policy in force, checks the requested
one (`loginPolicyRejectionOf`), audits before and after, and calls `IdpAdmin.setLoginPolicy`. The ZITADEL driver adds
or updates the organisation's own policy: loosened rules first, then the missing factors and providers, then the rules
as asked, removals last.

## Contracts

`IdpOrganizations`, `IdpOrganization`, `IdpAdmin.getLoginPolicy`, `LoginPolicyRejection`, `LoginPolicyRejectedError`;
the action, query and permissions with their manifest entries.

## Error handling

`NotFoundError` for a scope that is not the organisation's node (no existence leak); `LoginPolicyRejectedError` (with
its reason code) before any write; `IdpAdminUnavailableError` (retryable) when the provider fails part way, which
leaves a looser policy.

## Security and tenancy

The organisation is never input. The set call is L3 with a step-up and not an MCP tool. The audit carries rules and
provider-side ids only. A forced second factor reaches external-provider sign-ins.

A minor changeset for `@stackra/identity`. A product wires `IdpOrganizations` to its tenant map and grants
`identity.login_policy.set` at the tenant's root to its owner and administrator roles.
