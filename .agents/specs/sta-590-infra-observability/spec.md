**Input**: Build `@stackra/infra-observability` (infrastructure category, ADR 0127 and 0171 decision 2): the telemetry

- **Secrets**: no value in git. The OTLP token and the heartbeat URLs are secret Pulumi outputs; the archive's

- **ADR needed**: no (ADR 0184, ADR 0171 decisions 2 to 6, ADR 0127, ADR 0296, ADR 0185 decision 1)
- **New dependencies**: `@pulumi/pulumi` (peer), `@pulumi/aws`, `@pulumiverse/sentry`, `pulumi-logtail` and
  `pulumi-better-uptime`, referenced as `catalog:infra`, which the integrator adds
- **Deploy modes**: SaaS core stack; on-premises installs use the bundled LGTM stack and do not run it
- **Licence tier**: free (MIT; ADR 0171 decision 5 lists observability as free)
- **Docs to update**: `packages/infrastructure/infra-observability/README.md`,
  `packages/infrastructure/infra-observability/AGENTS.md`
- **Lane**: full (a new package)
- **Change risk**: R2 (new public contract; declares cloud resources only under `pulumi up`, which is the owner's)

## Clarifications

### Session 2026-10-25

- The `observability` section of the root runway is left open by `@stackra/runway` for its owner to check; this
  package checks it, strict, with the ADR 0184 values as defaults (30 days hot, 13 months in S3, every heartbeat on,
  objectives from the first paying tenant).
- The OTLP destination is a Better Stack OpenTelemetry source in the core stack (ADR 0171 decision 6), created when
  the root runway names `providers.betterstack`; the template's `ref:otlp.endpoint`, `ref:betterstack.source` and
  `ref:sentry.dsn.<member>` are this stack's outputs, copied into the stack config by the stacks repository.
- Heartbeats and alerts go to the deployed environments only: dev runs on a developer machine and a preview lives
  for days. A missed heartbeat mails and pushes whoever is on call (ADR 0185 decision 1).
- Indicators are measurements without targets, over the stable OpenTelemetry HTTP server histogram; objectives start
  at the first paying tenant (ADR 0184 decision 3).
- The services' jobs (crons, relays, workers) and their periods come from the caller, which reads the services'
  manifests; this package reads no file.

## User Scenarios & Testing

### User Story 1 - `stackra infra gen` builds the telemetry plan (Priority: P1)

The CLI reads the root runway, the app runways and the services' jobs, and gets one plan, or every failure at once.

**Independent Test**: `src/core/functions/__tests__/observability-plan.function.test.ts`.

**Acceptance Scenarios**:

1. **Given** the template's root runway, the web and mobile apps and two services, **When** `observabilityPlan` runs,
   **Then** the plan has staging and production, 30 days hot and 13 months cold, a heartbeat per environment and job,
   the `acme-web` and `acme-mobile` Sentry projects and two indicators per service.
2. **Given** an omitted key, **Then** it takes the ADR 0184 value; **given** a switch that is off, **Then** that
   kind's jobs get no heartbeat.
3. **Given** a misspelt or out-of-range `observability` key, retention or heartbeats without `providers.betterstack`,
   a Sentry project without an organization or claimed twice, or a job of an unknown service, with a bad name, a
   period under 30 seconds or listed twice, **Then** it throws one `ObservabilityConfigInvalidError` naming every
   path.

### User Story 2 - `pulumi preview` declares the telemetry (Priority: P1)

Inside the generated program, `observabilityStack(plan)` declares the log pipeline, the Sentry projects and the
heartbeats, and returns the outputs the runways name.

**Independent Test**: `src/node/functions/__tests__/*.function.test.ts` (Pulumi mocks).

**Acceptance Scenarios**:

1. **Then** one OpenTelemetry source keeps logs searchable for the hot days and writes a private S3 archive that
   expires after the full cold months; the archive's user reaches that bucket only.
2. **Then** each app gets a Sentry project, a DSN key and, per deployed environment, a new-or-regressed issue alert.
3. **Then** each planned heartbeat is a Better Stack heartbeat, and its URL a secret output.
4. **Then** the outputs are `otlp.endpoint`, `otlp.token` (secret), `betterstack.source`, `sentry.dsn.<member>`,
   `heartbeats.<env>.<service>.<job>` (secret) and `slis`.

## Requirements

- **FR-001**: Entries `.` (isomorphic, no Pulumi import) and `./node` (the Pulumi programs); one symbol per entry.
- **FR-002**: `observabilityPlan(root, members)` checks the root runway's `observability` section (strict, ADR 0184
  defaults) and reads `project`, the environments, `providers.betterstack`, `providers.sentry.org`, each app's
  `telemetry.sentryProject`, the service keys and the heartbeat jobs.
- **FR-003**: Alerts and heartbeats cover every root environment except dev and preview; a job gets a heartbeat when
  its kind's switch is on, with a grace of a fifth of its period.
- **FR-004**: Every service gets an availability and a latency indicator over `http.server.request.duration`; no
  objective is declared before `slos.startAt`.
- **FR-005**: `logPipeline` declares the Better Stack OpenTelemetry source with the hot retention and, when the cold
  months are above 0, the S3 archive (private, encrypted, HTTPS only, expiring after the full months) with one user
  limited to that bucket.
- **FR-006**: `sentryProjects` declares the team, one project and DSN key per app, and per deployed environment an
  issue alert that mails the owners on a new or regressed issue.
- **FR-007**: `heartbeatMonitors` declares one Better Stack heartbeat per planned heartbeat; its URL is a secret.
- **FR-008**: `observabilityStack` composes the parts the plan holds and returns outputs keyed like the runways'
  `ref:` paths; no secret value is a literal, a file or a log line, and nothing here calls a cloud outside
  `pulumi up`.

## Success Criteria

- **SC-001**: The template's runways give a plan; every refusal names its path.
- **SC-002**: Every public symbol has a test in a `__tests__/` folder beside it.
- **SC-003**: `pnpm verify` green for the member (run in the separate testing workflow).

## Out of scope

- The `stackra infra gen/preview` command that composes this package, and listing the services' jobs from their
  manifests (cli and gen).
- Sending heartbeats (scheduler, outbox, queue) and the services' OTLP exporter and redaction (logger, errors).
- Objectives and their alerts: from the first paying tenant (ADR 0184 decision 3).
- The on-call rotation, the severities and the status page of ADR 0185: owner decisions, and the status page starts
  at the first external customer.
